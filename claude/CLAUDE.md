**Fast is fine, but accuracy is everything.**

# 開発スタイル

TDD で開発する（探索 → Red → Green → Refactoring）。
KPI やカバレッジ目標が与えられたら、達成するまで試行する。
ユーザーの意図と背景の理解を最優先し、不明瞭な指示は質問して明確にする。

# コード設計

- 関心の分離を保つ
- 状態とロジックを分離する
- 可読性と保守性を重視し、開発者の認知不可を最小限に保つ
- 冪等性と耐障害性を重視し、再実行・部分失敗・異常入力でも安全に失敗・回復するよう設計する
- コントラクト層（API/型）を厳密に定義し、実装層は交換容易性を保ち再生成可能にする
- 静的検査可能なルールはプロンプトではなく、その環境の linter か ast-grep で記述する

# 調査と推論の規律

- 推測のみで調査・実装を進めない。必ずソースコード・ドキュメント・実測（コマンド実行、ログ、テスト結果）を根拠にする。根拠が取れない場合は「未確認」と明示し、推測であることを区別する。
- 推論は内部で十分に冗長に行い、ユーザーへの回答・ドキュメント・コード内コメントは簡潔かつ明確に書く。
- 必要な根拠（参照ファイル・行番号・実行結果）と注意点（前提・制約・既知の落とし穴）を簡潔に補足する。

# 委譲ワークフロー

実装・修正・リファクタ・調査を含む作業は、応答や他ツール呼び出しに先立って必ず **dev-orchestration** スキルを起動し、その判定に従って codex（調査・レビュー）/ cursor（実装）に委譲する。エージェント役割、判定トリガー、協力ループ（plan → build → verify）、例外パス、レッドフラグの詳細はスキル本文を参照。ソースコードへの直接 Edit/Write は `~/.claude/hooks/delegate-coding.sh` で物理ブロックされる（バックストップ）。
