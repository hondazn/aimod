# コンフリクト解決

PR ブランチとそのベースブランチ間のマージコンフリクトを解決する。コンフリクトが単純な場合（変更箇所が重複しない、フォーマットだけの差分など）は自動で解決する。コンフリクトがロジックの競合や設計判断を伴う場合は、ユーザーに選択肢を提示して選んでもらう。

## 入力

$ARGUMENTS

- 任意: PR番号、PR URL、ブランチ名
- 省略された場合はカレントブランチから検出する

## 手順

### Phase 1: PR とベースブランチの特定

1. 入力に PR番号 または URL が含まれていればそれを直接使う。
2. それ以外の場合はカレントブランチを取得する: `git branch --show-current`
3. 対応する PR を探す: `gh pr view --json number,title,baseRefName,headRefName,mergeable,mergeStateStatus`
4. PR が見つからなければ、どの PR を対象にするかユーザーに確認する。
5. **ベースブランチ**を記録する（例: `main`、`develop`、スタックド PR の場合は dev ブランチなど）。

### Phase 2: 統合の計画

1. **最新を取得**: `git fetch origin <base-branch>`
2. **戦略を決める** — プロジェクトの merge / rebase 慣習を確認する:
   - CLAUDE.md、CONTRIBUTING.md、`.github/` 配下の設定を確認する
   - 履歴を調べる: `git log --oneline --merges -10`（マージコミットが多ければ merge ワークフロー、リニアな履歴なら rebase を示唆）
   - 判断がつかなければ、デフォルトは **merge** とする — より安全で履歴を保持できる
3. **スコープをプレビュー**: `git diff --stat origin/<base-branch>...HEAD` でこのブランチが変更している内容を、`git diff --stat HEAD...origin/<base-branch>` で分岐以降にベースブランチが追加した内容を表示する。

ユーザーに簡潔な計画を提示する:

> **PR #123**: `feature/foo` -> `main`
> **戦略**: merge（プロジェクト慣習に一致）
> **ベースブランチ** はこのブランチが分岐してから 12 件の新規コミットがある。
> merge で進める。

PR が既にマージ可能（コンフリクトなし）であれば、その旨をユーザーに伝える — 対応は不要。希望があればベースブランチを取り込んでブランチを最新化することも提案する。

### Phase 3: merge/rebase の実行とコンフリクト解決

統合を開始する。merge と rebase でフローが異なる:

#### merge フロー

1. `git merge origin/<base-branch> --no-ff` を実行する
2. コンフリクトが発生すると git はマージを一時停止する。コンフリクトしているファイルを一覧する:
   `git diff --name-only --diff-filter=U`
3. コンフリクトしている各ファイルを解決する（下記の分類を参照）。
4. 解決したファイルをステージする: `git add <file>`
5. 全ファイルを解決したら完了する: `git commit`（マージメッセージは自動生成）

**うまくいかない場合**: `git merge --abort` でブランチをマージ前の状態に戻せる。

#### rebase フロー

rebase はコミットを 1 つずつ再適用するため、各コミットでコンフリクトが現れることがある。

1. `git rebase origin/<base-branch>` を実行する
2. あるコミットでコンフリクトしたら、そのコミットのコンフリクトしているファイルを解決する。
3. ステージして続行する: `git add <files> && git rebase --continue`
4. rebase が完了するまでコンフリクトする各コミットについて繰り返す。

**うまくいかない場合**: `git rebase --abort` でブランチを rebase 前の状態に戻せる。
rebase が複雑になりすぎた場合（多数のコミットでコンフリクトが連鎖するなど）は、中断して merge 戦略に切り替えることを提案する。

#### コンフリクトの分類

コンフリクトしている各ファイルについて、両側の変更とマージベースを読み、それぞれの変更の意図を理解する。

**自動解決可能**（確認せず解決する）:

- **重複しない編集**: 同じファイルの別々の箇所への変更。コンフリクトマーカーが出ているのは近接によるもので、意味的な競合ではない。
- **些細なバージョンバンプ**: 両側がバージョンを上げている — 高い方を採用する。
- **import の並び順 / フォーマット**: 両側の import を統合するか、プロジェクトのフォーマッタを適用する。
- **削除 vs 未変更**: 一方が削除したコードを他方は触っていない — 削除を採用する。
- **追加的な変更**: 両側がリスト・配列・設定ブロックに独立した新規項目を追加した — 両方を含める。
- **生成ファイル**（lock ファイル、コンパイル済みアセット）: 手動で解決しない。削除して再生成する（例: `rm package-lock.json && npm install`）。

**ユーザー判断が必要**（選択肢を提示する）:

- **競合するロジック変更**: 両側が同じ関数/ブロックを異なる意図で変更している。
- **構造的なコンフリクト**: 一方がファイルをリファクタし、他方が旧構造に機能を追加している。
- **削除 vs 変更**: 一方が削除したコードを他方が変更している。

確認する際は、対応可能な選択肢とともにコンフリクトを提示する:

```text
## src/auth/handler.ts のコンフリクト (42-58 行)

**ベースブランチ** (`main`) の変更:
  - トークン検証を JWT ライブラリの呼び出しに置き換えた

**このブランチ** (`feature/foo`) の変更:
  - 検証の前にレート制限チェックを追加した

### 選択肢:
1. 両方を残す（レート制限 + JWT）— こちらで統合します
2. ベースブランチ版を残す（JWT のみ）
3. このブランチ版を残す（レート制限 + 旧検証）
4. このファイルは自分で手動編集する
```

ユーザーの選択を待ってから、そのファイルの処理を進める。

### Phase 4: 検証とプッシュ

1. 利用可能なら **プロジェクトのチェックを実行する**:
   - 型チェック（tsc、swiftc、cargo check など）
   - リンタ / フォーマッタ
   - テスト（最低でも変更ファイルに関連するテスト）
2. チェックが失敗したら原因を切り分けて修正する。修正が自明でない場合は、問題を説明してから進めるかユーザーに確認する。
3. リモートブランチに **プッシュ** する:
   - merge: `git push`
   - rebase: まずユーザーに確認し、その上で `git push --force-with-lease`
4. **PR ステータスを確認**: `gh pr view --json mergeable,mergeStateStatus`
5. 結果を報告する:
   > コンフリクトを解決してプッシュしました。PR #123 はマージ可能になりました。

## エッジケース

- **スタックド PR**: ベースブランチが main ではなく別のフィーチャーブランチの場合も同様に扱う — ベースは PR が向けている対象が何であれそれだ。
- **作業ツリーが汚れている場合**: 開始前にコミットしていない変更があれば、まず stash する（`git stash`）。完了後に復元する（`git stash pop`）。変更が保持されることをユーザーに伝える。

## 安全ルール

- 常に中断（abort）の経路を確保しておく。merge/rebase を開始する前に作業ツリーをクリーンにしておけば、`--abort` できれいに戻せる。
- ユーザーの確認なしに force push しない。
- 既にプッシュ済みのコミットを、ユーザーの確認なしに改変しない。
- 変更の意図が不明な場合は、推測せず常に確認する。
- ユーザーが明示的に一方を破棄すると選択しない限り、両側のすべての機能的変更を保持する。
