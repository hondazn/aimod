# Branch Sweep

ゴミ git ブランチ（ローカル・リモート）を素早く安全に削除する。手作業でやると退屈でミスが
起きやすい作業だ。どのブランチが本当に完了済みかを見極め、squash マージされたブランチは git
からは未マージに見えることを覚えておき、未プッシュの作業を巻き込まないようにし、今いるブランチ
を消さないように気をつける必要がある。このスキルは読み取り専用スクリプトで分類を行い、計画を
提示してから、安全なものをバッチコマンドで削除し、リスクのあるものは確認する。

## 入力

`$ARGUMENTS` — すべて省略可:

- リモート名（デフォルト `origin`）。
- `dry-run` / `just show` → 計画提示（Phase 3）で停止し、何も削除しない。
- 1 つ以上のリポジトリパス → 複数リポジトリを並列で掃除する（**マルチリポジトリ** 参照）。

## 安全モデル — 3 段階、うち 2 つは自動

ブランチが **ゴミ** であるとは、そのコミットが信頼できる場所に保存されていて、削除しても何も
失わない状態を指す。削除を **確認なしで** 正当化できる *完了が証明された* 経路が 2 つ、
確認セットの中で最も「はい」と言いやすい *復旧可能だが未マージ* の経路が 1 つある — ただし
後者も確認は取る。ユーザーのポリシーが「マージ済み → 自動、**未マージ → 確認**」だからだ。

**自動削除（作業がランドしたことが証明済み）:**

1. **デフォルトブランチにマージ済み。** tip が `main` から到達可能なので、作業はそこに存在する。
   `git branch -d` がこれを許可する — これが自然なゲートになる。
2. **マージされた PR 経由で squash マージ済み。** GitHub がコミットを *異なる* ハッシュの 1 つの
   新しいコミットに squash したため、ブランチは `main` の祖先では **なく**、git は未マージだと
   判断する。完了していることを知っているのは PR レコードだけ — だから
   `gh pr list --state merged` でクロスチェックする。これらは `git branch -D`（強制）が必要だが、
   PR が作業のランドを証明しているので安全。

**確認するが、コストは低い（復旧可能、完了は未証明）:**

1. **upstream へ完全プッシュ済み（ローカル）だが未マージ。** 全コミットが既にリモートにある
   ローカルブランチは、ローカルから削除しても損失ゼロで落とせる — `git checkout -b <name>
   <remote>/<name>` 一発で復旧できる。これは「**リモートが本体を持っているなら、ローカルは
   削除しても極めて安全**」というルールを体現している。ただし *未マージ + プッシュ済み* は、
   ユーザーがまだ作業途中のバックアップ用にプッシュした feature ブランチとまったく同じ形でも
   あるので、黙って削除すると嫌な驚きになる。確認セットの中で **最も安全** な項目として扱い、
   データ損失リスクではなく、摩擦の少ない「はいでよし」として提示する。

   **この「最も安全」は、リモート追跡参照が新鮮であることが前提**。「完全プッシュ済み」の
   判定は `<remote>/<name>` と手元のブランチを比べているだけで、サーバを見ていない。
   `git fetch --prune` が失敗していれば、サーバ上でとっくに削除された／巻き戻されたブランチの
   参照がローカルに residue として残り、`ahead=0` すなわち「リモートが本体を持っている」と
   誤判定する。そのまま `git branch -D` すると、**唯一のコピーを、リスクなしと説明しながら
   消す**ことになる。前提が崩れているときの扱いは Phase 1 と Phase 5 を参照。

それ以外すべて — ローカルにしかないコミット、upstream より進んでいるコミット、ユニークな
コミットを持ちマージ済み PR の無いリモートブランチ — は **本物の作業の唯一のコピーである
可能性** があるので、決して自動削除しない。1 つずつ確認し、何が懸かっているかを正確に示す。

**決して、絶対に手を出さない:** デフォルトブランチ、現在チェックアウト中のブランチ、
**オープン PR** を持つブランチ（レビュー中のアクティブな作業）、**worktree** でチェックアウト
されているブランチ（git がそもそも拒否する）、長期運用の保護ブランチ
（`main master develop dev staging production release/* hotfix/*`）。

## 手順

掃除が非自明な場合（複数ブランチ、または複数リポジトリ）は TodoWrite で各フェーズを管理する。

### Phase 0 — スコープ

ユーザーが複数リポジトリを指定した場合は **マルチリポジトリ** へジャンプしてファンアウトする。
そうでなければ git リポジトリ内にいることを確認し（`git rev-parse --git-dir`）、現在のリポジトリ
で続行する。

### Phase 1 — リモート状態を同期

```bash
git fetch --prune --quiet
```

これは重要だ: prune しないと、リモートトラッキング参照が古くなる — 既にリモートで削除済みの
ブランチが見えたり、他人がプッシュしたものを見落としたり、upstream ポインタが古いせいで
「完全プッシュ済み」の判定を誤ったりする。

**`fetch` が失敗した場合（オフライン、認証切れ、一時エラー）は、リモート追跡参照に依拠する
判定をすべて信用しない。** 分類スクリプトは fetch せず `refs/remotes/*` を読むだけなので、
分類結果の鮮度は直前の fetch がすべてだ。影響を受けるのは 2 つあり、**どちらもデータ損失に
つながる**:

- **SAFE_REMOTE の自動削除** — こちらが「マージ済み」と見ている裏で他人が積んだコミットごと
  リモートブランチを消しうる。→ SAFE として扱わず Phase 5 の確認対象に落とす。
- **CONFIRM_LOCAL の「完全プッシュ済み」判定** — `<remote>/<name>` が実体を失った residue でも
  `ahead=0` になる。→ 「はいでよし」の枠から外し、**データ損失の可能性**として提示する
  （Phase 5 の live 再チェックを使えば救済できる）。

安全なのは、ローカルの `git branch -d`（デフォルトブランチにマージ済み）と、マージ済み PR の
head SHA 一致で証明された `-D` だけ。前者はローカルのグラフだけで完結し、後者は `gh` の
ライブ応答と手元の tip を突き合わせているので、どちらも fetch の鮮度に依存しない。

ローカルの分類自体は引き続き有用なので続行してよい。Phase 3 の計画で、どの判定が
「fetch 失敗により格下げされた」のかを明示する。

組み込みの保護リストを超える長期運用ブランチがプロジェクトにある場合
（リポジトリの CLAUDE.md / CONTRIBUTING / ブランチ保護設定を確認）、それらを渡して削除候補に
ならないようにする:

```bash
BRANCH_SWEEP_PROTECT="main develop release/* qa" \
  bash scripts/classify-branches.sh <remote>
```

### Phase 2 — 分類

読み取り専用の分類スクリプト（スキルに同梱の `scripts/classify-branches.sh`。何も削除・変更
しないので再実行しても安全）を実行する:

```bash
bash scripts/classify-branches.sh <remote>
```

出力は `DEFAULT_BRANCH`、`CURRENT_BRANCH`、`COUNTS=` 行、（`gh` が使えないときの）任意の
`PR_NOTE=`、そして 5 つのセクション。各ブランチ行は `name<TAB>sha<TAB>reason` の形式。
`sha` は復旧用ハンドルなので保持しておく。

**`PR_NOTE=` が出たら Phase 4 の自動削除を行わず、全件 Phase 5 の確認に回す。** PR 情報は
`gh` からしか得られないため、`gh` が無い・未認証・API 失敗のとき、この 2 つが同時に失われる:

- **オープン PR の保護** — 「オープン PR を持つブランチには決して手を出さない」は
  `gh pr list` の結果に依存している。取れなければ open PR 判定は常に偽になり、該当ブランチは
  SKIPPED に入らず **SAFE_LOCAL / SAFE_REMOTE に落ちうる**（実測確認済み）。レビュー中の
  ブランチをリモートごと消せば PR も壊れる。
- **squash マージの検出** — 完了しているブランチが CONFIRM 側に見える（安全方向の誤りなので
  害は小さい）。

前者は自動削除と両立しないので、`PR_NOTE` があるあいだ Phase 4 は使わない。

### Phase 3 — 計画を提示

何も削除する前に、分類スクリプトと同じグルーピングで、**ユーザーの言語で** コンパクトな
テーブルを提示する:

- **削除する（安全）:** SAFE_LOCAL + SAFE_REMOTE。各 1 行の理由付き。
- **先に確認する（リスクあり）:** CONFIRM_LOCAL + CONFIRM_REMOTE。何が懸かっているか
  （保存されていないコミット数）付き。
- **残す（保護対象）:** SKIPPED。理由付き（default / current / open PR / worktree）。

入力が `dry-run` だった場合は、ここで停止する。

### 削除の前に — backup ref（Phase 4 / 5 共通）

**デフォルトブランチから到達できないコミットを消すときは、必ず先に backup ref を書く。**

実行のはじめに run ID を 1 つ決め、その run のすべての退避で使い回す:

```bash
RUN_ID=$(date -u +%Y%m%dT%H%M%SZ)-$$   # 秒解像度だけだと同一秒の再実行で衝突するので PID を足す
git update-ref refs/branch-sweep-backup/$RUN_ID/local/<name>  <sha>   # ローカル削除の退避
git update-ref refs/branch-sweep-backup/$RUN_ID/remote/<name> <sha>   # リモート削除の退避
```

対象は「`git branch -d` で消せるもの以外すべて」— squash マージのローカル削除、CONFIRM_LOCAL、
およびリモートブランチの削除全般。`-d` で消えるものはデフォルトブランチがコミットを保持して
いるので不要。

**`<run_id>/<scope>/` を挟むのは、ref 名が衝突すると退避が黙って上書きされるからだ。**
`update-ref` は同名の ref を警告なく置き換える — 平坦に `refs/branch-sweep-backup/<name>` と
すると 2 通りで壊れる:

- **同じ run 内** — 同名のローカルとリモートは別の SHA を指しうる（ローカルが先行している等）。
  後から書いたほうが先の退避を消し、そちらのコミットは到達不能になる。
- **run をまたぐ** — feature ブランチの名前は再利用される。前回の退避を片付ける前に同名の
  ブランチをもう一度掃除すると、前回分の保証が消える。

**`update-ref` が失敗したらそのブランチは削除しない。** 退避先がネストする場合
（`feat` を退避済みのところへ `feat/foo`）、git は
`cannot lock ref ...: 'refs/branch-sweep-backup/<run>/local/feat' exists` として
**非 0 で終了する**。ここを見ずに削除へ進むと、退避なしで消すことになる — backup ref を
書く目的そのものが失われる。失敗したものは削除せず、理由を添えてレポートに残す。

なぜ必須かというと、**削除後にコミットを到達可能に保つものが何も残らない**からだ。ローカル削除は
ブランチ自身の reflog ごと消し、リモート削除は `refs/remotes/<remote>/<name>` を落とす。
このスキルはチェックアウトしないので HEAD の reflog にも載らない。結果、`gc` が回った時点で
控えた SHA すら使えなくなる（詳細は Phase 6「復旧の実際」）。ref を書いておけば本物の
到達可能性が与えられ、`gc --prune=now` を通してもコミットは残る。

### Phase 4 — 安全セットを削除（自動、バッチ）

ユーザーが選択したポリシーに従い、マージ済み/安全セットはこれ以上のプロンプトなしに削除する —
ただし常に可能な限り少ないコマンドにまとめ、常に計画を提示した後に行う。

**ローカル** — まずバッチ全体に対して安全削除を試みる:

```bash
git branch -d <safe_local_1> <safe_local_2> ...
```

**バッチは部分適用される。** マージ済みのものは削除され、拒否されたものだけが残り、それでも
全体の終了コードは 1 になる。`Deleted branch <name> (was <sha>)` の行と
`error: the branch '<name>' is not fully merged` の行を突き合わせて、どれが実際に消えたかを
判定すること（lease のバッチと同じ読み方）。

**`-d` のゲートを過信しないこと。** `-d` が見るのは「**upstream にマージ済み**、upstream が
無ければ HEAD にマージ済み」であって、デフォルトブランチではない。したがって
**未マージだが完全プッシュ済みのブランチは `-d` でも警告付きで削除される**
（`warning: deleting branch 'x' that has been merged to 'refs/remotes/origin/x', but not yet
merged to HEAD` と出るだけで exit 0）。つまり `-d` は、Phase 5 で確認すべき「完全プッシュ済み」
クラスを止めてくれない。**安全性を担保しているのは分類のほうであって `-d` ではない** — 渡す
名前は必ず SAFE_LOCAL に限ること。

`-d` が拒否する SAFE_LOCAL 項目は **PR マージ（squash）** のものだけ — その理由行には
`[git branch -D]` と書かれている。エスカレートするのは *それらだけ*（PR 検証済み — マージされた
PR が作業のランドを証明している）。ただし `-D` ではなく、**期待値を指定した plumbing で消す**:

```bash
git worktree list --porcelain | sed -n 's#^branch refs/heads/##p'   # ライブ確認。出たら消さない
git branch --show-current                                          # 同上
git update-ref refs/branch-sweep-backup/$RUN_ID/local/<pr_merged_branch> <sha> || exit
git update-ref -d refs/heads/<pr_merged_branch> <sha>              # <sha> は分類時の値
```

`git branch -D` は現在のブランチ tip を無条件に消すため、分類後にそのブランチへコミットが
積まれていると（別の worktree での作業、ユーザーの手動コミット）**その新しいコミットごと**
消える。退避した backup ref は分類時の SHA を指しているので、この分は救えない。
`update-ref -d <ref> <sha>` は ref が期待値と一致するときだけ削除し、動いていれば
`cannot lock ref ...: is at <new> but expected <old>` で**非 0 終了する**。

**plumbing はポーセリンの保護を持たないので、削除の直前に自分で確かめる。** `git branch -d/-D`
は現在チェックアウト中のブランチや worktree が使っているブランチを拒否するが、`update-ref -d`
は**拒否せず消す**（実測済み）。**SKIPPED を根拠にしてはいけない** — あれは分類時点の
スナップショットで、確認プロンプトを待つ数分のあいだに worktree が増えれば無効になる。
毎回ライブで引き直す:

```bash
git worktree list --porcelain | sed -n 's#^branch refs/heads/##p'   # worktree が使用中のブランチ
git branch --show-current                                          # このワークツリーの現在ブランチ
```

どちらかに名前が出たら削除しない。

**なぜ SHA 側だけ原子的にするのか。** ライブで引き直しても、引いてから消すまでの隙間は残る
（worktree はこの間に追加されうる）。SHA と worktree の両方を原子的に検査する手段は無いので、
**壊れたときに戻せないほう＝ SHA を `update-ref -d` の期待値に預ける**。worktree のほうは、
最悪すり抜けても壊れるのは worktree の状態であってコミットではない — backup ref から
ブランチを戻せば、その worktree はそのまま使える状態に復帰する（実測確認済み。復元は
Phase 6 の**作成専用形**を使うこと）。

**リモート** — 全部を 1 往復で。ただし **必ず lease を付ける**:

```bash
git push --force-with-lease=<name_1>:<sha_1> --force-with-lease=<name_2>:<sha_2> ... \
         <remote> --delete <name_1> <name_2> ...
```

`<sha_N>` は分類スクリプトが出力した SHA をそのまま使う（短縮形で通る）。

lease を付けない素の `--delete` は、サーバ上の現在値を一切見ずに ref を消す。`git branch -d` に
あたる安全ゲートがリモート削除には存在しないため、これが唯一の歯止めになる。分類時の SHA と
サーバの現在値が食い違えば git が `! [rejected] (delete) -> <name> (stale info)` で弾く —
他人が後から積んだコミットを巻き込まずに済む。

**終了コードではなく行単位の出力を読むこと。** 1 本でも弾かれると全体の終了コードは 1 になるが、
残りは削除済みになる（部分適用）。`- [deleted] <name>` の行だけを Phase 6 の削除済みリストに入れ、
`! [rejected] ... (stale info)` の行は「リモートが分類時から動いていた」ものとして、`git fetch
--prune` し直した上で Phase 5 の確認対象に回す。

削除前に SHA を控え、**squash マージの `-D` とリモート削除には backup ref を書く**（上記
「削除の前に」）。復旧 SHA が本当に復旧になるのは、lease がサーバの一致を確認できた場合だけ
である点にも注意 — lease 無しで消すと、表示した SHA には他人の新しいコミットが含まれず、
「取り消し可能」という約束そのものが崩れる。

### Phase 5 — 未マージセットを確認

CONFIRM_LOCAL / CONFIRM_REMOTE は 2 つのリスクレベルに分かれる — その違いを見せて、ユーザーが
安全なものを素早く承認できるようにする:

- **復旧可能（はいでよし）:** *「未マージだが完全プッシュ済み」* のローカル — リモートが全
  コミットを保持しているので、ローカルのコピーを落としても何も失わない。摩擦の少ないものとして
  提示する。確認が必要なのは未マージだからであって、リスクがあるからではない。
  **ただしこの枠に入れてよいのは、下記の live 再チェックを通ったものだけ。**
- **データ損失の可能性:** ローカルにしかないコミット、upstream より進んでいるコミット、
  ユニークなコミットを持ちマージ済み PR の無いリモートブランチ。これらは本物の作業の唯一の
  コピーかもしれない。live 再チェックに落ちた「完全プッシュ済み」もここに入る。

**live 再チェック — 「リモートが本体を持っている」をサーバに直接聞く:**

```bash
git ls-remote --heads <remote> refs/heads/<branch>
```

`refs/remotes/*` はローカルのキャッシュに過ぎず、`fetch --prune` が失敗していればサーバで
削除済み・巻き戻し済みのブランチの参照がそのまま残る。`ls-remote` はサーバの現在値を返すので、
fetch の成否と無関係にこの前提を検証できる。判定は:

- **出力が空** → サーバにそのブランチは無い。ローカルが唯一のコピー。**データ損失の可能性**へ。
- **SHA が手元の tip と不一致** → 巻き戻されている。手元にしかないコミットがある。同上。
- **SHA が一致** → 本当に完全プッシュ済み。「はいでよし」でよい。
- **コマンド自体が失敗**（ネットワーク断など）→ 検証できていないので **データ損失の可能性**へ。

**終了コードではなく出力を見ること。** ブランチが存在しないときも `ls-remote` は 0 で返り、
標準出力が空になるだけだ（`--force-with-lease` の部分適用と同じ落とし穴）。

**この再チェックは削除の直前にもう一度実行する。** ここで一度通しただけでは、
確認プロンプトへの回答を待っている数分がまるごと検証と削除の隙間に入る — その間にサーバから
ブランチが消えれば、「リモートが本体を持っている」という承認の根拠は失われたまま削除が走る。
待ち時間は隙間の大半を占め、かつ完全に避けられる。ここでの結果はユーザーに提示するリスク区分を
決めるためのもの、削除直前の結果が実際に削除してよいかの判定、と使い分ける。

判断材料として、各ブランチを未マージのコミット件名とともに表示する:

```bash
git log --oneline <default_branch>..<branch>        # ローカル
git log --oneline <default_branch>..<remote>/<branch>  # リモート
```

そして **AskUserQuestion** で確認する — リスクのあるブランチを列挙した 1 つのマルチセレクトでも
よいし、懸かるものが異なるなら 1 ブランチごとでもよい。全オプションのデフォルトは *残す* に
する。明示的な「はい」が出たときのみ、**再チェックを挟んでから**削除する:

```bash
# 「完全プッシュ済み」を根拠に消すローカルは、直前にもう一度サーバへ問い合わせる
git ls-remote --heads <remote> refs/heads/<branch>   # 空 / SHA 不一致 / 失敗なら中止して再提示
git worktree list --porcelain | sed -n 's#^branch refs/heads/##p'              # ライブ確認。出たら消さない
git branch --show-current                                                     # 同上
git update-ref refs/branch-sweep-backup/$RUN_ID/local/<branch> <sha> || exit  # 退避。失敗したら消さない
git update-ref -d refs/heads/<branch> <sha>                                   # ローカル。期待値付き（後述）

git update-ref refs/branch-sweep-backup/$RUN_ID/remote/<branch> <sha> || exit # 退避。失敗したら消さない
git push --force-with-lease=<branch>:<sha> <remote> --delete <branch>         # リモート
```

リモートは Phase 4 と同じく lease を付ける。ユーザーが「はい」と言った根拠は分類時点の
スナップショットであり、確認している間にリモートが動いている可能性は消えないからだ。

**ローカル削除も期待値付きで消す。** `git branch -D` ではなく
`git update-ref -d refs/heads/<branch> <sha>` を使い、その直前に worktree / current を
**ライブで**引き直す（理由と手順は Phase 4 の同じ記述を参照）。これで **ローカル側のずれ**
（分類してから消すまでにブランチが動いた）は原子的に弾ける。ここで SKIPPED を再利用しては
いけない — 確認待ちの数分は worktree が増えるのに十分な時間だ。

**それでも残る隙間について。** 上で塞げるのは「ローカルの ref が動いた」ケースだけだ。
`ls-remote` が確かめた **リモート側の状態** については、リモート削除と違って原子的な手段が無い。
lease はサーバ側で「参照の現在値の確認」と「削除」を不可分に行うので、リモート削除に隙間は
無い。一方 `ls-remote`（サーバへの問い合わせ）と `update-ref -d`（手元の ref 操作）は別マシン上の
別々の操作であり、両者を不可分にまとめる手段は無いため、**直前に再チェックしても
ミリ秒規模の隙間は原理的に残る**。これは縮められるが消せない。

消せない代わりに、この隙間が起きても取り返しがつくようにしておく。それを担うのが上記
「削除の前に」の backup ref だ。**reflog はこの役目を果たさない**（理由は Phase 6
「復旧の実際」）。なお `update-ref -d` は `git branch -d/-D` と違って **SHA を一切出力しない**
ので、レポートに載せる SHA は分類結果か backup ref から取ること。`-d` が出す `(was <sha>)` も
**手がかりであって保証ではない** — オブジェクトが生きている間しか使えない。

### Phase 6 — レポート

何が起きたかを要約する。**復旧手順は backup ref を起点に書く** — `<sha>` を裸で示すだけでは、
下記の理由でその SHA が使えなくなりうる:

**復元コマンドは必ず「作成専用」形で案内する。** 復元は事故から時間が経ってから実行されうる —
そのあいだにユーザーが同名ブランチを作り直して作業している可能性がある。素の
`git update-ref <ref> <new>` も素の `git push <src>:<dst>` も、**既存の ref を黙って
上書きする**（後者は fast-forward なら通る）。復元が新たなデータ損失になっては本末転倒なので、
期待値に **全ゼロ OID = 「存在しないこと」** を渡して、既存があれば弾かれるようにする:

- **削除済み（ローカル）:** `<name> <sha>` → 復元は
  ```bash
  git update-ref refs/heads/<name> refs/branch-sweep-backup/<run_id>/local/<name> ""
  ```
  第 3 引数の空文字が「この ref は存在しないはず」の意味になり、既に在れば
  `cannot lock ref ...: reference already exists` で**何もせず失敗する**
- **削除済み（リモート）:** `<name> <sha>` → 復元は
  ```bash
  ZERO=$(git hash-object -t blob /dev/null | tr '0-9a-f' '0')   # そのリポジトリのゼロ OID
  git push --force-with-lease=<name>:$ZERO <remote> \
           refs/branch-sweep-backup/<run_id>/remote/<name>:refs/heads/<name>
  ```
  サーバに同名が復活していれば `! [rejected] ... (stale info)` で弾かれる。削除自体は lease で
  サーバの一致を確認した上で行っているので、backup ref の内容は確かに削除直前のものを指す

  **ゼロ OID をリテラルで書かないこと。** 桁数はリポジトリのハッシュ方式で変わる（SHA-1 は
  40 桁、SHA-256 は 64 桁）。40 桁を決め打ちすると SHA-256 リポジトリで
  `error: cannot parse expected object name` となり、**復元コマンドがそもそも実行されない**
  （上書きはされないので安全側に倒れるが、復旧できない）。上の導出は空 blob の OID を
  全部 `0` に潰すもので、どちらの方式でも正しい長さになる（両方で実測確認済み）。
  ローカル復元の `""` は長さに依存しないのでそのままでよい。

どちらも弾かれた場合は、**上書きせずユーザーに判断を返すこと**（同名の別物が存在している）。
- **削除を見送ったもの:** 理由を添えて挙げる — 退避の失敗（多くは退避先のネスト衝突。先に
  前回分を片付ければ次回は通る）、分類後にブランチが動いた（`update-ref -d` が
  `is at <new> but expected <old>` で拒否）、削除直前のライブ確認で worktree / current に
  入っていた、`ls-remote` の再チェックに落ちた、lease が `(stale info)` で弾いた
- **worktree が壊れた場合の修復:** 万一 worktree の使用中ブランチを消してしまったら、上の
  ローカル復元（作成専用形）でブランチを戻す。その worktree はそのまま使える状態に復帰する
  （実測確認済み）。ここでも素の `update-ref` を使わないこと — 壊れた worktree に気づく前に
  同名ブランチが作り直されていれば、その作業を上書きしてしまう
- **backup ref:** **この run の `<run_id>` を明示する**（復元にも後片付けにも必要）。内容に
  納得したら run 単位で片付ける:
  `git for-each-ref --format='%(refname)' refs/branch-sweep-backup/<run_id>/ | xargs -r -n1 git update-ref -d`。
  掃除しない限り残り続け、溜まると退避先の衝突も起きやすくなるので、**黙って溜めず必ず
  レポートに出す**
- **確認後に残した / 保護対象:** 簡潔なリスト。

**復旧の実際 — 「reflog があるから大丈夫」は、このスキルの削除には当てはまらない。**

一般には reflog が削除済みブランチの受け皿になるが、branch-sweep の削除はその条件から外れる:

- **HEAD の reflog に載らない。** このスキルは削除のためにチェックアウトしない（そもそも
  チェックアウト中のブランチは対象外）。HEAD がそのコミットを指したことがなければ、
  HEAD の reflog にエントリは残らない。
- **ブランチ自身の reflog はブランチと一緒に消える。** `git branch -d/-D` も
  `git update-ref -d` も `.git/logs/refs/heads/<name>` ごと削除する（どちらも実測確認済み）。
  結果 `git reflog --all` でもヒットしない。
- **一時的に生き延びるのは `refs/remotes/<remote>/<name>` のおかげ**だが、これは Phase 1 が
  問題にしていたまさにその residue であり、**次に成功した `git fetch --prune` が落とす**。
  その瞬間コミットは到達不能になり、あとは `gc` が刈るまでの猶予しかない。刈られた後は
  控えた SHA があっても復元できない。

リモート削除も同じで、`git push --delete` は `refs/remotes/<remote>/<name>` を落とすため、
デフォルトブランチに含まれないコミットはその場で到達不能になる。

したがって取り消し可能性を担保できるのは「削除の前に」で書く **backup ref** だけであり、
上のレポートはそれを起点に案内する。

## マルチリポジトリ（並列）

複数のリポジトリを掃除するとき、スピードの勝ち筋は **並列サブエージェント** — リポジトリごとに
1 つ、それぞれが自分のディレクトリでこの同じスキルを実行する。1 ターンで（並列ツールコールで）
起動する:

> `<repo-path>` で branch-sweep スキルを使ってゴミブランチを掃除して。ブランチを切り替えないこと
> — 削除にチェックアウトは不要。マージ済み/安全セットのみ自動削除し、リスクのあるものは削除せず
> 私にリストで返して。<language> で回答して。

サブエージェントは決して `git checkout`/`switch` してはならない（全エージェントの作業ツリーが
動いてしまう） — ブランチ *削除* にチェックアウトは不要なのでこれは安全だが、念のためプロンプト
に明記する。各リポジトリのリスクあるブランチリストを集め、それらをメインスレッドでユーザーに
確認する。

## スピードに関する注記

速い経路は、1 リポジトリ内での **並行ではなくバッチ化** だ:

- `gh pr list --state all` の 1 回の呼び出しで全ブランチの PR 状態を一度に分類する —
  ブランチごとの API 往復は不要。
- `git push --force-with-lease=b1:<sha> --force-with-lease=b2:<sha> ... <remote> --delete b1 b2 b3`
  は多数のリモートブランチを 1 往復で削除する; ブランチごとのループは遅い罠。lease は ref ごとに
  独立して判定されるので、バッチ化しても安全性は落ちない（1 本弾かれても残りは削除される）。
- `git branch -d b1 b2 b3` は多数のローカルブランチを 1 プロセスで削除する。

サブエージェント並列は、各リポジトリが本当に独立した作業であるマルチリポジトリのケースに
取っておく。

## 分類スクリプトが既に処理しているエッジケース

- **`origin/HEAD`** はリモート名に短縮され、ブランチに化けるが — フル refname でマッチすることで
  除外している。
- **Squash マージ** は git からは未マージに見える — マージ済み PR の head ref 経由で捕捉する。
- **Detached HEAD** — `CURRENT_BRANCH=<detached>`; 何も current として扱われない。
- **リモートなし / ローカルのみのリポジトリ** — リモートセクションは単純に空になる。
- **`gh` が無い / 未認証** — PR による補強がスキップされ、`PR_NOTE` が警告する;
  削除前に squash マージのブランチを手動で確認する。
- **macOS システム bash（3.2）** — スクリプトはそこでも動くように書かれている。
