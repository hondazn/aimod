# TypeScript 型設計 — 不正状態を作れなくする

型の仕事は、起こり得ない状態をコンパイル時に落とすことにある。網羅的な型を最初から書くのではない。実装中に「この組み合わせは起きないはず」と気づいた箇所だけ、その組み合わせが書けない型へ置き換える。

`as`（境界で検証を済ませた直後の1回を除く）・`!`・`any` は、型が仕事を放棄した印である。見つけたら、代わりに置く型を探す。

## いつ効くか / いつ効かないか

効く:

- 型・インターフェース・関数シグネチャを書く・直す
- フラグや省略可能フィールドが増え、有効な組み合わせを説明できなくなった
- 既存のスキーマや生成型があり、そこから形を導出できる
- 型を含むコードレビュー

効かない:

- 信頼境界での入力検証とパース → `coding-standards` の Parse don't validate
- 言語非依存の実装規律（認知負荷の閾値・CQS・テスト先行）→ `coding-standards`
- 構造の分割と境界の切り方 → `design-code` / `design-principles`

判断は一つ。**部分性（partiality）が現れた箇所だけ型を強くする。** 全操作が総関数である `T[]` はそのままにする。

## パターン一覧

| # | パターン | 何を不能にするか | 型の形 |
|---|---|---|---|
| 1 | ブランド型 | 同じ素の型どうしの取り違え | `string & { readonly __brand: "AgentId" }` |
| 2 | 判別可能ユニオン | 矛盾するフラグの組み合わせ | `{ kind: "idle" } \| { kind: "ready"; data: D } \| { kind: "failed"; error: E }` |
| 3 | NonEmpty | 空配列と、それを前提にした添字アクセス | `[T, ...T[]]` とガード `isNonEmpty` |
| 4 | Pairs | 奇数長のリスト | `[T, T][]` |
| 5 | 時間範囲 | 負の範囲、`start > end` | `{ start: Date; durationMs: number }` |
| 6 | 総関数 | 呼び出し側へ漏れる空・未定義 | 全入力で値を返す `sum(T[])`、境界で1回だけ `NonEmpty` へ絞る |
| 7 | 型の導出 | スキーマ・実装との二重管理 | `Pick` / `Omit` / `Parameters` / `ReturnType` / `Awaited` / `typeof` |
| 8 | オブジェクト引数 | 同型の位置引数の取り違え | `fn({ uri, selection })` |
| 9 | 網羅性検査 | 変種を足したときの分岐追加漏れ | `default` で `const _e: never = v` |
| 10 | `unknown` と絞り込み | `any` による型検査の停止 | `unknown` を受け、`typeof` / `in` / 判別子で絞る |

判別子の名前は1つに固定する（`kind` / `type` / `tag` のいずれか）。ブランドの形も既存コードの `readonly __brand: "X"` に合わせ、新しい流儀を持ち込まない。

## アンチパターン

| 症状 | なぜ壊れるか | 直し方 |
|---|---|---|
| `{ loading: boolean; diff?: X; error?: Y }` | フラグの組み合わせが意味を持たず、有効な状態を列挙できない | 状態ごとの判別可能ユニオン → [2] |
| `id: string` が複数の意味で流用される | 取り違えてもコンパイルが通る | ブランド型 → [1] |
| `as User` を境界で使う | 実行時に落ちるまで誤りが見えない | `unknown` からパースして型を獲得 → [10] |
| 引数が `any` | その値に触れる全箇所で検査が止まる | `unknown` に置き換えて絞る → [10] |
| `list[0]!` / `list.at(0)!` | 空のときに実行時エラー。型は嘘をついている | `NonEmpty` を要求するか `T \| undefined` を返す → [3] |
| コメントで `// start <= end` と書く | 不変条件が型に載らず、レビューでしか守れない | `{ start, durationMs }` → [5] |
| 公開型が内部実装の型を含む | 内部変更が呼び出し側を壊し、結合が固定される | 公開面は最小の構造にし、内部型を変換して渡す |
| 位置引数の羅列 | 順番を入れ替えてもコンパイルが通る | オブジェクト引数 → [8]（毎フレームのホットパスは除く） |

## サボった兆候

- 差分に `!` と `as` が増え、その正当化がコメントで書かれている
- フラグ変数が2つ以上あり、有効な組み合わせをコメントやテストで説明している
- 「ここは空にならない」の根拠が、型ではなく書き手の知識にある
- スキーマとは別に、同じ形の `interface` を手で書いている
- 変種を足したのに分岐を足していない。`never` 検査が無いのでコンパイルは通る
- 公開関数の型が、内部でしか使わない型をそのまま露出している

## 判定テスト

- 「不正な状態の値を構築できるか」— できるなら、型が仕事をしていない
- 「同じ `string` を取る2つの引数を入れ替えてもコンパイルが通るか」— 通るならブランド型が要る
- 「空・未定義のときこの関数は何を返すか」— 型に出ていないなら、境界か `NonEmpty` で1回だけ処理する
- 「変種を1つ足したとき、コンパイルエラーになる場所を挙げられるか」— 挙げられないなら網羅性検査が無い
- 「この型はスキーマや既存の型から導出できるか」— できるなら、手書きは必ずドリフトする
- 「公開している型は、呼び出し側が知る必要のある情報だけか」— 内部の型が漏れていないか
