# ドメインをモデリングすること

## ユーザー入力

```text
$ARGUMENTS
```

## このスキルの目的

ドメイン駆動設計の**戦術的設計（How: どう実装するか）** を担う。
境界の内側で、業務ロジックをどう表現し、どこにトランザクション境界を引き、
どの技術方式に乗せるかを決める。

**中心にあるのは一つの決定木**である。業務領域のカテゴリーを入口に、
実装方式 → 技術方式 → テスト方針が芋づる式に決まる。

そして本スキルの結論は、上流の判断を**検証し返す**。実装方式からカテゴリーを逆算して
事業側の認識とずれていたら、それは事業活動の理解を見直す絶好の機会である（後述「逆算検証」）。

境界そのもの（どこで文脈を切るか、業務領域をどう分類するか）は `/ddd-discovery` が扱う。
まだ決まっていないなら先にそちらへ行く。ただし**業務領域のカテゴリーさえ仮置きできれば本スキルは動く**。

## 訳語について

書籍『ドメイン駆動設計をはじめよう』(Vlad Khononov) の訳語を主に使う。

| 本スキルの用語 | 従来訳 | 原語 |
|---|---|---|
| 業務領域 / 中核・一般・補完 | サブドメイン / コア・汎用・支援 | subdomain |
| 区切られた文脈 | 境界づけられたコンテキスト | bounded context |
| 同じ言葉 | ユビキタス言語 | ubiquitous language |
| イベント履歴式ドメインモデル | イベントソーシング・ドメインモデル | event-sourced domain model |
| 業務イベント | ドメインイベント | domain event |
| 業務サービス | ドメインサービス | domain service |
| 送信箱 | アウトボックス | outbox |
| モデル変換装置 / 共用サービス | 腐敗防止層 / 公開ホストサービス | ACL / open-host service |

## 中心の決定木

上から順に評価し、最初に当てはまったものを採る。

```
業務領域のカテゴリーは？
│
├─ 補完的な業務領域 / 一般的な業務領域との連係
│   └─ データ構造は複雑か（1対多・多対多）？
│       ├─ はい → アクティブレコード
│       └─ いいえ → トランザクションスクリプト
│
└─ 中核の業務領域
    └─ お金 / 分析 / 監査記録を扱うか？
        ├─ はい → イベント履歴式ドメインモデル
        └─ いいえ → ドメインモデル
```

言い換えると、次の4つの問いを上から順に投げる。

1. お金や金融取引の追跡・一貫した監査記録・業務視点の深い行動分析が必要か → **イベント履歴式ドメインモデル**
2. 業務ルールは複雑か → **ドメインモデル**
3. データ構造は複雑か → **アクティブレコード**
4. いずれも否 → **トランザクションスクリプト**

決まった実装方式から、残りが決まる。

| 実装方式 | 技術方式 | テスト方針 |
|---|---|---|
| トランザクションスクリプト | レイヤードアーキテクチャ（3層） | 逆ピラミッド形（E2E 中心） |
| アクティブレコード | レイヤードアーキテクチャ（4層＝サービス層を追加） | ダイヤモンド形（統合テスト中心） |
| ドメインモデル | ポートとアダプター | ピラミッド形（単体テスト中心） |
| イベント履歴式ドメインモデル | CQRS | ピラミッド形 |

**例外**: 実装方式にかかわらず、**永続化モデルを複数持ちたい場合は CQRS が有効**である。

**「複雑か単純か」の判定補助**

- 複雑な業務ロジック＝入り組んだ業務ルール＋不変条件＋最適化アルゴリズム
- 単純な業務ロジック＝入力データの検証が中心
- **同じ言葉の複雑さで測る** — 主に CRUD 操作を説明していれば単純、
  入り組んだ業務プロセスと複雑な業務ルールを説明していれば複雑

**背後にある価値観**: できるだけ単純なツールを選ぶ。
ドメインモデル・イベント履歴式・CQRS は**本当に必要な時の最後の手段**である。

これは厳格なルールではなく経験則である。イベント履歴式に習熟して全領域をそれで実装するチームもある
（そのチームにとってはそのほうが単純だからである）。判定方法を自分たちの状況に合わせて変えてよい。

## 進め方

### 1. 入力を確認する

- 対象の区切られた文脈・業務領域は何か
- そのカテゴリー（中核 / 一般 / 補完）は何か。未確定なら仮置きする
- 既存コードがあるか（あるなら診断から入る → ステップ 5）

### 2. 決定木を通す

上の決定木で実装方式・技術方式・テスト方針を決める。
各方式の適用条件・利点・破綻する条件は **[references/logic-patterns.md](references/logic-patterns.md)**、
技術方式と CQRS の詳細は **[references/architecture.md](references/architecture.md)** を読む。

**1つの文脈に単一の技術方式を強制しない。** 1つの文脈が複数の業務領域を含むことがあり、
その場合は水平のレイヤーに加えて**垂直の境界（モジュール）**を引き、業務領域ごとに適切な方式を採る。
この垂直の論理境界は、将来より細かい区切られた文脈の物理境界にリファクタリングできる。

### 3. 逆算検証する — 上流に問いを返す

**これが本スキルで最も価値の高い手順である。**
実装方式を素直に選んだ後、そこから業務領域のカテゴリーを逆算し、事業側の認識と照合する。

| 不一致 | 二つの可能性 |
|---|---|
| 業務担当者は**中核**と考えるが、**1日で開発できる** | (a) 開発者が課題を簡単に考えすぎている → 課題のとらえ方の精度を上げる (b) その機能が競争優位に結びついていない → 重要性・優先度を再検討する |
| 業務担当者は**補完**と考えるが、**ドメインモデル／イベント履歴式が必要** | (a) 業務担当者が必要以上に創造性を発揮して要件を複雑化している（よくある）→ 要件はもっと単純にできるし、そうすべき (b) 業務担当者がその領域が**競争優位の源泉になり得ることに気づけていない** → 開発者が新たな収益源の発見に貢献できる |

開発者が業務担当者の知見を要するように、**業務担当者も開発者の知見を要する**。
不一致は問題ではなく、対話の機会である。

### 4. モデルを設計する

ドメインモデル系を選んだなら、部品を設計する。

- **値オブジェクト** — 値で識別する不変オブジェクト。「使える時はいつでも」使う。
  基本データ型への執着を解消し、その値を使う業務ロジックを一元化する
- **集約** — **データの一貫性を強制する境界**。トランザクション境界そのもの
- **業務イベント** — 集約が発行する、過去形の名前を持つ出来事
- **業務サービス** — 状態を持たず、複数集約にまたがる計算を担う

**守るべき原則**（理由とともに理解する。丸暗記しない）

- **1トランザクションで変更するのは1集約だけ。** 複数集約を1トランザクションでコミットしたくなったら、
  それは**集約の境界がまちがっている**というサインである
- **集約はできるだけ小さく。** 一貫性を保証する対象は、集約の業務ロジックが必要とするデータだけに限る。
  判定法は「そのデータが結果整合性しか保証されなかった場合、業務ロジックが不正な状態になる危険があるか」
- **外部の集約は ID で参照する。** 境界の外であることを明示し、固有のトランザクション境界を保証するため
- **状態変更は集約の公開メソッド（コマンド）経由のみ。** 外部には読み取りだけを許す

集約をまたぐ処理が必要になったら、サーガやプロセスマネージャーで結果整合に委ねる。
ただし順序を逆にしない — **集約境界の設計が不適切なことを補うためにサーガを使ってはいけない。**
サーガを書きたくなったら、まず「これは本来1つの集約なのではないか」を問う。
同じ集約に所属させるべきなのは、**強い一貫性が保証されたデータを必要とする処理**である。

設計の詳細、集約境界の引き方、複雑さと自由度の理論は
**[references/aggregates.md](references/aggregates.md)** を読む。

### 5. 既存コードを診断する

既存コードが対象なら、**事業価値と実装方式の不一致がひどい箇所を見つけること**が何より重要である。
典型例は、中核の複雑な業務ロジックがトランザクションスクリプトやアクティブレコードで実装されていること。
中核は変化し続けるので、そこの設計がまずいと変更が極めてやっかいで危険になる。

**診断の観点**

- [ ] 実装方式は、その業務領域のカテゴリーと課題の複雑さに合っているか
- [ ] **変更がやっかいで危険になっていないか** — 実装方式を見直す最重要のシグナル
- [ ] 補完のはずの領域で業務ロジックが複雑化していないか（収益に貢献するなら中核化の兆候、
      しないなら不必要な複雑さ）
- [ ] 複数集約にまたがるトランザクションがないか
- [ ] 集約に、一貫性と無関係なデータが増えていないか
- [ ] 結果整合でよいデータに、厳密な一貫性を課していないか
- [ ] 集約の内部から直接イベントを発行していないか（→ 送信箱を使う）
- [ ] 内部モデル・内部の業務イベントをそのまま外部に公開していないか
- [ ] 業務ロジックが UI や DB（ストアドプロシージャ）に漏れていないか
- [ ] 集約境界の失敗をサーガで補っていないか

診断項目の詳細と、アンチパターンの一覧は
**[references/evolution.md](references/evolution.md)** にある。

### 6. 移行計画を立てる

**大原則: 「大きな絵」を描き、「小さく始める」。**
全面書き直しはほぼ成功しないし、技術視点のシステム再構築を経営陣が支持することはまずない。

安全な移行の順序が決まっている。

```
トランザクションスクリプト → アクティブレコード → ドメインモデル → イベント履歴式ドメインモデル
```

**トランザクションスクリプトやアクティブレコードから、いきなりイベント履歴式に書き換えるのは無謀である。**
まず**状態ありの集約**を設計し、効果的な集約境界を見つけることに時間を使う。
状態ありの集約を経由してからイベント履歴式へ移るほうが、まちがったトランザクション境界を
持ち込む危険を冒すより桁違いに安全である。

**ドメインモデルへの移行は一気にやらなくてよい。値オブジェクトの抽出から始める。**
状態が変化しないオブジェクトを導入するだけで複雑さはかなり小さくなり、
本格的なドメインモデルに移行しなくても十分な効果がある。

各移行の具体的な手順（setter を private にしてコンパイルエラーで状態変更箇所を炙り出す技法、
イベント履歴への移行で過去を修復するか移行イベントで済ませるか、ストラングラー方式）は
**[references/evolution.md](references/evolution.md)** を読む。

### 7. 実装する

設計に沿ってコードを書く。同じ言葉を守る — クラス名・フィールド名・メソッド名・発行イベント名まで、
すべてその区切られた文脈の同じ言葉で命名する。

**業務ロジックを技術的関心事から完全に切り離す。** 実行基盤のライブラリやフレームワークに依存させず、
古くからある単純なオブジェクトだけで組み立てる。

文脈をまたぐ通信（送信箱、サーガ、プロセスマネージャー、モデル変換）を実装するなら
**[references/communication.md](references/communication.md)**、
イベント履歴式を実装するなら **[references/event-sourcing.md](references/event-sourcing.md)** を読む。

### 8. まとめる

```

**対象**
- 区切られた文脈 / 業務領域: [名前]
- カテゴリー: 中核 / 一般 / 補完（根拠）

**決定**
| 項目 | 選択 | 理由 |
|---|---|---|
| 業務ロジックの実装方式 | ... | ... |
| 技術方式 | ... | ... |
| テスト方針 | ... | ... |

**逆算検証**
- 選んだ実装方式から逆算されるカテゴリー: ...
- 事業側の認識との一致 / 不一致: ...
- 不一致の場合の解釈と、業務担当者に確認すべきこと: ...

**モデル**（ドメインモデル系の場合）
```

## 次のステップ

- **境界そのものを見直す** → `/ddd-discovery`
  逆算検証で不一致が出た、集約を単純化したら別のモデルが見えた、文脈間の通信が過剰だった —
  いずれも境界の再設計に戻る合図である
- **コード構造の設計に落とす** → `/design-code`
  型・インターフェース・データフロー・エラー境界を詰める
- **実装に着手** → 完了後は `/git-commit` → `/create-pr`

## 注意事項

- **集約や値オブジェクトを実装することが DDD ではない。**
  ソフトウェアの「設計」判断を「事業活動（ドメイン）」で駆動するのが DDD である
- **すべてかゼロかではない。** 全技法の習得・実践はおそらく不可能で、一部だけでも DDD は価値を生む。
  既存システムでは特に重要である
- 権威に訴えない。「本にそう書いてあるから集約を使おう」は禁じ手である。
  **その方法がどういう課題を解こうとしているか**の論理で説明する
- 複雑な手段を最後の手段として扱う。業務ロジックが単純なら、手の込んだ設計は不必要な複雑さを持ち込むだけである
- **実装がたいへんなら、それは重要な兆候である。** 事業モデルの発展や設計判断の進化を示している。無視しない
- 技術的視点でなく**業務の視点**で集約境界を決める。トランザクションの必要性を徹底分析して初めて設計できる
- 全面書き換えでなく、段階的な移行を選ぶ
- 全ての応答は日本語で行う
