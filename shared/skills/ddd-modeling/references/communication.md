## 1. outbox

**やってはいけない実装**: 集約の内部から `_messageBus.Publish(newEvent)` する。理由は2つある。

1. DB に新しい状態をコミットする**前**に発信するので、購読側が見る状態と不整合になりうる
2. コミットが失敗（書き込み競合・後続ロジックの無効判定・障害）してもロールバックできるのは DB だけで、
   **届いてしまったドメインイベントは撤回できない**

**アプリケーション層に移してコミット後に発行するのも不十分**である。
メッセージ通信基盤の停止や、コミット直後・発行前のサーバー停止で不整合になる。

**outbox の手順**

1. 更新された集約の状態とドメインイベントの**両方を一つのトランザクション**で DB にコミットする
2. 中継サービスが新規コミットされたドメインイベントを読み取る
3. 中継サービスがメッセージ通信基盤に発行する
4. 送信成功後、DB のイベントに送信済みの印をつける、または削除する

**実装の選択肢**

- リレーショナル DB なら**outboxテーブル**
- 複数ドキュメントのトランザクションができない NoSQL では、**集約レコード内に `outbox` 属性として
  イベントを埋め込む**
- 未送信イベントの読み取りは**プル方式**（ポーリング。負荷を抑えるため適切なインデックスが必要）か
  **プッシュ方式**（トランザクションログ追跡、DynamoDB Streams 等）

**保証は「少なくとも1回（at-least-once）」である。**
送信直後に「送信済」への更新が失敗すれば、次のサイクルで同じメッセージが二重送信される。
**購読側は必ずべき等に設計する。**

## 2. サーガ

開始から終了まで長く続く業務プロセス。厳密には**ドメインイベントとコマンドを対応させる仕組み**である。

「長く続く」は時間の絶対的な長さではなく、**多数のトランザクションで構成される**という
トランザクションの視点を指す。秒単位のものも年単位のものもある。

- 特定のイベントを検知して**暗黙的に**起動する
- 状態を持たない実装もある。状態を追跡する複雑なサーガはイベントソーシング集約で実装する
- 失敗時はシステムの一貫性を確保するため**補償アクション**を実行する

**例**

```
CampaignActivated   → SubmitAdvertisement
PublishingConfirmed → TrackPublishingConfirmation
PublishingRejected  → TrackPublishingRejection   ← 補償アクション
```

**重要**: **コマンド実行ロジックはサーガの外部に置き、非同期で実行する。**
サーガは `CommandIssuedEvent` を生成するだけにして、outbox で中継する。
そうすることで途中で障害が起きても確実なコマンド実行を保証できる。

## 3. プロセスマネージャー

業務ロジックが中心となる**複雑な**業務プロセスを扱う。プロセスの状態を管理し、次のステップを決める「CPU」。

| | サーガ | プロセスマネージャー |
|---|---|---|
| 対象 | 単純で直線的な業務フロー | 業務ロジックが中心の複雑な業務プロセス |
| 起動 | 特定イベントを検知して**暗黙的に** | **明示的に**起動する。特定のソースイベントと結びつかない |
| 状態 | 状態を持たない実装もある | 明示的なプロセス ID と永続化する状態を持つ。多くの場合、複数の集約の組み合わせ |

**見分ける経験則: サーガの実装で if-else による分岐が必要になったら、それはおそらくプロセスマネージャーである。**

**例**: 出張手配（フライト選定 → 本人確認 → 別便希望なら上司承認 → 航空券手配 → ホテル予約 →
予約できなければ航空券キャンセル）。プロセスマネージャーが各イベントを購読し、
`CommandIssuedEvent` を生成する。

## 4. サーガと一貫性の原則

> データが強く整合していると想定できるのは、集約の境界の内側だけである。
> 集約の境界の外側にあるデータは結果的に整合する。

**集約境界の設計が不適切なことを補うためにサーガを使ってはいけない。**
同じ集約に所属させるべき業務処理は、**強い一貫性が保証されたデータを必要とする処理**である。

サーガを書きたくなったら、まず「これは本来1つの集約なのではないか」を問う。

## 5. 変換の3方式

上流のモデルが下流に都合が悪いときに変換する。
実装は**ACL（下流側）と Open Host Service（上流側）でほぼ同じ**である。

| 種類 | 実装 | 使いどころ |
|---|---|---|
| **状態なし・同期** | 変換ロジックをコードベースに埋め込む、または API ゲートウェイ（Kong / KrakenD / AWS API Gateway / Apigee / Azure API Management）にまかせる | リクエスト時に即時変換する。API ゲートウェイなら複数バージョンの Published Language を提供しやすい。複数コンテキストから使われる変換装置は独立した**変換用 Bounded Context** になる |
| **状態なし・非同期** | メッセージプロキシが発行メッセージを代理受信 → 変換 → 本来の購読者へ転送。無関係なメッセージのフィルタリングもできる | **内部モデルやドメインイベントをそのまま外部にさらすのはありがちな誤り**。変換して Published Language にすることで実装の詳細をカプセル化し、内部イベントと公開イベントを区別する |
| **状態あり** | 永続化の仕組みが必要。API ゲートウェイでは実現できない。Kafka / AWS Kinesis（ストリーム）、Apache NiFi / AWS Glue / Apache Spark（バッチ） | ①到着データを一つにまとめる（複数リクエストの一括処理、細分メッセージの統合）②複数の発生元からのデータ統合（BFF など。複数上流を持つ下流の手前に置いて、データ連係と業務ロジックを分離する） |

どのパターンをいつ選ぶか（Partnership / Shared Kernel / Conformist / ACL / Open Host Service / Separate Ways）は
`/ddd-discovery` の `references/integration.md` を参照する。
