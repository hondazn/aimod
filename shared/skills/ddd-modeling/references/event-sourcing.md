# イベント履歴式ドメインモデル（イベントソーシング）

集約の現在の状態を記録する代わりに、ライフサイクルで発生する**すべての変化を一連のイベントとして永続化**し、
それを「真実を語る唯一の情報源」とする。

状態テーブルは「今」しか語らない。**どういう経緯で今に至ったかが欠落する**のが根本の問題である。

> 著者は「イベントソーシング」ではなく「イベント履歴式ドメインモデル」と呼ぶ。
> イベントソーシングは集約の状態管理に限らず適用できる一般的な手法だからである。

## 投影（projection）

イベント種別ごとに多重定義した `Apply` メソッドを順に実行して、任意のモデルを作る。
**同じ履歴から複数のモデルを投影できる**のが本質的な価値である。

| 投影 | 内容 |
|---|---|
| 状態モデル | 現在の状態。従来の状態テーブルに相当 |
| 検索モデル | 旧姓・旧電話番号も保持し、過去の値でも検索できる |
| 分析モデル | フォロー回数の集計など、業務的な集計値 |

`Version` は状態変更回数を表す。途中まで適用すれば**任意時点の状態**が得られる（タイムトラベル）。

## イベントストア

追記専用。最低限の機能は2つだけである。

- 特定エンティティの全イベント取得
- イベント追記

`Append(id, events, expectedVersion)` の `expectedVersion` で楽観的排他制御を行う。

**集約の操作手順**

1. イベント履歴を読み込む
2. ある時点の状態を再構築する
3. コマンドを実行し、業務イベントを生成する
4. 新イベントをイベントストアにコミットする

## 利点

- **タイムトラベル** — 分析、判定結果の検査、障害調査に使える
- **深い洞察** — 後から新しい投影を追加できる。設計時に予期しなかった問いに答えられる
- **厳密な監査ログ** — 法的義務や金融取引に有効
- **進化した楽観的排他制御** — 衝突かどうかを**業務視点で判定できる**

## 欠点

- **学習曲線** — チームに経験がないと相当な時間がかかる
- **モデルの発展性** — イベントのデータ構造の変更は、テーブル設計の変更よりはるかに難しい
- **技術方式の複雑さ** — CQRS が絡む（集約の状態でクエリできないため必須になる）

**正当な理由がなく、より単純な方法が使えるなら、これらの欠点は深刻である。**

## よくある質問

**性能は大丈夫か**

集約1インスタンスのイベントが1万を超えれば性能に影響する。
しかし実際には**100を超えるシステムはほとんどない**。まず計測すること。

それでも必要ならスナップショット（別プロセスが投影をキャッシュし、以降の差分イベントだけ適用する）。
ただし**スナップショットが要ると思ったら、まず集約の境界の設計を見直す**。
1万を超える規模でなければ、その複雑さは不要である。

**スケールするか**

集約 ID でシャーディングできるので簡単にスケールする。

**削除（GDPR）はどうするか**

「忘れられる内容」（forgettable payload）パターンを使う。
機微情報を暗号化し、鍵を別の Key-Value ストアに集約 ID を Key として保存する。
**鍵を消せば復元不能になる。**

**もっと単純な代替案ではだめなのか**

| 代替案 | なぜだめか |
|---|---|
| ログファイルへの書き出し | DB とファイルのトランザクション管理ができず、結果的に不整合になる |
| 状態＋履歴テーブルを同一トランザクションで更新 | 技術的には一貫するが、保守時に履歴反映を忘れる／履歴テーブルの扱いがいいかげんになる |
| トリガーで履歴を複製 | 書き忘れは防げるが、**業務の文脈（変更理由）が欠落する**。新たなモデルを投影できる可能性がきわめて小さくなる |

最後の点が決定的である。イベント履歴式の価値は「変化の記録」ではなく「**なぜ変化したかの記録**」にある。

## 導入時の説得

多くの人が「極端すぎる」と感じる方式である。有効な進め方は、**業務エキスパートと会話すること**。

状態更新式とイベント履歴式の2種類があることを伝え、違いとイベントソーシングの利点、
特に**時間軸にそったモデルの利点**を説明する。
たいてい、そこから得られる洞察の深さを気に入り、**業務エキスパート自身が同僚に売り込んでくれる**。

会話では同じ言葉を使うことを絶対に忘れない。

## 境界の外に出すときの注意

**イベント履歴式の集約の業務イベントを、そのまま他文脈に公開してはいけない。**
内部イベントは実装の詳細である。購読側が全業務イベントに依存すると、
イベント追加やデータ構造変更のたびに購読側も変更が必要になり、しないとデータ不整合が起きる。

公開する業務イベントをごく一部に制限するか、公開用に別種のイベントを設計する
（詳細は `/ddd-discovery` の `references/integration.md`）。
