# ドメインモデルの部品

ドメインモデル＝ロジックとデータの両方を一体化させた、事業活動を表現するオブジェクトモデル。

**2つの設計原則**

- **複雑さ** — 技術的関心事（DB・外部通信）から完全に切り離す。実行基盤のライブラリやフレームワークに
  依存させず、古くからある単純なオブジェクトだけで組み立てる
- **同じ言葉** — クラス名・フィールド名・メソッド名・発行イベント名まで、すべて区切られた文脈の同じ言葉で命名する

## 1. 値オブジェクト

**定義**: 内部のフィールド値の組み合わせによって識別されるオブジェクト。
明示的な ID フィールドは**不要**である（あると同じ値の重複行が作れてしまい、不具合の元になる）。

**実装要件**

- **不変**（イミュータブル）。変更は新インスタンスの生成で表現する（`red.MixWith(green)` は新しい色を返す）
- 同一性判定は値の比較でオーバーライドする（C# なら `Equals` / `==` / `GetHashCode`。`record` 型なら不要）

**効能**

- 「**基本データ型への執着**」というコードのいやな臭いを解消する
- 意図が明確になる
- 妥当性検査が値オブジェクト自身に一元化される
- **その値を使う業務ロジックを一元的に記述できる**のが真価である
- 不変なのでスレッド安全

**いつ使うか**: **使える時はいつでも**。エンティティの属性として使う。

特に重要な用途が**通貨・金銭的価値**である。基本データ型のままだと、丸めや端数処理に危険な不具合が入る。
他に、状態区分、パスワード、電話番号、身長など。

```csharp
Height.Metric(180) > Height.Imperial(5, 3)   // 単位変換を型の内側に閉じる
PhoneNumber.Parse("+972-52-1234567").Country // 派生属性を型が知っている
```

## 2. エンティティ

個々のインスタンスを特定する識別情報（ID）を持つ。ID 値はインスタンスごとに一意で、
存在する限り変更しない。値オブジェクトと違い不変ではない。値オブジェクトはエンティティの状態を表現する手段である。

**エンティティ単独では実装しない。必ず集約の一部になる。**

## 3. 集約

**定義**: 集約はエンティティである。ただし目標は**データの一貫性の保証**にある。
集約＝**データの一貫性を強制する境界**。

**カプセル化**

- 状態を変更できるのは**集約内部の業務ロジックだけ**
- 外部には**読み取りだけ**を許可する
- 変更は公開メソッド＝**コマンド**の実行を通す。通常の公開メソッド、または
  パラメーターオブジェクト（`Execute(AddMessage cmd)` の多態）で表現する
- **業務ルール（不変条件）を、受信するすべてのコマンドで検証して守る**

**アプリケーション層の役割**（実質はトランザクションスクリプト）

1. 最新状態の集約を生成する
2. 操作を実行する
3. 永続化する
4. 結果を返す

**並行処理の例外検査が一貫性保証の最重要部分**である。

**楽観的排他制御**: 集約に `_version` を持たせ、更新時に検査する。

```sql
UPDATE aggregates SET ..., agg_version = agg_version + 1
WHERE id = @id AND agg_version = @expected
```

**トランザクション境界の原則**

- 集約はトランザクションの境界である。集約の状態変更は**単一トランザクションで全部コミットするか、何もしないか**
- **複数の集約にまたがるトランザクションを実行してはいけない。** 集約ごとに独立したトランザクションで別々にコミットする
- 複数集約を1トランザクションでコミットしたくなったら、**集約の境界がまちがっている**というサインである

**集約のルート**: 外部に公開するインターフェース役のエンティティは1つだけである。
内部エンティティへのアクセスはルート経由のみに限る。

## 4. 集約の境界の引き方

複数オブジェクトを1トランザクションで扱う必要（同時更新、あるオブジェクトの業務ルールが別オブジェクトの
状態に依存する）から、集約はエンティティの階層構造になる。
業務ロジックが全オブジェクトを必要とするなら、その構造全体が1つの集約である。

**判断基準は一貫性である。** 集約の業務ロジックが**強い一貫性を必要とする情報だけ**を内側に入れる。
結果整合でよい情報は境界の外（別の集約）へ出す。

**具体的な判定法**

> そのデータが結果整合性しか保証されなかった場合、業務ロジックが不正な状態になる危険があるか？

例: 「対応期限の半分が経過してもメッセージが未読なら、別の担当者に再割り当てする」というルールがある場合、
既読／未読が結果整合だと大量の誤再割り当てが起きる。だから既読状態はチケット集約の内部で管理する。

**経験則: 集約はできるだけ小さく設計する。** 大きいとパフォーマンスとスケーラビリティの問題が出る。

**外部の集約は ID で参照する。**

```csharp
private List<ProductId> _products;
private UserId _assignedAgent;
```

境界の外であることを明示し、集約ごとに固有のトランザクション境界を持つことを保証するためである。

**技術的視点でなく業務の視点で決める。** トランザクションの必要性を徹底分析して初めて集約の境界を設計できる。

**集約を単純化するリファクタリングで、隠れていた別のモデル＝新たな区切られた文脈を発見することは少なくない。**

## 5. 業務イベント（ドメインイベント）

事業活動で起きた重要な出来事を表現するメッセージ。

- **名前は必ず過去形**（`TicketEscalated` 等）
- そのイベントに関する必要なデータをすべて提供する
- 集約の公開インターフェースの一部である。集約が発行し、他のプロセス・集約・外部サービスが購読する

**実装**: 集約内で `_domainEvents` リストに追加していく。
**発行そのものを集約内でやってはいけない** — 送信箱を使う（`communication.md` 参照）。

## 6. 業務サービス（ドメインサービス）

**状態を持たないステートレスなオブジェクト**で、業務ロジックだけを記述する。

**用途**: 集約や値オブジェクトにカプセル化するのが不自然なロジック、**複数の集約にまたがる計算・分析**。
例: 担当者の所属部門ポリシー＋勤務予定＋チケット優先度から対応期限を計算する。

**注意**: 業務サービスは「1トランザクション1集約」原則の抜け道ではない。
役に立つのは複数集約を**参照する計算ロジック**を書く場合である。

マイクロサービスや SOA の「サービス」とは無関係である。

## 7. なぜこれで複雑さが下がるのか

システムの複雑さ＝振る舞いを制御・予測する難易度＝**状態を表現するデータ項目の数（自由度）**である。

5つの公開 setter を持つクラスは自由度5。派生値を内部で計算するクラスは自由度2で、
見た目は複雑でも実は単純である。

**不変条件をカプセル化することで自由度が下がり、複雑さが小さくなる。**
これが集約と値オブジェクトの背景にある考え方である。

## 8. アンチパターン

| アンチパターン | なぜだめか |
|---|---|
| 値オブジェクトに ID を持たせる | 同じ値の重複行が作れてしまい、不具合の原因になる |
| 基本データ型への執着 | 妥当性検査ロジックが散らばり、検査済みの保証が難しくなる |
| 複数集約にまたがるトランザクション | 集約境界がまちがっているサインである |
| 業務サービスを1集約1トランザクション原則の抜け道にする | 業務サービスがあっても原則は変わらない |
| 集約の内部から業務イベントを発行する | コミット前の発信になり、撤回もできない。送信箱を使う |
| 集約に一貫性と無関係なデータを入れる | 不必要な複雑さ。性能も悪化する |
| 集約の機能の一部をストアドプロシージャに移す | ロジックが重複し、物理的・論理的に離れた実装は差異を生み、データ不整合の原因になる |
