# 技術方式とテスト方針

技術方式は、コードベースの関心事の境界を明確にし、**業務ロジックの拡散**
（UI や DB に業務ロジックが漏れる、複数コンポーネントに重複する）を防ぐ。

## 選択基準

| 技術方式 | 構造 | いつ使うか |
|---|---|---|
| **レイヤードアーキテクチャ** | プレゼンテーション層 / 業務ロジック層 / データアクセス層。各層は**直下の層のみに依存**する。派生としてサービス層を挟める | **トランザクションスクリプト / アクティブレコード**に適する。業務ロジック層がデータアクセス層に依存するため。ドメインモデルの実装も可能だが難しい（集約・値オブジェクトは基盤から独立すべきなので工夫が要る） |
| **ポートとアダプター** | プレゼンテーション層とデータアクセス層をインフラストラクチャ層に統合し、依存関係逆転で依存を逆転させる。業務ロジック層が中心になり、その上にアプリケーション層（ファサード）。業務ロジック層が「ポート」（抽象インターフェース）を定義し、インフラ層が「アダプター」として実装、依存性注入で結合する | **ドメインモデル／イベントソーシング**に最適。業務ロジックを技術的関心事から切り離せる |
| **CQRS** | コマンド実行モデル（強い一貫性・唯一の真実の情報源・楽観的排他制御）と、複数の読み取りモデル（投影のキャッシュ、読み取り専用、消して再生成できる）を分離する | 同じデータを複数のモデルで扱う必要がある場合（OLTP と OLAP、複数種類の永続化の併用）。**イベントソーシングには必須**（集約の状態でクエリできないため） |

**サービス層は常に必要ではない。**
業務ロジックがトランザクションスクリプトなら、それ自体が公開インターフェースなのでサービス層は復唱にすぎない。
アクティブレコードのように外部の制御ロジックが要る場合はサービス層が必要になる
（サービス層をトランザクションスクリプトで実装し、アクティブレコードを業務ロジック層に置く）。

## 用語の対応

| 本書の用語 | 別名 |
|---|---|
| プレゼンテーション層 | ユーザーインターフェース層 |
| サービス層 | アプリケーション層 / ユースケース層 |
| 業務ロジック層 | ドメイン層 / モデル層 / コア層 |
| データアクセス層 | インフラストラクチャ層 |
| ポートとアダプター | ヘキサゴナル / オニオン / クリーンアーキテクチャ |

**ポートとアダプター、ヘキサゴナル、オニオン、クリーンアーキテクチャは用語が違うだけで原則は同じ**である。

**レイヤー ≠ ティア**: レイヤーは論理的境界（同じライフサイクルで実装・進化・デプロイされる）、
ティアは物理的境界（独立してデプロイできる）である。

## CQRS の投影方法

| 方式 | 仕組み | 特性 |
|---|---|---|
| **同期投影** | 投影エンジンが最終チェックポイント以降の変更を業務系 DB に問い合わせ → 読み取りモデルを更新 → チェックポイント保存 | **チェックポイントを 0 にリセットするだけで、新規投影の追加やゼロからの再生成が簡単**。チェックポイントを使ったクエリが一貫した結果を返すことが重要（後から小さい値のレコードが現れるとスキップされる） |
| **非同期投影** | コミット済み変更をメッセージ通信基盤に発行し、投影エンジンが購読する | スケール・性能で有利。ただし**順序の乱れ・重複処理**で一貫性が崩れ、新規投影の追加・再生成が難しい |

**推奨: 常に同期投影を実装し、オプションとしてその上に非同期投影を追加する。**

## CQRS のよくある誤解

**「コマンドはデータを返さない」は誤りである。**

コマンドは成功／失敗と失敗理由を常に呼び出し元に知らせる必要があり、ほとんどの場合データを返すべきである。
返さない設計は不必要な複雑さを生み、ユーザー体験を損なう。

唯一の制限は、**返すデータは強い一貫性のあるモデル（コマンド実行モデル）を元にすること**である
（投影は即時更新とは限らないため）。

## 適用範囲 — 1コンテキストに単一の技術方式を強制しない

これらの技術方式は「Bounded Context の全体構造」ではない。
1つのコンテキストに複数の業務領域が含まれることがあり、**単一の技術方式を強制すると思わぬ複雑さを招く**。

水平のレイヤーに加えて**垂直の境界（モジュール）**を引き、業務領域ごとに適切な技術方式を採用する。
例: 最適化＝ポートとアダプター、キャンペーン＝CQRS、広告素材カタログ＝レイヤード。

この垂直の論理境界は、将来より細かい Bounded Context の物理境界にリファクタリングできる。

## テスト方針

| 形 | 構成 | 適する実装方式 | 理由 |
|---|---|---|---|
| **ピラミッド形** | 単体テスト中心、統合が少なく E2E がさらに少ない | ドメインモデル / イベントソーシング | 集約と値オブジェクトの単体テストが、業務ロジックのテストとして最も効果的である |
| **ダイヤモンド形** | 統合テスト中心 | アクティブレコード | 業務ロジックがサービス層と業務ロジック層の2層にまたがるので、2層を統合するテストが中心になる |
| **逆ピラミッド形** | E2E テスト中心 | トランザクションスクリプト | 業務ロジックが単純でレイヤー数が少ないため、処理フローを最初から最後まで検証するのが効果的である |

テスト方針は実装方式から導かれる。実装方式を変えたらテスト方針も見直す。
