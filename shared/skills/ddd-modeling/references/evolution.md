# 既存コードの診断と段階的な移行

皮肉なことに、**DDD が大きな効果をもたらすのはすでに稼働しているソフトウェア**である。
事業への貢献が実証済みで、技術的負債と設計の乱雑さの刷新が必要なシステムこそ、取り組む価値が最も高い。

「すべてかゼロか」は誤解である。全技法の習得・実践はおそらく不可能で、一部だけでも DDD は価値を生む。
限られた時間しかない既存システムでは特に重要な認識である。

## 1. 診断

**最も重要なのは、事業価値と実装方式の不一致がひどい箇所を見つけること**である。
典型例は、中核の複雑な業務ロジックがトランザクションスクリプトやアクティブレコードで実装されていること。
中核は変化し続けるので、そこの設計がまずいと変更が極めてやっかいで危険になる。

**既存システムの構造を調べる**

- 既存の構造は DDD の区切られた文脈ではなく、**開発の都合で分割したサブシステムの境界**であることが多い
- 注目点は**サブシステムごとのライフサイクルの違い**。モノレポや一枚岩でも、他と切り離して
  修正・拡張・テスト・配置できるサブシステムがないか確認する
- コンポーネントごとに含まれる業務領域、選択されている実装方式と技術方式を調べ、
  「現在の実装方式は課題の複雑さと合致しているか」「洗練させるべき場所はどこか」
  「手を抜ける／既製品を使える領域はどこか」を問う
- **異なるコードベースの業務ロジックも追跡する** — DB のストアドプロシージャ、サーバーレス関数

**進化のシグナル**

- [ ] **変更がやっかいで危険になっていないか** — 実装方式を見直す最重要のシグナル
- [ ] 補完のはずの領域で業務ロジックが複雑化していないか
      （収益に貢献するなら中核化の兆候、しないなら不必要な複雑さ）
- [ ] 文脈間の通信が過剰になっていないか（＝モデルが不適切）
- [ ] 複数の区切られた文脈にまたがる変更が頻発していないか（＝境界の設計失敗）
- [ ] 集約に、一貫性と無関係なデータが増えていないか
- [ ] **業務エキスパートの言葉が入り組んできていないか** — 実装方式の限界を示すサイン
- [ ] 組織の変化（チーム増加、拠点分散）に連係方法が追随しているか

**設計改善の前に、失われた業務知識を探す。**
中核で業務知識の消失があれば、関係者を集めてイベントストーミングを実施し、
修復しながら同じ言葉を育てる（`/ddd-discovery`）。

## 2. 移行の大原則

**「大きな絵」を描き、「小さく始める」。**

全面書き直しはほぼ成功しないし、技術視点のシステム再構築を経営陣が支持することもまずない。
リファクタリングでも置き換えでも、**少しずつ段階的に**進める。

**実装方式の変更を恐れない。** 事業の発展は予測不能で、全領域に同じ手の込んだ設計をすることは不可能である。

## 3. 論理境界から始める

第一歩は、システムを複数の業務領域に切り分けることである。
**物理的な区切られた文脈である必要はない。論理的な境界（名前空間・モジュール・パッケージ）と
業務領域の境界を対応させる**ところから始める。

```
Marketing.Application / Infrastructure / Model / Mobile / Services / UI   ← 技術視点
                            ↓
Marketing.AdvertisingMaterials / Campaigns / Optimization / Publishing    ← 業務視点
```

モジュール構成の変更は**比較的安全なリファクタリング**である（業務ロジックは変えず、型の配置場所を移すだけ）。
ただし DLL やリフレクションなど**完全修飾型名への参照を壊さない**よう注意する。

ストアドプロシージャにも新しい境界を適用する（プロシージャ名を改名する、
モジュールに対応するスキーマを DB に追加して移動する）。

**論理境界 → 物理境界へ変換する判断**

早い段階から小さく区切るのは危険である。**大きな価値を生む場所だけ**物理境界に変換する。

- **一つのコードベースを複数のチームが変更しているか** → チームごとに文脈を定義し、
  開発ライフサイクルを切り離す
- **競合するモデルが異なるコンポーネントに使われていないか** → 競合モデルをそれぞれ別の文脈に移す

## 4. 実装方式の移行手順

**移行の検知指標**: 既存の設計では目の前の事業ニーズにうまく対応できない状況。
とりわけ**変更がやっかいで危険であること**は重要なシグナルである。

安全な順序は決まっている。

```
トランザクションスクリプト → アクティブレコード → ドメインモデル → イベント履歴式ドメインモデル
```

### 4-1. トランザクションスクリプト → アクティブレコード

両者は同じ考え方（手続き的スクリプト）で、違いはデータ構造の扱い方だけである。

1. データ構造が込み入った部分を見つける
2. その部分のデータ操作をアクティブレコードオブジェクトにカプセル化する
3. DB を直接操作するのをやめ、アクティブレコード経由でモデルと構造を抽象化する

### 4-2. アクティブレコード → ドメインモデル

着手条件: 業務ロジックが複雑化し、データの不整合やロジックの重複が増えていることに気づいたとき。

**ステップ1: 値オブジェクトを見つける**

不変に表現できそうなデータ構造を特定し、関係する業務ロジックをそのメソッドとして記述する。
**ここだけでも十分な効果がある。** 状態が変化しないオブジェクトを導入するだけで複雑さはかなり小さくなり、
本格的なドメインモデルに移行しなくてもよい。

**ステップ2: setter を全部 private にする**

外部から状態変更できなくしてコンパイルエラーを出させ、**エラー箇所＝状態を変更している場所**を
機械的に特定する。これが移行で最も効く技法である。

```csharp
// before
public class Player { public Guid Id { get; set; } public int Points { get; set; } }

public class ApplyBonus {
  public void Execute(Guid playerId, byte percentage) {
    var player = _repository.Load(playerId);
    player.Points *= 1 + percentage / 100.0;   // ← ここがコンパイルエラーになる
    _repository.Save(player);
  }
}
```

**ステップ3: 状態変更ロジックをオブジェクトの内側へ移動する**

```csharp
public class Player {
  public Guid Id { get; private set; }
  public int Points { get; private set; }
  public void ApplyBonus(int percentage) { this.Points *= 1 + percentage / 100.0; }
}
```

**ステップ4: 集約の候補を探す**

業務ルールと不変条件の一貫性を厳密に保証するために必要な階層構造を検討する。
最小のトランザクション境界（＝一貫性保証に必要なデータの最小の集まり）を見つけ、
オブジェクト階層をそれに分解する。**外部の集約の参照は ID だけ**にする。

このとき、**結果的に整合すればよいデータに厳密な一貫性を保証していないか**を確認する。
技術的視点でなく**業務の視点**で判断する。トランザクションの必要性を徹底分析して初めて集約の境界を設計できる。

**ステップ5: 集約ルートを特定する**

外部に公開するインターフェースのエントリーポイントを決め、それ以外の内部メソッドは private にする。

### 4-3. ドメインモデル → イベント履歴式ドメインモデル

前提: **集約の境界を適切に設計したドメインモデル**であること。

**トランザクションスクリプトやアクティブレコードから、いきなりイベント履歴式に書き換えるのは無謀である。**
まず状態ありの集約を設計し、効果的な集約境界を見つけることに時間を使う。
状態ありの集約を経由してからイベント履歴式へ移るほうが、まちがったトランザクション境界を
持ち込む危険を冒すより桁違いに安全である。

集約のデータを直接変更する代わりに、集約のライフサイクルを表現する一連の業務イベントを特定する。
**最大の難所は既存集約の履歴**である（最新状態しかなく、変更履歴が残っていない）。対応は2択。

**(a) 過去の状態変化を修復する**

最新状態を投影できる「近似的」なイベント履歴を生成する。

1. 現在の集約データから、業務ロジック上ありえた状態変化のシナリオを想定する
   （例: 新規作成 → 連絡済 → 注文発行済 → 支払完了）
2. それを業務イベント列として書き出す
3. **検証**: イベント列を順に適用して投影した結果と元データを比較すれば、正しさを簡単に確認できる

欠点: 完全な修復はできない（例: 見込み客への架電回数＝失われた架電イベント数はわからない）。

**(b) 移行イベントとして表現する**

過去の履歴を失っている事実を認め、現在の全項目を載せた「移行」イベントを、
既存集約の**最初のイベント**として記録する。

- 利点: 過去の記録が失われたことが明示され、「履歴が完全に残っている」という誤解を防ぐ
- 欠点: 旧システムの存在がイベント履歴に残り続ける。最新状態を投影するたび移行イベントを意識することになる

## 5. ストラングラー方式

既存システムを段階的に置き換える方法。

1. 新たな要求を実装するための**区切られた文脈をストラングラーとして追加**する
2. 既存システム側の文脈では、**緊急度の高い修正を除き、機能の修正と拡張を停止する**
3. 既存機能を少しずつ新しい文脈へ移行する
4. **ファサード**（外部への公開インターフェースとして機能する薄い抽象レイヤー）を前段に置き、
   リクエストを既存システムか新文脈かに振り分ける
5. 移行完了（既存システム運用停止）後、**役目を終えたファサードを取り除く**

**データベース共有の例外**: 本来「一つの区切られた文脈に一つのデータベース」だが、
ストラングラー方式ではこの原則を緩めて DB を共有してよい。
新旧の連係を複雑にせず、分散トランザクションの複雑さを回避するためである。
**あくまで一時的な対応**で、既存システム消滅後は原則通りに戻す。

移行中は、**モデル変換装置**で新コードベースを古いモデルから保護し、
**共用サービス**で公開された言葉を提供して上流の変更が下流に影響しないようにする。

## 6. アンチパターン一覧

| アンチパターン | 内容 |
|---|---|
| 中核の業務領域にトランザクションスクリプト | 複雑な業務ロジックに対応できず、ロジックが重複して一貫性が崩れ、変更が危険な**大きな泥だんご**になる |
| 基本データ型への執着 | 標準ライブラリの型だけで事業活動の概念を表現する。妥当性検査ロジックが散らばる |
| トランザクション管理の欠落 | 複数更新を1トランザクションにしていない |
| （暗黙的な）分散トランザクション | DB 更新＋メッセージ発行、呼び出し元との通信を含む非べき等な操作 |
| 複数集約にまたがるトランザクション | 集約境界がまちがっているサインである |
| 値オブジェクトに ID を持たせる | 同じ値の重複行が作れてしまい不具合の原因になる |
| 業務サービスを1集約1トランザクション原則の抜け道にする | 業務サービスがあっても原則は変わらない |
| 集約の内部から業務イベントを発行する | コミット前の発信で撤回不能。送信箱を使う |
| 内部モデル／業務イベントをそのまま外部に公開する | 区切られた文脈の内部モデルを露出させる。公開された言葉に変換する |
| CQRS でコマンドがデータを返さない | 誤解。不必要な複雑さを生みユーザー体験を損なう |
| 集約境界の失敗をサーガで補う | 本来1つの集約であるべきものを分けている |
| 監査目的でログファイル／履歴テーブル／トリガーを使う | 順に、トランザクション不整合／書き忘れと軽視／**業務の文脈（変更理由）の欠落** |
| 1つの区切られた文脈に単一の技術方式を強制する | 思わぬ複雑さを引き起こす。垂直の境界で業務領域ごとに選ぶ |
| 不必要なスナップショット | イベントが1万を超える規模でなければ不要。まず集約境界の設計を見直す |
| **一つの集約を二つの区切られた文脈に分ける** | 事例研究で「自殺行為となった境界」と呼ばれた失敗。二重実装と本番データの長期汚染を招き、脱出に数年かかった |
| **集約ごとにサービスを分ける** | 事例研究で**分散した大きな泥だんご**を生んだ。サービス間通信が激増し、疎結合を狙って地獄の運用保守になった |

## 7. 移行時の安全弁チェックリスト

- [ ] 全面書き換えでなく段階的移行を選んだか
- [ ] トランザクションスクリプト／アクティブレコードから、いきなりイベント履歴式にしていないか
      （状態ありの集約を経由する）
- [ ] 値オブジェクトの抽出から始めたか
- [ ] 結果整合でよいデータに厳密な一貫性を課していないか
- [ ] 集約境界を技術視点でなく業務視点で決めたか
- [ ] ストラングラー方式ならファサードを置き、既存側の機能追加を止めたか。
      DB 共有が一時的措置だと合意できているか
- [ ] イベント履歴式への移行で、修復イベント方式か移行イベント方式かを選び、欠点を認識しているか
- [ ] モジュール移動で完全修飾型名への参照（DLL、リフレクション）を壊していないか
- [ ] 論理境界のまま留めるべきものを、早すぎる段階で物理境界にしていないか
