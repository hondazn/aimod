# 業務ロジックの4つの実装方式

選択の背骨は**業務領域のカテゴリー（中核・一般・補完）と業務ロジックの複雑さ**である。

## 選択の意思決定表

| 方式 | 適用条件 | 利点 | 破綻する条件 |
|---|---|---|---|
| **トランザクションスクリプト** | 業務ロジックが手続き的なデータ操作だけ。ETL（抽出・変換・書き出し）。**補完的な業務領域**。一般的な業務領域に導入した外部サービスとの連係。コンテキストをつなぐ ACL の一部 | 単純さ。抽象化が最小限、実行時オーバーヘッドが小さい、業務ロジックが理解しやすい | 業務ロジックが複雑になると、あちこちのスクリプトで同じロジックが重複し一貫性が崩れる。**中核の業務領域に使ってはいけない** |
| **アクティブレコード** | 業務ロジックは単純だがデータ構造が複雑（1対多・多対多）。用途はトランザクションスクリプトと同じ3種 | 複雑なデータ構造とテーブル構造のマッピングをカプセル化。DB 操作の最適化 | 用途は CRUD と入力値の妥当性検査程度に限定。**本質的にはトランザクションスクリプト**なので、複雑な状態遷移では同じく破綻する |
| **ドメインモデル** | 複雑な状態遷移・業務ルール・不変条件を扱う。**中核の業務領域** | 業務ロジックを集約と値オブジェクトの境界内にカプセル化し、自由度を下げて複雑さを制御する。ソースコードがユビキタス言語を話す | 業務ロジックが単純な場合に使うと、手の込んだ設計で**不必要な複雑さ**を持ち込むことになる |
| **イベントソーシング** | ドメインモデルと同じ対象（複雑な業務ロジック・中核）。加えてタイムトラベル／深い洞察／監査ログ／進化した楽観的排他制御が要る場合 | 過去の任意時点の状態を再現。1つのイベント履歴から後付けで新しい投影を追加できる。厳密な監査ログ。衝突を業務視点で判定できる排他制御 | 学習曲線／イベントのデータ構造変更が難しい／技術方式が複雑になる。**正当な理由がなく、より単純な方法が使えるなら欠点が深刻** |

## トランザクションスクリプトの落とし穴

「単純な方式」だが、見た目より難しい。よくある3つの失敗。

**1. トランザクション管理の欠落**

複数の更新を1トランザクションにしていないと、途中で障害が起きて不整合が残る。

**2. 分散トランザクション**

DB 更新とメッセージ発行の組み合わせなど。分散トランザクションはスケールせずエラーも起きやすいので、
多くの場合は使わない。対処は CQRS と**outbox**（`communication.md` 参照）。

**3. 暗黙的な分散トランザクション**

```sql
UPDATE visits SET count = count + 1 WHERE id = @id
```

単一テーブルの更新でも、**呼び出し元との通信を含む**ため、再実行で二重加算が起きる。対処は2つ。

- **べき等化** — 呼び出し元が最終値を渡す
- **楽観的排他制御** — `WHERE count = @expected` で期待値を検査する

## 現実的に考える

汎用ルールは無い。大規模データ処理では一貫性に柔軟なアプローチを取ることもある
（数十億件中 0.001% の重複・欠落を重大事件とするかどうか）。
特殊ケースを切り捨てるリスクと事業影響を評価して判断する。

## アクティブレコードと「貧血ドメインモデル」

アクティブレコードは「貧血ドメインモデル」としてアンチパターン扱いされることがある。
ただし**業務ロジックが単純なら問題はない**。むしろそこに手の込んだ設計を持ち込むほうが、
不必要な複雑さを生む。

問題になるのは、**中核の業務領域や複雑な業務ロジックに対してこれを使っている**場合である。
その判定は「業務ロジックが複雑か」であって、パターン名ではない。
