# 証拠の規律 — 述べる前に確かめる

**確認していないことを、確認したかのように滑らかに書かない。**

「確認した / していない」の二値では、実際には多くの報告がその中間に落ちる。
コンパイルは通った、テストは緑、しかし本番と同じ経路は通していない。
段階を数えて下限を決めると、届かなかったことを申告する場所ができる。

## いつ効くか / いつ効かないか

効く: 完了を宣言する直前。調査結果を報告する直前。委譲した作業を受け取った直後。
出荷前に「何が壊れるか」を問う直前。意図（なぜこうなったか）を述べる直前。

効かない:
- 実装中のテストの書き方・TDD の順序 → `coding-standards`
- 何を解くかの定義と未確認事項の整理 → `understand-problem`
- 既存コードの仕組み・置き場・流れ → `explain-system`
- 委譲そのものの設計 → `delegation-discipline`

## 証拠の強度

1. **そう言った** — 単独では価値がない
2. **該当箇所を指した** — 実在する `file:line`、またはライブラリの実装
3. **起こり得ないことを論証した** — 失敗経路を辿り、そこに到達しないことを示した
4. **実際に走らせた** — 本物のコードを呼び、間違っていれば失敗するスクリプトかテスト
5. **本番と同じ経路で再現した**

**下限は 4。** 4 に届かない主張は、届いていないことを明示する。
4 は多くの場合、対象の関数を実際に呼ぶ小さなスクリプト1本で足りる。

## 合格ではないもの

次はいずれも合格ではない。合格の定義より、合格でないものの列挙のほうが効く。

- コンパイルが通った
- 型検査が通った
- ユニットテストが緑
- lint が通った
- 差分が妥当に見える
- CI が緑
- 委譲先が「できました」と言った
- 判定不能だった

**判定不能は合格ではない。判定不能と書く。** 隠さない。

## 確信度に応じた語

語彙を確信度に対応づけて固定する。ラベルを付けるより、使える語を縛るほうが崩れにくい。

| 確信度 | 使う語 | 条件 |
|---|---|---|
| 直接の根拠がある | 「〜だから」「〜のために設計された」「〜を直した」 | **引用が隣にあるときだけ** |
| 複数の間接証拠が収束 | 「証拠は〜を強く示している」 | 根拠を列挙する |
| 解釈 | 「〜と思われる」「〜と整合する」「一つの読み方としては」 | 推論の鎖を明示する |
| 仮説 | 「〜の可能性はあるが、直接の証拠はない」 | 対立仮説と並べる |
| 不明 | 「〜を調べたが見つからなかった」 | 何を調べたかを書く |

使わない語: **「明らかに」「もちろん」「単に」**。明らかならその問いは立たない。
矛盾する出典は両方残す。

## 出荷前の安全事実

呼び出し元の grep は仕事ではない。grep が止まる先を見る。呼んでいるライブラリの実装、ピン留めバージョン、ワイヤ形式、DB カラム、別言語が読む同じバイト、フラグ、3ホップ先。

怖そうに見える変更は、たいてい **1つの安全事実** で大半の懸念が死ぬ。その事実を強度 4 まで持っていく。届かなければ未証明と書く。

## 意図は履歴から取る

コードの形は動機ではない。null チェックがあることは、null を恐れた理由を説明しない。

「〜のために設計された」は、コミット・PR・チケット・コメントの引用が隣にあるときだけ使う。先に `git blame` / `git log --follow` / `gh pr view` を当たる。コード形状から意図を推論しない。

## 空振りの扱い

調べて無かったことは成果である。**何を調べて何が無かったか**を書く。

「見つからなかった」より「Issue を A と B のキーワードで検索し、該当なし」のほうが役に立つ。
読み手が調査の網羅性を自分で判定でき、抜けを指摘できる。

**「分からなかったこと」の節が空なら疑う。** 調査に穴が無いことは稀である。

## 委譲の検証

委譲先は「やったこと」ではなく「やろうとしたこと」を報告する。要約ではなく成果物を見る。

- 差分そのもの（`git diff`）
- ファイルの中身
- 実行結果

代替物を証拠と呼ばない。スクリーンショット・ユニットテスト・状態の読み取りは、
それぞれが証明できる範囲を超えて使わない。

## サボった兆候

- 完了報告に、実行したコマンドとその出力が1つも入っていない
- 「〜のはずです」「問題ないと思われます」で締めている
- 「分からなかったこと」の節が無い、または空
- 委譲先の要約をそのまま貼っている
- 調べた範囲を書かずに「見つかりませんでした」とだけ書いている
- 呼び出し元を列挙して「影響はない」と書いた
- 意図をコード形状から書いた

## 判定テスト

- 「この主張は強度の何段階目か。4 に届いていないなら、そう書いたか」
- 「『分からなかったこと』の節が空か」— 空なら疑う
- 「委譲先の要約ではなく、成果物そのものを見たか」
- 「『動きました』の根拠は、本番と同じ経路を通ったか」
- 「『〜だから』と書いた箇所の隣に、引用または実行結果があるか」
- 「あまりに簡単に通ったと感じたか」— 感じたなら、対象より先に観測方法を疑う
- 「安全だと言った1事実を、強度4まで持っていったか。届いていなければ未証明と書いたか」
- 「意図を、コード形状から書いていないか」
