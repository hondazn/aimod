# RDBテーブル設計 — アンチパターン回避リファレンス

## 使い方

- **新規設計・DDL作成時**: 下の設計チェックリストを順に確認する
- **既存スキーマのレビュー時**: アンチパターン一覧を症状から引く
- 該当が疑われた項目だけ、同ディレクトリの `ANTIPATTERNS.md` の該当節を読む

## 設計チェックリスト（新規設計時）

1. **主キー**: 列名は `id` でなくエンティティを表す名前（`bug_id`）。交差テーブルは複合主キー。慣習だけで `id SERIAL` を足していないか → [4]
2. **関連**: 多対多は交差テーブル。カンマ区切り列・`tag1..tag3` 列・年別テーブルにしていないか → [2][8][9]
3. **外部キー**: すべての参照に宣言し、`ON UPDATE` / `ON DELETE` の挙動を設計したか → [5]、定義ミスは [26-27]
4. **複数親への参照**: `xxx_type` + `xxx_id` の二重目的キーを使っていないか → [7]
5. **可変属性**: EAVテーブルではなくサブタイプモデリングで表現したか → [6]
6. **データ型**: 金額・正確な小数は `NUMERIC`/`DECIMAL`（FLOAT禁止）→ [10]。値セットが流動的な列は ENUM/CHECK でなく参照テーブル → [11]
7. **大容量データ**: 外部ファイルパス格納とBLOBを要件（トランザクション・バックアップ・権限）で比較したか → [12]
8. **インデックス**: 実クエリを根拠に張ったか（闇雲に張らない・全廃しない）→ [13]
9. **正規化**: 1NF〜5NFに照らして冗長性・更新異常がないか → [A]
10. **横断プラクティス**: 時刻・ID戦略・マイグレーション互換・論理削除などは下の設計プラクティス一覧も確認 → [P1-P8]

## アンチパターン一覧

| # | 名前 | やりがちな設計 | 何が壊れるか | 解決策 |
|---|---|---|---|---|
| 2 | Jaywalking | 複数IDをカンマ区切りで1列に格納 | 検索・JOIN・集約・更新・FK検証すべて困難 | 交差テーブル |
| 3 | Naive Trees | 階層を `parent_id` だけで表現 | 深さ無制限の子孫取得ができない | 再帰CTE / 経路列挙 / 入れ子集合 / 閉包テーブル |
| 4 | ID Required | 全テーブルに機械的に `id` 列 | 冗長キー・重複行・JOINの列名衝突 | 意味のある列名、自然キー・複合キー活用 |
| 5 | Keyless Entry | 外部キー制約を宣言しない | 孤立行の混入、整合性チェックが全部アプリ任せ | FK宣言 + カスケード設計 |
| 6 | EAV | 属性を Entity-Attribute-Value の行として格納 | 型・NOT NULL・FKが効かず行再構築が爆発 | サブタイプモデリング（STI/具象/クラステーブル継承/JSON） |
| 7 | ポリモーフィック関連 | `issue_type` + `issue_id` の二重目的FK | FK制約を宣言できない | 参照を逆向きに（交差テーブル）or 共通の基底テーブル |
| 8 | Multicolumn Attribute | `tag1`,`tag2`,`tag3`... と列を複製 | 検索・更新が煩雑、一意性・上限が破綻 | 従属テーブル（1値1行） |
| 9 | Metadata Tribbles | 年別テーブル `Bugs_2020`... や年別列 | テーブル増殖・整合性/一意性/FK破綻 | パーティショニング、従属テーブル化 |
| 10 | Rounding Errors | 金額に FLOAT/DOUBLE/REAL | 丸め誤差の蓄積、等価比較の失敗 | NUMERIC / DECIMAL |
| 11 | 31 Flavors | 値リストを ENUM/CHECK に埋め込み | 値の取得・追加・廃止のたびに列再定義 | 参照テーブル + FK |
| 12 | Phantom Files | 画像は外部ファイル必須と思い込む | 削除・トランザクション・バックアップ・権限が非管理 | 要件次第で BLOB（思考停止の外部格納をやめる） |
| 13 | Index Shotgun | 根拠なくインデックスを張る/張らない/効かないクエリ | 無駄なオーバーヘッド or 全件スキャン | MENTOR原則（測定→解析→指名→テスト→最適化→再構築） |
| 26-27 | 外部キーの誤用 | 参照方向逆転・型不一致・インラインREFERENCES等 | エラー、または黙ってFKが作られない | 定義チェックリスト参照 |
| A | 正規化違反 | 繰り返しグループ・部分/推移的関数従属など | 冗長性と更新異常 | 1NF〜5NFの適用 |

## 設計プラクティス一覧（詳細は `PRACTICES.md`）

| # | トピック | 指針 |
|---|---|---|
| P1 | 時刻とタイムゾーン | UTCで格納・表示時に変換。`created_at`/`updated_at` を標準装備 |
| P2 | ID戦略 | 分散採番はUUIDv7/ULID（v4は断片化）。内部IDと公開IDを分離 |
| P3 | マイグレーション | expand-contract の3段階で新旧コード共存。大テーブルALTERのロック確認 |
| P4 | 論理削除 | 安易に `deleted_at` を足さない。UNIQUE干渉・全クエリ条件漏れの罠。履歴/アーカイブテーブルを先に検討 |
| P5 | NOT NULL/CHECK | NOT NULLをデフォルトに。値関係（`start <= end`）はCHECKで宣言 |
| P6 | 文字コード | MySQLは `utf8mb4` 必須。COLLATEは全体で統一 |
| P7 | 楽観ロック | 競合編集は `version` 列 + 影響行数チェック。集中カウンタのホットスポット注意 |
| P8 | 命名規約 | 1プロジェクト1規則。boolean `is_`、時刻 `_at`、主キーはエンティティ名入り |

## 横断原則

- **メタデータとデータを混ぜない**: 列名・テーブル名に値を埋め込まない（8, 9）。値に列名・テーブル名を埋め込まない（6, 7）
- **同じ意味の値は1つの列に格納する**（2, 8）
- **整合性はアプリコードでなく制約で強制する**（ポカヨケ。5, 10, 11）
- **測定してから最適化する**: インデックスも非正規化も、まず正規形+実測、逸脱は根拠を持って（13, A）

## 判定テスト

- 「この列は将来 NULL を持ちうるか。持つならその NULL が何を意味するか言えるか」
- 「主キーは業務上の意味を持つ値に依存していないか」
- 「このマイグレーションは、旧コードが動いたまま適用できるか」— できないなら段階を分けたか
- 「時刻列のタイムゾーンを、保存・比較・表示のどこで変換するか決めたか」
