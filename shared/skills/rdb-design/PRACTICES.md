# 設計プラクティス詳細

## P1. 時刻とタイムゾーン

- **UTCで格納し、表示時にユーザーのタイムゾーンへ変換する**。ローカル時刻での格納はDST・サーバー移設・多地域対応で破綻する
- 型の選択: PostgreSQL は `timestamptz`（UTCに正規化して格納）。naive な `timestamp` はタイムゾーン情報を持たず事故のもと。MySQL は `DATETIME` + アプリでUTC統一が無難（`TIMESTAMP` はUTC変換されるが**2038年問題**がある）
- 時刻が不要な日付（誕生日・締切日）は `DATE`。「その日」の意味がタイムゾーン依存になる点だけ注意
- 全テーブルに `created_at` / `updated_at` を標準装備する（障害調査・データ移行・監査の最後の砦）

## P2. ID戦略

- 単一DBで完結するなら auto-increment / シーケンスで十分（列名は `bug_id` 形式に）
- **UUIDv4 を主キーにするとB-treeへの挿入がランダム位置になり、インデックス断片化・キャッシュ効率低下を招く**。分散採番が必要なら時系列ソート可能な **UUIDv7**（RFC 9562）や ULID を使う
- UUIDは文字列（`VARCHAR(36)`）でなくネイティブ型（PostgreSQL `uuid`）/ `BINARY(16)` で格納する
- **内部IDと公開IDを分離する**: 連番を URL 等に露出すると総件数・作成順が漏れ、列挙攻撃（enumeration）を許す。外部にはUUID・ハッシュ化ID等を出す

## P3. 後方互換マイグレーション（expand-contract）

稼働中のシステムのスキーマ変更は「拡張 → 移行 → 収縮」の3段階に分け、**各段階で新旧コードが共存できる状態を保つ**（ロールバックは直前段階に戻すだけで済む）。

- 列追加は nullable（またはDEFAULT付き）で追加 → バックフィル（大量ならバッチ分割） → NOT NULL 等の制約付与、の順
- 列の改名・型変更は一発で行わず、新列追加 → 二重書き込み → 読み取り切替 → 旧列削除
- 大テーブルの ALTER はロック挙動を必ず確認する。PostgreSQL: `ADD COLUMN ... DEFAULT` はPG11以降書き換え不要、NOT NULL追加は `CHECK ... NOT VALID` → `VALIDATE CONSTRAINT` の二段が定石。MySQL: `ALGORITHM=INSTANT/INPLACE` を確認し、不可なら gh-ost / pt-online-schema-change
- DDLはアプリのデプロイと分離し、**DDL先行・コード後続**（前方互換）を原則にする

## P4. 論理削除の罠

`deleted_at`（または `is_deleted`）による論理削除は安易に採用しない。採用前に「本当の要件」を確認する — 復元機能か、監査証跡か、参照整合性の維持か。

- **UNIQUE制約と干渉する**: 削除済み行が UNIQUE(email) を占有し再登録できない。PostgreSQL は部分インデックス `CREATE UNIQUE INDEX ... WHERE deleted_at IS NULL`、MySQL は生成列（有効行のみ 1、削除行は NULL）+ 複合UNIQUEで回避
- 全クエリに `WHERE deleted_at IS NULL` が要る（漏れが即バグ）。ビューで包むか、ORMのデフォルトスコープで強制する
- 削除行の蓄積でテーブル・インデックスが肥大化する
- 代替を先に検討: 監査目的なら**履歴テーブル/監査ログ**、復元目的なら**アーカイブテーブルへの移動**の方が本体スキーマを汚さない

## P5. NOT NULL デフォルトと CHECK の活用

- **列は NOT NULL をデフォルトにし、NULL許容は「不明/未設定が正当な状態」と説明できるときだけ**にする（クエリ側の NULL 対策より前の、設計側の予防）
- 値同士の関係は CHECK 制約で宣言する: `CHECK (start_date <= end_date)`、`CHECK (price >= 0)`（値リストの列挙には使わない）
- PostgreSQL の排他制約（`EXCLUDE USING gist`）は期間の重複禁止（予約システム等)をDB層で強制できる

## P6. 文字コードと照合順序

- MySQL の `utf8` は**3バイトまでしか格納できない別物**（絵文字・一部漢字が入らない）。必ず `utf8mb4` を使う
- 照合順序（COLLATE）はDB全体で統一する。テーブル間で不一致だと JOIN でインデックスが効かなくなり、FK定義もエラーになる（ANTIPATTERNS.md の 26-27 参照）
- 大文字小文字・アクセントの区別（`_ci` / `_cs` / `_bin`）は要件として明示的に決める（例: メールアドレスの一意性判定）

## P7. 楽観ロック

- 同一行を複数ユーザーが編集しうる画面には `version INT`（またはタイムスタンプ）列を置き、`UPDATE ... WHERE id = ? AND version = ?` で更新。**影響行数0なら競合**としてユーザーに再確認させる。悲観ロック（`SELECT ... FOR UPDATE`）より接続を長時間占有しない
- 集中カウンタ（いいね数等）は1行への更新集中がロック競合のホットスポットになる。カウンタ行の分散や、イベント行のINSERT + 定期集計を検討する

## P8. 命名規約

- 1プロジェクト1規則で一貫させる（snake_case、テーブル名の単数/複数はどちらでもよいが混在させない）
- boolean は `is_` / `has_`、タイムスタンプは `_at`、日付は `_on` サフィックス
- 主キーは `bug_id` のようにエンティティ名を含め、外部キー側も同じ名前を踏襲する。関連の意味を示したい場合のみ `reported_by` のような役割名にする
- 予約語（`order`, `by`, `table`...）を識別子にしない
