# 設計アンチパターン詳細

各節の構成: 症状（アンチパターンの形）／見つけ方（会話・スキーマ上の兆候）／例外（用いてもよい場合）／解決策。

## 2. ジェイウォーク（信号無視） / Jaywalking

**症状**: 外部キー列を VARCHAR にし、複数IDをカンマ区切りで格納（`'12,34,56'`）。検索は `REGEXP '\\b12\\b'`、JOINも集約も正規表現頼みでインデックス不使用。更新は取得→アプリ加工→再保存。FK検証不能で `'12,banana'` も入る。

**見つけ方**: 「リストの最大エントリ数は？」「SQLで単語境界をマッチするには？」「リスト要素に絶対使わない区切り文字は？」

**例外**: 個別要素へのアクセスが不要でリストを丸ごと出し入れするだけの場合。測定に基づく意図的な非正規化。DBの配列型（PostgreSQL等）で軽減できる場合。

**解決策**: 交差テーブル。関連自体への属性追加（追加日等）も可能になる。

```sql
CREATE TABLE Contacts (
  product_id BIGINT UNSIGNED NOT NULL,
  account_id BIGINT UNSIGNED NOT NULL,
  PRIMARY KEY (product_id, account_id),
  FOREIGN KEY (product_id) REFERENCES Products(product_id),
  FOREIGN KEY (account_id) REFERENCES Accounts(account_id)
);
```

ミニAP: 既存CSV列を行に分割して表示したい場合は `unnest`（PostgreSQL）/ `STRING_SPLIT`（SQL Server）/ 連番テーブルJOIN / 再帰CTE。いずれも回避策であり根本解決は設計変更。

## 3. ナイーブツリー（素朴な木） / Naive Trees

**症状**: 階層構造を `parent_id`（自己参照FK）だけで表現。JOIN数=取得可能な深さになり、深さ無制限のサブツリー取得・集約ができない。サブツリー削除は多段クエリ。

**見つけ方**: 「深さは何階層までサポートすればいい？」「ツリーの孤立行を掃除するスクリプトを定期実行している」

**例外**: 再帰クエリ対応DBなら隣接リスト+再帰CTEで十分（アンチパターンでなくなる）。深さが要件上限定的なら隣接リストのみで可。高度なツリーモデルの過剰投資に注意。

**解決策**: 4モデルから要件で選ぶ。

| 設計 | 子孫クエリ | 挿入・移動 | 参照整合性 | 向き先 |
|---|---|---|---|---|
| 隣接リスト+再帰CTE | 簡単 | 簡単 | ○ | 第一候補（MySQL 8.0+, PostgreSQL 8.4+ 等） |
| 経路列挙（path列 `1/4/7/`） | 簡単(LIKE) | 簡単 | × | パンくず表示。整合性はアプリ任せで脆い |
| 入れ子集合（nsleft/nsright） | 簡単 | 難しい | × | 検索≫更新のツリー |
| 閉包テーブル（全先祖×子孫の組を別テーブル） | 簡単 | 簡単 | ○ | 最汎用。ノードの複数ツリー所属可。行数コスト |

ミニAP: 開発環境と本番のDBバージョン差（再帰CTE対応等）で「自分の環境では動く」事故。クエリ挙動に関わる設定・バージョンを本番に揃える。

## 4. IDリクワイアド（とりあえずID） / ID Required

**症状**: 全テーブルに機械的に `id SERIAL PRIMARY KEY`。自然キー候補（`bug_id VARCHAR UNIQUE`）があっても重ねて付ける。交差テーブルで `id` を主キーにして `(bug_id, product_id)` の一意性が消え、関連の重複行が入る。`Bugs.id` と `Accounts.id` の列名衝突。

**見つけ方**: 主キー列名が一律 `id`。「なぜ多対多の関連が重複した？」「このテーブルに主キーは不要では」（主キーと疑似キーの混同）。

**例外**: ORMの規約（設定より規約）に乗る場合。自然キーが長すぎる/変わりうる/存在しない場合。親子連鎖で複合主キーが際限なく伸びる場合。

**解決策**: 主キーは制約でありデータ型ではない。列名はエンティティを表す名前（`bug_id`）にし外部キー側も踏襲。交差テーブルは複合主キー（DDL例は2章の Contacts）。ORM規約は上書き可能（Rails: `self.primary_key = 'bug_id'`）。

ミニAP: 自動採番の枯渇不安 — 32ビットINTは高頻度INSERTで枯渇しうるが、BIGINTは事実上枯渇しない。`MAX(id)+1` での採番はレース条件があり、シーケンス機構を使う。

## 5. キーレスエントリ（外部キー嫌い） / Keyless Entry

**症状**: FK制約を宣言せず整合性維持をアプリコードに委ねる。挿入前・削除前の存在確認SELECTが必要になり、確認と実行の間に割り込まれるレース条件は明示ロックでしか防げない。孤立行検出クエリの定期実行が必要になり、発見しても修正できないことがある。

**見つけ方**: 「別テーブルに存在しない値を調べるクエリは？」「外部キーは遅いから使うなと教わった」。EAV・ポリモーフィック関連の採用（FKを張れない設計）も同症状。

**例外**: FK非対応エンジン（MyISAM等）・水平パーティショニング使用時。オンラインスキーマ変更ツールの制約。既知の孤立行がある大掃除中。いずれも代替の整合性チェックが必要。

**解決策**: FK宣言 + カスケードで「事後検出」を「登録時点で防止」に変える（ポカヨケ）。

```sql
FOREIGN KEY (reported_by) REFERENCES Accounts(account_id)
  ON UPDATE CASCADE ON DELETE RESTRICT,
FOREIGN KEY (status) REFERENCES BugStatus(status)
  ON UPDATE CASCADE ON DELETE SET DEFAULT
```

使い分け: 親削除を禁止したい参照は `RESTRICT`、マスタ参照は `SET DEFAULT`、親の値変更を波及させるなら `ON UPDATE CASCADE`。FKのコストは代替（確認SELECT+ロック+定期チェック）よりはるかに小さい。

## 6. EAV（エンティティ・アトリビュート・バリュー） / Entity-Attribute-Value

**症状**: `(entity, attr_name, attr_value)` の3列汎用テーブルに属性を「行」として格納。NOT NULL相当の強制不可、attr_value は文字列なので型検証不可、特定属性だけへのFK不可、属性名の表記揺れ（`date_reported` vs `report_date`）、1エンティティの再構築に属性数分のJOIN。

**見つけ方**: 「メタデータの変更なしで実行時に新しい属性を定義できる」「クエリはJOINをいくつまでサポートしてる？」「レポートの書き方がわからずコンサルタントが要る」

**例外**: スキーマレスが本当に必要な箇所がごく少数に限定できる場合の消去法。レガシー・サードパーティ製品の既定。本質的に非リレーショナルなら専用DB（DynamoDB, MongoDB等）を検討。

**解決策**: サブタイプのモデリング。検索パターンで選ぶ。

| 方式 | 向いている場面 | 弱点 |
|---|---|---|
| シングルテーブル継承（1テーブル+type列） | サブタイプ・固有属性が少ない | NULL散在、列数上限 |
| 具象テーブル継承（型ごとに独立テーブル） | 横断クエリがほぼ不要 | 共通属性変更が全テーブルに波及 |
| クラステーブル継承（基底+型別子テーブル） | 共通列への横断クエリが頻繁 | 1エンティティの複数子テーブル紐付けを防げない |
| 半構造化データ（JSON列） | サブタイプ多数・実行時に属性定義 | 個別属性へのSQLアクセスが厄介 |

やむを得ずEAVを使う場合、単一行への再構築クエリは書かず、行の集合のまま取得してアプリ側で組み立てる。

## 7. ポリモーフィック関連 / Polymorphic Associations

**症状**: 子テーブルに `issue_id` + 参照先テーブル名を持つ `issue_type` 列（二重目的FK）。FKは単一テーブルしか参照できないため制約を宣言できず、クエリは親候補すべてへの LEFT OUTER JOIN + 出し分け。

**見つけ方**: 「あらゆるリソースと関連付けられる」タギング/コメントスキーマ。「この設計では外部キーは宣言できません」。`entity_type` 列の存在。Rails `polymorphic: true` / Hibernate エンティティ継承の使用。

**例外**: 成熟したORMがロジックをカプセル化してくれる場合のみ。手書き実装は労力の無駄。

**解決策**: 関連を単純化する2案。

1. **参照を逆向きに**: 親ごとに交差テーブル（`BugsComments`, `FeaturesComments`）を作り両側にFK。`comment_id` に UNIQUE で重複紐付けを抑制
2. **共通の基底テーブル**: 親たちが継承する `Issues` を作り、子は `Issues` だけを参照（クラステーブル継承と同型）。`issue_type` 列が消えFK1本で整合性を完全保証

使い分け: 既存親テーブルを変えられないなら1、設計変更できるなら2（整合性が最も強い）。

## 8. マルチカラムアトリビュート（複数列属性） / Multi-Column Attributes

**症状**: `tag1, tag2, tag3` のように同じ意味の列を複製。検索は `OR` の羅列、追加は空き列探索（レース条件あり）、同値の重複を防げない、上限到達で ALTER TABLE + 全SQL修正。

**見つけ方**: 「サポートすべきタグの最大数は？」「複数の列を同時に検索するには？」

**例外**: 列の役割が論理的に異なる場合（`reported_by` / `assigned_to` / `verified_by`）は複数列が正しい。列名は役割を表す名前にする。

**解決策**: 従属テーブル（1値1行）。原則「同じ意味を持つ値は1つの列に格納する」。

```sql
CREATE TABLE Tags (
  bug_id BIGINT UNSIGNED NOT NULL,
  tag VARCHAR(20),
  PRIMARY KEY (bug_id, tag),  -- 重複タグをDBが拒否
  FOREIGN KEY (bug_id) REFERENCES Bugs(bug_id)
);
```

ミニAP: 「価格の保存」— `Orders.price` は `Merchandise.price` の重複ではなく「購入時に支払った金額」という別ファクト。交差テーブルでは関連発生時点の属性値を保存してよい（正規化違反ではない）。

## 9. メタデータトリブル（メタデータ大増殖） / Metadata Tribbles

**症状**: 値でテーブルを分割（`Bugs_2020`, `Bugs_2021`...）または列を増殖（`revenue2002`, `revenue2003`...）。新年のテーブル作成忘れでINSERT失敗、年またぎUPDATEが移動処理に化ける、横断クエリはUNION ALL、テーブル横断の一意性・FKが定義不能。

**見つけ方**: 「〜ごとにテーブル（列）を作る必要があるんだね」「テーブル数の上限は？」「新しい年のテーブルを作り忘れた」

**例外**: アクセス頻度が大きく違う過去データのアーカイブ分割。閾値を超えた規模でのシャーディング（運用上の利点が上回る）。

**解決策**: 手作業分割をやめDB機能に任せる。

- 行数過多 → **水平パーティショニング**（`PARTITION BY HASH(YEAR(date_reported))` 等。SQL上は1テーブルのまま）
- 大きい列が原因 → **垂直パーティショニング**（BLOB等を従属テーブルへ分離）
- 列の増殖 → 従属テーブル化（`ProjectHistory(project_id, year, bugs_fixed)` で行に）

## 10. ラウンディングエラー（丸め誤差） / Rounding Errors

**症状**: 金額等に FLOAT/DOUBLE PRECISION/REAL（IEEE 754 二進浮動小数点）。59.95 が 59.950000762939... で格納され、等価比較が失敗、SUMで誤差蓄積、複利計算で指数的拡大。

**見つけ方**: 金額・会計用途の FLOAT 列。`WHERE float_col = リテラル`。`ABS(x - y) < 閾値` の「実質等しい」判定。集計が手計算とズレる報告。

**例外**: 広い実数範囲が必要で近似精度で足りる科学技術計算。完全一致検索をしない集計・範囲検索中心の用途。

**解決策**: `NUMERIC(精度, スケール)` / `DECIMAL`（同義）。リテラルとの等価比較が成立し誤差が出ない。金額・要正確合計 → NUMERIC、科学計算 → FLOAT系、と用途で使い分ける。

## 11. サーティワンフレーバー（31のフレーバー） / 31 Flavors

**症状**: 有効値リストを ENUM / CHECK 制約 / DOMAIN に埋め込む。値一覧の取得に INFORMATION_SCHEMA のパースが要りアプリ側にもハードコードされて二重管理化。値の追加・廃止は列の再定義（製品によってはETL）。廃止値の過去データ移行を ALTER TABLE は解決できない。

**見つけ方**: 「選択肢を1つ追加するにはDBをオフラインにする必要がある」「このリストが変わることはまずない（→変わる）」。流動的な値セットへの `CHECK (col IN (...))` / `ENUM`。

**例外**: 値セットが本当に不変な場合（左/右、オン/オフ等の2値）。値同士の関係検証（`開始 < 終了`）にCHECKを使うのは正当。

**解決策**: 値セットを**データ**として参照テーブルに置き、FKで強制。

```sql
CREATE TABLE BugStatus (status VARCHAR(20) PRIMARY KEY);
-- Bugs側: FOREIGN KEY (status) REFERENCES BugStatus(status) ON UPDATE CASCADE
```

値一覧は普通のSELECT、追加はINSERT、廃止は `active` 列で論理無効化（UIは ACTIVE のみ表示）。

ミニAP: 予約語（`order`, `by`, `table`...）を識別子に使うと構文エラー。区切り文字（標準 `"order"` / MySQL バッククオート / SQL Server `[order]`）で回避できるが、避けるのが無難。バージョンアップで予約語が増えることに注意。

## 12. ファントムファイル（幻のファイル） / Phantom Files

**症状**: 「画像は外部ファイルに置くべき」という思い込みで、DBにはパス文字列のみ格納。行DELETEでファイルが残る（ゴミ蓄積）、変更がCOMMIT前に他クライアントへ見える、ROLLBACKでファイルが戻らない、DBバックアップにファイルが含まれず同期も保証されない、SQL権限が効かない、パスの妥当性を検証できない。

**見つけ方**: 次の問いに即答できるか — 画像込みのバックアップ/復元手順は？孤立ファイルの削除は？画像のアクセス権限管理は？変更の取り消しは？曖昧ならこのアンチパターン。

**例外**: DB容量・バックアップ時間の削減、外部ツールでの画像編集など利点が上回り、上記の問題が実害にならないと**案件ごとに判断**した場合は外部格納も正当。Oracle BFILE / SQL Server FILESTREAM のような透過型があれば併用可。

**解決策**: 必要に応じて BLOB 列に格納。行と画像のライフサイクル（削除・トランザクション・バックアップ・権限）が自動的に一致する。サイズ上限は製品依存（MySQL LONGBLOB 4GB等）だが通常の画像には十分。

## 13. インデックスショットガン（闇雲インデックス） / Index Shotgun

**症状**: 3形態 — (1) 更新オーバーヘッドを恐れて全く張らない。(2) 張りすぎ・無駄張り（主キーへの重複インデックス、長いVARCHAR、検索されない列、複合インデックスの列順ミス）。(3) インデックスが効かないクエリ（複合 `(last, first)` に対する `first` のみ検索、`MONTH(col) = 4` の関数適用、`OR` 条件、`LIKE '%word%'`）。低選択性の列（値の種類が少ない）はインデックスよりフルスキャンが安い。

**見つけ方**: 「（文脈なしで）このクエリを速くするには？」「全列にインデックスを張ったのに速くならない」「インデックスは遅くなるらしいから使わない」

**例外**: クエリパターンが未確定の初期段階に完璧な設計は不可能。それでも情報に基づく推測はすべき（「張らない」の免罪符にしない）。DBがボトルネックとは限らない — 先にアプリをプロファイリング。

**解決策**: **MENTOR** の原則。

| 手順 | 内容 |
|---|---|
| Measure | スロークエリログでボトルネックを特定（実行時間×頻度） |
| Explain | EXPLAIN で実行計画を確認、フルスキャン箇所を発見 |
| Nominate | インデックス未使用箇所から候補を選定 |
| Test | 作成後に再計測し効果を定量確認 |
| Optimize | キャッシュメモリ調整でインデックスをメモリに乗せる |
| Rebuild | 更新蓄積で不均衡化するため定期メンテ（頻度は個別判断） |

カバーリングインデックス（クエリ参照列を全部含める）が使える場面では大幅高速化。全列・全順列に張るのは論外（複合の順列は列数の階乗）。今使うクエリを支えるものだけ張り、必要になったら分析して足す。

## 26-27. 外部キー定義の誤用チェックリスト

26章（標準SQL）と27章（MySQL固有）の誤用パターン。FK定義時・レビュー時に照合する。

**標準SQL共通**:

| 誤用 | 結果 |
|---|---|
| 参照方向が逆（親側にFK定義） | エラーは出ないが親1行が子1つしか持てない関係になる |
| 未作成のテーブルを参照 | エラー。親を先に作る。相互参照は後から ALTER TABLE で |
| 親の非キー列を参照 | エラー。参照先は PRIMARY KEY / UNIQUE 必須 |
| 複合キーを列ごとに別FKで書く | エラー。1つの FOREIGN KEY 句に列順を揃えて書く |
| 複合FKの列順が親と不一致 | エラーにならず INSERT 時に失敗する |
| 親子で型・符号・COLLATE不一致 | エラー（VARCHARの長さ違いのみ許容） |
| 孤立データが残ったままFK追加 | エラー。先に孤立行を解消（`LEFT OUTER JOIN ... IS NULL` で検出） |
| NOT NULL列に `SET NULL` | エラー。SET NULL を使う列は NULL 許容に |
| 制約名の重複 | エラー。命名規則を決めるか自動生成に任せる |

**MySQL固有（要注意: 黙って無視されるものがある）**:

| 誤用 | 結果 |
|---|---|
| FK非対応エンジン（MyISAM等）と混在 | 親が非対応→エラー。**子が非対応→エラーなしでFKが無視される** |
| 列定義内のインライン `REFERENCES` | **エラーなしで無視される**。テーブルレベル制約構文で書く |
| `REFERENCES Parent`（列名省略） | エラー。列名は必ず明示 |
| TEXT/BLOB/JSON へのFK | エラー。必要ならハッシュのSTORED生成列+UNIQUEを参照（可能なら疑似キー推奨） |
| TEMPORARY / PARTITIONED テーブル | エラー |

FKが本当に作られたかは `SHOW CREATE TABLE` で確認する。

## A. 正規化のルール

前提（リレーションの要件）: 行に順序なし・列に順序なし・重複行なし（主キー必須）・各列は単一型で1行1値・隠されたコンポーネント（ROWID等）なし。

| 正規形 | 禁じること | 違反の兆候 | 直し方 |
|---|---|---|---|
| 1NF | 繰り返しグループ | カンマ区切り複数値（→2章）、同一ドメインの複数列（→8章） | 1値1行の別テーブル |
| 2NF | 複合主キーの一部への従属（部分関数従属） | 同じ属性値がキーの一部単位で重複し不整合の余地 | 従属先だけのテーブルへ分離 |
| 3NF | 非キー列経由の従属（推移的関数従属） | `assigned_to` と `assigned_email` の同居 | 従属列を本来のテーブルへ移動 |
| BCNF | 候補キーが複数あるときのキー属性への従属 | 候補キー間で属性が従属し不整合 | 従属属性を別テーブルへ |
| 4NF | 独立した複数の多対多関連の混在（多値従属性） | 主キーが定まらずNULL許容・冗長値 | 関連の種類ごとに交差テーブルを分離 |
| 5NF | 独立した事実の1テーブル混在 | 「担当中」と「担当可能」が1行に混ざり冗長化 | リレーションシップごとにテーブル分離 |

実務指針:

- 正規化の目的は整合性であってパフォーマンスではない。ただし「正規化は遅い」は誤り — 非正規化は特定クエリを速くする代わりに他を犠牲にするトレードオフで、まず正規化してから測定して判断（13章 MENTOR を適用）
- 「3NFで十分」も誤り — ビジネスDBの2割超が4NF違反という調査があり、データ喪失バグの原因になる
- 6NF・DKNF は通常のアプリには過剰（テンポラルDB等の専門用途向け）
