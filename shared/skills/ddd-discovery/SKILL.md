# ドメインを発見すること

## ユーザー入力

```text
$ARGUMENTS
```

## このスキルの目的

ドメイン駆動設計は二層に分かれる。**戦略的設計（What / Why: どんなソフトウェアを、なぜ作るか）** と
**戦術的設計（How: どう実装するか）** である。このスキルは前者だけを扱う。

ゴールは、次の4つを言語化すること。

1. **事業領域と業務領域** — この事業は何で稼いでいて、どの部分が競争優位の源泉か
2. **同じ言葉** — 業務エキスパートと開発者が共有できる、一語一義の語彙
3. **区切られた文脈** — その言葉が一貫していられる範囲＝モデルの境界
4. **連係方法** — 文脈どうしがどういう契約でつながるか

実装方式（トランザクションスクリプト／ドメインモデル／イベントソーシング等）は決めない。
それは `/ddd-modeling` の仕事である。ただし**両者は環になっている** — 実装方式を選ぶと
業務領域のカテゴリーを逆算検証でき、その結果このスキルの結論が覆ることがある（後述「次のステップ」）。

## 訳語について

本スキルは書籍『ドメイン駆動設計をはじめよう』(Vlad Khononov) の訳語を主に使う。
従来訳に慣れている場合は次の対応で読み替える。

| 本スキルの用語 | 従来訳 | 原語 |
|---|---|---|
| 事業領域 | ビジネスドメイン | business domain |
| 業務領域 | サブドメイン | subdomain |
| 中核 / 一般 / 補完の業務領域 | コア / 汎用 / 支援サブドメイン | core / generic / supporting subdomain |
| 同じ言葉 | ユビキタス言語 | ubiquitous language |
| 区切られた文脈 | 境界づけられたコンテキスト | bounded context |
| 文脈の地図 | コンテキストマップ | context map |
| モデル変換装置 | 腐敗防止層 | anti-corruption layer |
| 共用サービス / 公開された言葉 | 公開ホストサービス / 公表された言語 | open-host service / published language |

## 進め方

状況によって入口が変わる。**新規に事業を分析する**のか、**既存システムを診断する**のかを最初に見極める。
既存システムなら、コードベースの構造が業務領域の分布を教えてくれる（後述 3-b）。

### 1. 事業活動を理解する

まず、対象の事業が何をしているかを掴む。ここを飛ばすと以降の判断がすべて宙に浮く。

- 事業活動を展開している領域はどこか
- 顧客は誰か
- 顧客に提供しているサービス、あるいは価値は何か
- 競合している企業や製品は何か

そのうえで部門構成（組織図）へズームインする。各部門が事業の存続と発展にどう寄与しているかを見る。
ただし**組織図は粗すぎる出発点**である点に注意する。「顧客サービス部門」を一括りにすると、
その内側に隠れている中核の業務領域を見落とす。

### 2. 業務領域を洗い出し、分類する

事業活動を、**強く関連するユースケースの集まり**（同じアクターが関与し、同じ外部システムとつながり、
密接に関係するデータを操作するユースケース群）に分解する。これが業務領域の単位として最も精度が高い。

各業務領域を **中核 / 一般 / 補完** に分類する。この分類が以降のすべての投資判断を駆動する。

| 分類 | 競争優位 | 複雑さ | 変化 | 実装手段 |
|---|---|---|---|---|
| **中核** | 生む | 複雑 | 多い | 社内開発必須。最も有能な技術者を割り当てる |
| **一般** | 生まない | 複雑 | 少ない | パッケージ購入 / OSS / クラウドサービス |
| **補完** | 生まない | 単純 | 少ない | 社内または外部委託。高速開発重視 |

分類の判定と、既存コードからカテゴリーを見つける手がかりは
**[references/subdomains.md](references/subdomains.md)** を読む。
「これ以上細分化すべきか」の停止判断もそこに書いてある（分割しても設計判断が変わらないなら止める）。

### 3. 同じ言葉を採取し、ほころびを見つける

**同じ言葉こそが DDD の中核**である。書籍の事例研究では、同じ言葉の有無がプロジェクトの成否を
最もよく予測した — 設計が拙くても言葉が確かなら成功し、言葉が二重化すると数年の傷を負った。
そしてソースコードは書き直せても、**関係者に染み付いた言葉を変えるのはコードの改善よりはるかに難しい**。
だからここに最も早く投資する。

やることは、業務で使われている用語を集め、次の3つのほころびを探すことである。

- **あいまいな用語** — 1つの言葉が複数の意味を持っている（「ポリシー」が統制ルールと保険契約の両方）
- **同義語** — 複数の言葉が同じものを指している。あるいは意図の違いが言葉に現れていない
- **技術用語の混入** — 業務エキスパートに通じない言い回しでロジックが語られている
  （DB の status カラムの値でしか業務を語れない、という状態がその典型）

整理した言葉は、**会話・要件定義・テスト・ドキュメント・図・ソースコードのすべてで一貫して使う**。
どれか一つでも欠けると、そこから言葉は元に戻る。だから成果物には必ず
**「コード上の識別子を今の名前から何に変えるか」**を含める。改名されて初めて言葉は実体を持つ。

そして**用語集だけでは足りない**ことを忘れない。用語集が扱えるのは名詞（モノ・プロセス・役割）だけで、
本当に重要なのは**振る舞い**（業務ルール、前提条件、制約）である。
用語を整理したら、それぞれの語に紐づくルールと前提条件も一緒に書き出す
（ユースケースや、業務エキスパートが読んで検証できる形式のテストと組み合わせる）。

#### 3-a. 会話・ドキュメントから採取する場合

業務エキスパートの説明をそのまま拾う。重要な業務知識は言語化されていないことが多いので、
**到達手段は質問すること**しかない。正常系だけでなく特殊ケースを聞く — 業務エキスパート自身が
特殊ケースを考慮できていないことは、特に中核の業務領域で普通に起きる。

#### 3-b. 既存コードベースから採取する場合

コードを読み、型名・テーブル名・API のパス・イベント名から語彙を抽出する。
そのうえで**接頭辞が必要になっている用語**を探す — `CRMLead` と `MarketingLead` のように
文脈を名前に埋め込まないと区別できない用語は、**そこに文脈の境界が隠れている**強いシグナルである。

同時に構造も調べる。
- サブシステムごとの**ライフサイクルの違い** — 他と切り離して修正・テスト・配置できる単位はどこか
- **ストアドプロシージャやサーバーレス関数に漏れ出した業務ロジック** — 別コードベースの業務ロジックも追跡対象
- **最も入り組んだ設計の場所** — 中核の業務領域である可能性が高い（強力だがありがたくない経験則）

詳細は **[references/language.md](references/language.md)**。既存組織への導入と抵抗への対処もそこにある。

**業務知識そのものが失われている**（ドキュメントがなく、誰も全体を理解していない）なら、
イベントストーミングに切り替える → ステップ 6。

### 4. 区切られた文脈の境界を引く

同じ言葉の一貫性が保てる**最も広い範囲**を特定する。それが文脈の候補である。

順序を守る。**モデルを作ってから大きさを決める**のであって、大きさを先に決めてはいけない。
そして**広い範囲から始める**。論理的境界（名前空間・モジュール・パッケージ）の引き直しは、
物理的に切り離した境界の変更よりはるかに安い。業務知識が浅いほど広く区切るのが安全で、
知識が増えて安定してから小さく切り出す。

分割する動機は限られている — 開発チームを増やす / 別ライフサイクルで開発したい / 特定機能だけスケールさせたい。
動機がないなら分けない。**同じデータを操作するユースケース群を複数の文脈に分散させない**。

判断材料と、マイクロサービスの粒度（サービスの「深さ」、分割しすぎの害）は
**[references/bounded-contexts.md](references/bounded-contexts.md)** を読む。

### 5. 連係方法を決め、文脈の地図を描く

文脈は独立して進化するが、独立してはいない。接合部には必ず**契約**があり、
「どちらの文脈の同じ言葉を使うか」が設計課題になる。連係方法は**チーム間の協力関係**で決まる。

| 連係方法 | 力関係 | 選ぶ条件 |
|---|---|---|
| 良きパートナー | 対等 | 共通目標があり頻繁に同期できる。地理的に近い |
| モデルの共有 | 共同所有 | 重複コスト > 調整コスト。中核に限る。範囲は最小限に |
| 従属する関係 | 上流が強い | 上流の契約が安定していて、下流のニーズを満たす |
| モデル変換装置 | 上流が強い | 下流が中核 / 上流モデルが使いにくい / 上流が頻繁に変わる |
| 共用サービス | 下流が強い | 供給側が内部変更から利用者を守りたい |
| 互いに独立 | なし | 一般的な業務領域、または統合コストが見合わない。**中核どうしには使わない** |

描き上げた地図は、設計だけでなく**組織の問題**も映す。ある上流に対して全下流がモデル変換装置を
作っているなら、それは技術ではなく関係性の問題を示している。

各方法の詳細、境界を越えるイベントの種類（イベント通知 / 状態転送 / 業務イベント）の使い分け、
分析系データ（データメッシュ）への展開は **[references/integration.md](references/integration.md)**。

### 6. 業務知識が足りないならイベントストーミングを回す

業務知識が失われている、モデルが混乱している、新しい業務要件を探索したい — こうした場合は
関係者を集めてイベントストーミングを実施する。ローテクだが、同じ言葉を作り上げる手段として最も効果が高い。

**成果物はボーナスにすぎない。本当の価値はモデリング活動そのもの**（知識共有、メンタルモデルの一致、
相反するモデルの発見）にある。

進行手順（10ステップ）、色の凡例、準備物、ファシリテーションのコツ、リモート実施の制約は
**[references/event-storming.md](references/event-storming.md)** にそのまま回せる粒度で書いてある。

対象の業務プロセスが**単純で明白**なら実施しない。流れ作業のような領域ではうまくいかない。

### 7. まとめる

得られた結論を整理して提示する。規模に応じて要素を取捨する。

```
## ドメイン分析

**事業領域**
- [顧客に提供している価値を一文で]

**業務領域**
| 業務領域 | 分類 | 根拠 | 実装方針 |
|---|---|---|---|
| ... | 中核/一般/補完 | ... | ... |

**同じ言葉（主要な用語）**
| 用語 | 意味 | 通用する文脈 | 紐づく業務ルール・前提条件 | コード上の識別子（現在 → 変更後） |
|---|---|---|---|---|

**発見したほころび**
- [あいまいな用語 / 同義語 / 技術用語の混入 と、それが示唆する境界]

**区切られた文脈**
- [文脈名]: [対象業務領域] / [担当チーム] / [なぜこの境界か]

**文脈の地図**
- [上流] → [下流] : [連係方法] （選んだ理由）

**未解決の問い**
- [業務エキスパートに確認が必要なこと]
```

## 次のステップ

- **各文脈をどう実装するか決める** → `/ddd-modeling`
  実装方式を選ぶと、そこから業務領域のカテゴリーを**逆算検証**できる。
  「中核のはずが1日で作れる」「補完のはずがドメインモデルが要る」といった不一致は、
  このスキルの結論を見直す合図になる。実際、その不一致から新たな収益源が見つかることがある。
- **コード構造の設計に落とす** → `/design-code`
  境界と責務、型、データフローの設計判断を導く。文脈の境界が決まっていれば入力として使える。

## 注意事項

- コードは書かない。境界・語彙・関係を決める段階である
- 「一つの業務領域に一つのモデル」という固定観念を持たない。業務領域は**発見**するもの（事業が決める）、
  区切られた文脈は**設計**するもの（技術者が決める）で、1:1 とは限らない
- 全社共通の単一モデルを作らない。「あらゆることに手を出すと、どれもちゃんとできない」
- 分類や境界に確信が持てない部分は「未解決の問い」に置く。推測で確定させない
- 業務領域の分類は、**開発しているソフトウェアシステムの粒度に対応づける**。
  事業として新規でも、必要なソフトウェア機能は補完的ということがある
- パターン名で説得しない。それぞれの方法が**どういう課題を解こうとしているか**の論理で説明する
- 全ての応答は日本語で行う
