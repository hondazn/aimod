# イベントストーミング

業務プロセスのモデルを迅速に作ることを目的に、関係者が集まってブレインストーミングスタイルで進める
ローテクな手法。業務知識を共有するための戦術的なツールである。

流れは、モデル化の対象範囲を決める → 付箋でドメインイベントを時系列に並べる → アクター・コマンド・
外部システムなどを少しずつ追加 → **業務プロセスの仕組みを説明できるところまで要素がそろったら終了**。

> ワークショップのゴールは、できるだけ短い時間でできるだけ多くのことを学ぶことである。
> キーパーソンの貴重な時間を無駄にしない。

**成果物はボーナスにすぎない。** 本当の価値はモデリング活動そのもの — 関係者の知識共有、
事業のメンタルモデルの一致、相反するモデルの発見、そして何より**ユビキタス言語を作り上げること**にある。

## 1. いつ使うか / 使ってはいけないか

**使う場面**

- ユビキタス言語の構築
- 業務プロセスのモデル化（DDD の構成要素にもとづくので、集約・Bounded Context を効果的に発見できる）
- 新しい業務要件の探求（要件で考慮されていない特殊ケースが明らかになる）
- **失われた業務知識の修復**（特にレガシーシステム）
- 既存の業務プロセスの改善方法を探る（開始から終了まで見渡すことで非効率と改善機会に気づく）
- 新しいチームメンバーへのガイダンス

**使ってはいけない場面**: 探求する業務プロセスが**単純・明白**な場合。
流れ作業のように、興味をひく業務ロジックや複雑さを伴わない領域ではうまくいかない。

## 2. 参加者

- エンジニア、業務エキスパート、プロダクトオーナー、テスター、UI/UX デザイナー、サポート担当者など、
  **対象業務領域の関係者なら誰でも**
- **10人以上は難しい**。全員が貢献できる規模に保つ
- リモートは **5人まで**を推奨

## 3. 準備物

| 物 | 要件 |
|---|---|
| モデリングスペース | 壁一面に貼った模造紙が最高。大きなホワイトボードでも可。とにかく大きく |
| 付箋 | さまざまな色を**大量に**。色は伝統的な慣習に従う |
| サインペン | **参加者全員分**。知識共有の制約にしない |
| お菓子 | 通常2〜4時間続くのでヘルシーなものを |
| 部屋 | 広々と。**中央に大きなテーブルを置かない**（移動と閲覧の妨げになる）。**椅子は撤去**（座って傍観させない。ただし厳格なルールではなく、立ち続けが難しい人のため数脚は残してよい） |

## 4. 色の凡例

| 色・形 | 要素 |
|---|---|
| オレンジ | ドメインイベント |
| 水色 | コマンド |
| 小さい黄色 | アクター |
| 大きい黄色 | 集約 |
| 紫 | ポリシー |
| 緑 | 読み取りモデル |
| ピンク | 外部システム |
| ピンク（45度傾けたダイヤモンド形） | 問題点（pain point） |
| 縦線上に配置 | 転換イベント |

ファシリテーターは冒頭でこの凡例を作り、**ワークショップ中ずっと全員から見える場所に掲示する**。

## 5. 10ステップ

### ステップ1: 発散的に探索する

- オレンジの付箋にドメインイベントを書いて貼る。**必ず過去形**（すでに起きた出来事）
- 順序も重複も気にしない。洗い出しに集中する
- **誰も新しいイベントを追加できなくなるまで**続ける

### ステップ2: 時系列に並べる

- **正常系のシナリオから**並べる
- 完了後に代替シナリオ（エラー、異なる意思決定）を追加する。分岐は先行イベントから2つのフローを出すか、矢印を描く
- このステップで不正確なイベントの修正・重複排除・不足イベントの追加も行う

### ステップ3: 問題点を洗い出す

- ボトルネック、自動化できていない作業、文書化されていないもの、業務知識が不足している箇所を特定する
- **ピンクの付箋を45度傾けてダイヤモンド形**でマークする
- 明示しておくことで、後で戻って対処しやすくなる
- **このステップ限定ではない**。全ステップを通じてファシリテーターは参加者の発言に気を配り、
  問題や懸念が上がったら問題点として書き出す

### ステップ4: 転換イベントを見つける

- 文脈やフェーズの変化を示す重要なドメインイベントを探す
- **垂直線を引き、その線上にイベントを配置**して前後の転換を表現する
- 例: 「ショッピングカートが初期化された」「注文処理が開始された」「注文が出荷された」
  「注文が配達された」「注文が返品された」
- **転換イベントは Bounded Context を発見する手がかり**になる

### ステップ5: コマンドを見つける

- コマンド＝イベント（フロー）を引き起こすもの、システムの操作。**指示する形式**で表現する
  （「キャンペーンを公開する」「処理を取り消す」「注文を送信する」）
- **水色の付箋**に書き、**そのコマンドが生成するイベントの前**に貼る
- 特定の役割を持つアクターが実行する場合は**小さな黄色の付箋**でアクターを追記する
  （顧客、管理者、編集者などのユーザー／ペルソナ）
- すべてのコマンドにアクターがいるわけではない。**明らかな場合に限って**追加する

### ステップ6: ポリシーを定義する

- アクターに紐づかないコマンドについて、それを実行する**自動化ポリシー**
  （あるイベントがコマンドの実行を引き起こすシナリオ）を探す
- **紫の付箋**で、イベントとコマンドを接続する形で表現する。離れている場合は矢印を描く
- **判定条件があれば付箋に明記する**
  （例:「苦情が受け付けられた」→「苦情をエスカレーションする」だが「VIP 顧客のみ」）

### ステップ7: 読み取りモデルを見つける

- 読み取りモデル＝アクターがコマンドを実行するか判断するために使う、対象領域の状態を表現するデータのビュー
  （画面、レポート、通知）
- **緑の付箋**に、判断に必要な情報源を簡潔に書く
- **コマンドの前に配置**する（アクターは読み取りモデルを確認した後にコマンドを実行するため）

### ステップ8: 外部システムを追加する

- 探求している業務領域の外側のシステム。コマンドを実行する（入力）／イベント通知を受ける（出力）
- **ピンクの付箋**
- **完了チェック: このステップ終了時点で、すべてのコマンドは「アクターが実行」「ポリシーが発動」
  「外部システムが呼び出す」のいずれかになっているはずである**

### ステップ9: 集約を見つける

- 関連する概念を集約として整理する。**集約はコマンドを受け取り、イベントを生成する**
- **大きな黄色の付箋**。**左にコマンド、右にイベント**を配置する

### ステップ10: Bounded Contextに分割する

- 機能的に密接に関係している、または自動化ポリシーを介して結合している集約のまとまりを探す
- そのまとまりが**Bounded Context の境界の自然な候補**になる

## 6. 進め方のレシピ

考案者は厳密なルールを定めていない（イベントストーミングは「指針」である）。推奨される進め方は2段構え。

1. **組織への初導入時**: ある範囲の業務活動全体を対象に、**ステップ1〜4 だけ**実施して全体像を把握する。
   ユビキタス言語の強力な基盤と、 Bounded Context のアウトラインが得られる
2. 全体像から業務プロセスを特定した後、**業務プロセスごとに別セッションを設け、今度は全10ステップ**を
   実施してモデルを完成させる

得られたモデルはイベントソーシングの実装土台に使える
（Bounded Context・集約・主要なドメインイベントがすでに明らかになっているため）。

## 7. ファシリテーションのコツ

- **冒頭で全体の流れ・対象業務プロセスの概要・モデリング要素を説明**し、そのまま凡例を作る
- **場の活力に注目する**。落ちてきたら、質問で再活性化できるのか、次のステップに進むタイミングなのかを見きわめる
- **全員に参加機会を**。遠ざかっている人がいたら、モデルの現状について質問して巻き込む
- **休憩は必須**（集中を要する活動である）。ただし**全員が戻るまで再開しない**。
  再開時は**モデルの現在の状態を確認するところから**始めて、全員を協調状態に戻す

## 8. リモート実施

考案者はリモート実施にたびたび異議を唱えている（同じ場所にいないと参加度合いと知識共有のレベルがばらつく）。

- ツールは Miro が最注目
- コミュニケーション効果の低下を前提に、忍耐強く進める
- **参加者は5人に制限する**。多人数が必要なら複数グループに分けて実施し、モデルを後から比較・統合する
- 状況が許すなら対面に戻すことを推奨

## 9. 実施チェックリスト

- [ ] 参加者は対象領域の関係者を横断しているか。対面10人／リモート5人以内か
- [ ] 模造紙・多色の付箋・全員分のペン・お菓子・広い部屋（テーブルなし、椅子は原則撤去）
- [ ] 冒頭で凡例を作り、全員から見える場所に掲示したか
- [ ] イベントはすべて過去形か
- [ ] 正常系を先に並べ、その後に代替シナリオを足したか
- [ ] 問題点を全ステップを通じて拾い続けたか
- [ ] ステップ8終了時、すべてのコマンドがアクター／ポリシー／外部システムのいずれかから発動されているか
- [ ] 初導入ならステップ1〜4で全体像に留めたか
- [ ] 休憩後は全員が戻ってから、モデルの現状確認で再開したか
