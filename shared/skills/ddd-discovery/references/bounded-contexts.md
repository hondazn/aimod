# 区切られた文脈（境界づけられたコンテキスト）

同じ言葉を複数の小さな言葉に分割し、それぞれが適用できる明確な文脈に割り当てたもの。
**同じ言葉の一貫性を保つための境界**であり、用語の意味・業務方針・業務ルールの一貫性が
維持できるのは文脈の内側だけである。

事業活動の規模が大きくなると暗黙の文脈が必ず生じる。それを明示化する方法が区切られた文脈である。

## 1. なぜ必要か

テレマーケティング会社の例。販売促進部門にとって「見込み客」は**ある人が製品に興味を持ったという通知**
（連絡先が手に入るという単発の出来事）。営業部門にとって「見込み客」は**営業プロセスのライフサイクル全体を
表す、時間をかけて取り組む複雑な対象**である。

- 営業の複雑なモデルを販売促進に持ち込む → **過剰な設計**
- 販売促進の単純なモデルを営業に持ち込む → **不十分な設計**

**却下される2つの解法**

| 解法 | なぜだめか |
|---|---|
| すべてを表現した単一の巨大モデル（壁一面の ER 図） | 「あらゆることに手を出すと、どれもちゃんとできない」。不要な詳細から必要な情報を見つけるのが困難で、最新に保てない |
| 名前に文脈を付ける（`MarketingLead` / `SalesLead`） | ①一語を使い分ける認知負荷が大きく、誤用が必ず紛れ込む ②会話では「販売促進の」とは言わない＝同じ言葉の考え方と一致しない |

つまり**接頭辞が必要になった時点で、そこは本来分けるべき文脈である**。

## 2. 業務領域との関係

| | 業務領域（サブドメイン） | 区切られた文脈 |
|---|---|---|
| 性質 | **発見**するもの | **設計**するもの |
| 誰が決めるか | 事業方針が決める。技術者は分析して識別する | ソフトウェア技術者が、目的と制約に合わせて決定する |
| 目的 | 事業戦略・差別化の理解 | 事業活動を扱いやすい単位に分割する設計判断 |

**対応関係は 1:1 とは限らない。** 小さなシステムなら単一文脈でよいし、不整合が見つかれば分割する。

**「一つの業務領域に一つのモデル」という固定観念を持たない。**
一つの業務領域に複数の課題があるなら、課題ごとに別のモデルを作るほうがよい。
1:1 に固定すると課題解決の柔軟性が失われる。

## 3. 文脈が定める2つの境界

> システム設計の本質は境界の決定である。

**物理的な境界**

区切られた文脈は独立したサービスまたはプロジェクトとして実装する。他文脈から切り離して開発・変更・
バージョン管理でき、文脈ごとに最適な要素技術を選べる。
1つの文脈が複数の業務領域を含む場合、物理的には単一境界だが**論理的には複数の境界が存在する**
（名前空間 / モジュール / パッケージ）。

**所有権の境界**

**1つの区切られた文脈の開発・変更・保守は1つのチームが担当する。複数チームが1つの文脈を担当してはいけない。**
関係は単方向で、**1チームが複数の文脈を所有するのは可**である。

チームを隔離することで、1つのソフトウェアに異なるモデルを無意識に作り込むのを防ぐ。
代わりに連係の約束事（契約）を明示する。

## 4. 大きさをどう決めるか

> サービスの境界を決める時に役に立つ経験則はたくさんある。「大きさ」はもっとも役に立たないものの一つである。

**手順を逆にする。**

1. **モデルを作ってから文脈の大きさを決める**。「大きさを決めてからモデルを作る」は禁じ手
2. **広い範囲から始める**。同じ言葉の一貫性が保てる最も広い範囲を特定する。
   論理的境界の引き直しは、物理的に切り離した境界の変更よりはるかに簡単
3. 業務知識が増えたら、必要に応じて小さな文脈に切り分ける
4. 中核の業務領域を含む場合は特に効く。**中核と頻繁にやりとりする他の業務領域（補完・一般でも）を
   同じ文脈に含めておく**と、初期に予測しにくい変更に対応しやすい

**経験則: 区切られた文脈の境界は業務知識の深さに合わせる。**
業務ロジックがよくわかっていない／変更が多いときは広く区切るほうが安全である。

**分割する動機**（無いなら分けない）

- 開発チームを増やす
- 非機能要件（別々のライフサイクルで開発したい）
- スケーラビリティ（スケールアウトが必要な機能だけ切り離す）

**分割しすぎの弊害**: 組み合わせて全体を組み立てるのがやっかいになる。本来分割すべきでない機能を切ると
独立した進化が難しくなり、**1つの変更要求のために複数の文脈を同時に修正・同時に配置する調整**が必要になる。

**経験則**: 同じデータに対して操作を行うユースケースの集まりを、複数の区切られた文脈に分散させない。

## 5. マイクロサービスの粒度

**マイクロサービス＝きわめて小さな公開インターフェースを持つサービス**である。
小さい行数でも、小さいコード量でもない。公開インターフェースは「玄関のドア」であり、
出入りするデータはすべてそこを通る。だからマイクロサービスはデータベースを公開しない
（SQL を外部にさらせば、組み合わせが無限なので公開インターフェースは巨大化する）。

**二層の複雑さ**

| 種別 | 何で決まるか |
|---|---|
| 局所的な複雑さ | 個々のサービスの実装 |
| 全体の複雑さ | サービスどうしの相互作用と依存関係 |

- 全体の複雑さだけを最小化 → 相互作用ゼロ＝モノリス＝**大きな泥だんご**
- 局所的な複雑さだけを最適化 → **分散した大きな泥だんご**
- **両方のバランスを取ることが全体最適**。片方だけの最適化は局所最適である

**深さ**: 公開インターフェースが簡潔で、内部にカプセル化する業務ロジックが多いモジュールが「深い」。
浅いモジュールはカプセル化する複雑さが小さく、システムに不要な複雑さを持ち込む。
**浅いサービスこそマイクロサービス失敗の原因**である。

**分割しすぎの実例**: 8メソッドのサービスを「1サービス1メソッド」で分割した結果、
サービス間でデータを同期するため各サービスに連係用の公開メソッドを大量に追加する羽目になった。
玄関ドアは小さくなったが「スタッフ専用の裏口」が大量にできた。
個別の戦いには勝ったが戦争には負けた — 各サービスは単純になったが、システム全体は桁違いに複雑になった。

**有効な範囲**

```
集約（最狭）  ←─── 設計として問題のない帯 ───→  区切られた文脈（最広）
   ↓ これより細かく分けると                        ↑ これより広げると
   分散した大きな泥だんご                          大きな泥だんご
```

- **すべてのマイクロサービスは区切られた文脈である。しかしすべての区切られた文脈がマイクロサービスではない**
- **デフォルトは業務領域に合わせること**。これが最もバランスがとれた安全な選択肢で、ほとんどのマイクロサービスにとって最適解である。理由は、業務領域が「どのように」ではなく「何を」を語る単位で、複雑な業務ロジックを実装詳細としてカプセル化する＝**自然に深いモジュールになる**から
- 集約をサービスにしてよいかの判断: 同じ業務領域内の他の集約とやりとりがあるか／値オブジェクトを共有しているか／業務ロジックの変更が他コンポーネントにどの程度影響するか。**関係が強いほど単独サービスとしては「浅く」なる**

**公開インターフェースを小さくする道具**

- **共用サービス** — 実装モデルと連係用モデルを分離。ロジック量は同じでも公開インターフェースが小さくなり、サービスが「深く」なる
- **モデル変換装置を独立サービスとして実装** — 利用側の業務の複雑さと変換の複雑さを分離し、局所と全体の両方の複雑さを軽減する

## 6. 境界を引き直すシグナル

- **変更の影響を特定の文脈にカプセル化できない** — 境界設計の失敗そのもの
- **1つの変更要求で複数の文脈を同時に直す必要がある**
- **文脈間の通信が過剰**（あらゆる操作で他文脈と通信する）— モデルが不適切。自律性を高める方向に区切り直す
- **「何にでも手を出して、どれもちゃんとできていない」モデル**になっている
- チームが増えた → 広く区切った文脈を分割し、チームごとに文脈を持たせる

境界のリファクタリングはとてもたいへんなので放置されがちで、**大きな技術的負債**になる。
境界が無効になる原因は、事業活動の理解不足と、事業要求の頻繁な変化（＝中核の業務領域の特徴）である。

**集約を単純化するリファクタリングで、隠れていた別のモデル＝新たな区切られた文脈を発見することは少なくない。**

## 7. アンチパターン

- 全社共通の単一モデル / 巨大 ER 図
- 用語に文脈の接頭辞を付けて、1コードベースに2モデルを同居させる
- 「同じ言葉＝組織全体の共通語」という誤解
- 分割しすぎ／本来分割すべきでない機能の分割
- 1つの区切られた文脈を複数チームで担当する
- 業務領域と区切られた文脈を 1:1 に固定する
- **一つの集約を二つの区切られた文脈に分ける** — 事例研究で「自殺行為となった境界」と呼ばれた失敗。
  最も複雑な集約が境界で分断され、2チームが別々の言葉でモデル化した結果、二重実装と本番データの
  長期汚染を招き、脱出に数年かかった。**絶対にやってはいけない**
- 業務知識が浅い段階で小さく区切る

## 8. 問いかけリスト

1. 同じ用語を、部門や関係者によって違う意味で使っていないか。その違いはモデルの複雑さの差として現れていないか
2. 一方のモデルを他方に持ち込むと、過剰な設計 or 不十分な設計にならないか
3. この同じ言葉が一貫性を保てる最も広い範囲はどこまでか
4. 分割する動機は何か（チーム増員 / 非機能要件 / スケーラビリティ）。無いなら分けない
5. 同じデータを操作するユースケース群を、複数の文脈にまたがらせていないか
6. 1つの変更要求で複数の文脈を同時に直す必要が出ていないか
7. この文脈のオーナーチームは1つに定まっているか
8. このモデルは何の課題のために作るのか。同じ業務領域に別の課題があるなら、別モデルを検討したか
9. その境界の公開インターフェースは、内部ロジック量に比べて小さいか（深いか）
10. 分割によって「連係専用の公開メソッド／イベント」を新設する必要が出ていないか（出ていたら分割しすぎ）
11. 局所的な複雑さと全体の複雑さの、両方を見ているか
