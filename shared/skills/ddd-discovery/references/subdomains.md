# 業務領域（サブドメイン）の分類

事業領域＝企業が事業活動を展開する領域。顧客に提供するサービス。
業務領域＝それを細分化したもの。すべてが連動して初めて事業活動になり、**個々の業務領域単体は利益を生まない**。

分類は投資判断そのものである。どこに最も有能な技術者を置き、どこを買い、どこを外部委託するかが決まる。

## 1. 3分類の定義と方針

| カテゴリー | 定義 | 競争優位 | 複雑さ | 変化 | 実装手段 | 課題の特性 |
|---|---|---|---|---|---|---|
| **中核**（core subdomain） | 競合他社との違いを生み出す業務活動 | 生む | 複雑 | 多い | **社内開発必須** | 複雑で興味深い |
| **一般**（generic subdomain） | どの会社も同じやり方をする領域 | 生まない | 複雑 | 少ない | パッケージ / OSS / クラウド | 既存の解決策がある |
| **補完**（supporting subdomain） | 事業を支えるが差別化を生まない | 生まない | 単純 | 少ない | 社内または外部委託 | 明確 |

**開発戦略**

- **中核**: 購入・外部委託は不可。短期的に危険で、長期的には会社の存続に関わる。競合も同じものを買えるなら優位性は生まれない。最も先進的な開発のやり方と、自社で最も有能な技術者を割り当てる。**中核のソフトウェア開発に「完了」はない** — 創発的活動として常に進化させる。
- **一般**: 自社開発より購入・採用のほうが費用対効果が高い。必要ならコンサルタントを雇う。
- **補完**: 適切な製品がないので作るしかないが、外部委託の有力候補。精緻な設計や高度な技法は不要で、高速開発重視のフレームワークを使う。**若手技術者の育成の場**として使える。

**戦略的な含意**: 補完的な業務領域は、可能なら一般的な業務領域へ移すのが望ましい。
パッケージやクラウドが使えるなら自社開発の負担が消える。

## 2. 分類の判定

2軸で位置づける — 横軸「競合他社との差別化」、縦軸「業務ロジックの複雑さ」。
差別化・大／複雑＝**中核**、差別化・小／複雑＝**一般**、差別化・小／単純＝**補完**。
差別化が小さく複雑さも小さい領域はグレーゾーンで、「一般または補完」のどちらかになる。

| 問い | Yes なら |
|---|---|
| その業務領域**単体でビジネスとして成立する**か。誰かが金を払うか | 中核 |
| 外部サービス導入より**自作のほうが簡単・安い**か | 補完（そうでなければ一般） |
| ソースコードは CRUD 画面の集まりか、それとも複雑なアルゴリズム・業務ルールと制約か | 前者＝補完 / 後者＝中核 |
| 実装が単純で、競争優位が短命になりそうか | 中核ではない（**中核は必然的に複雑になる**） |
| 競合が複製しても自社が痛まないか | 補完（複製されても競争優位は劣化しない） |

**注意すべき点**

- **中核は技術的とは限らない**。宝飾品メーカーの中核は「宝石のデザイン」であって、オンライン販売は一般的な業務領域。優秀な人材の採用能力や独創的なデザインを生む能力が競争優位ということもある。
- 不正申請を人力で検知する事業では、中核は「担当者の判断」であって、文書を表示して記録するだけの支援ソフトは中核ではない。
- **ソフトウェアが関与しない競争優位を中核のソフトウェアと混同しない**。関与しない業務機能を先に特定しておくと、対象システムの業務領域に集中できる。
- 分類の粒度は**開発しているソフトウェアシステムに対応づける**。事業として新規の収益源でも、必要なソフトウェア機能は補完的ということがある（競争優位がソフトの機能ではなく協業関係や交渉力にある場合）。

## 3. どこまで細分化するか

出発点は組織図（倉庫・顧客サービス・出荷・配送・品質管理・販売促進など）。ただしこれは**粗すぎる**。

**業務領域の正確な単位は「強く関連するユースケースの集まり」** — 同じアクターが関与し、
同じ外部システムとつながり、密接に関係するデータを操作するユースケース群。

**停止判断**

- 中核の業務領域では**厳密な特定が絶対に必要**。一般・補完を切り離して、中核に時間とエネルギーを集中させるため。
- 補完・一般は深掘りしない。**分割しても設計判断に影響する発見が無ければ、それ以上分割しない**。
  分割後のカテゴリーが全部同じになるなら分割は不要。
  例: ヘルプデスクを分割してもチケット管理・検索・知識ベース・通知はすべて一般 → ヘルプデスク単位でパッケージを使えばよい。

**粗い分類が中核を隠す例**: 「顧客サービスは外部委託が多いから補完」と一括りにすると見落とす。
細分化すると、ヘルプデスク＝一般、架電システム＝一般、シフト管理＝補完、
そして**新規案件の解析と過去案件との類似性判定を行う「担当者選びアルゴリズム」＝中核**が現れる。

## 4. 既存システムからカテゴリーを見つける

| カテゴリー | 探し方 |
|---|---|
| **中核** | 競合とどう差別化しているか。独自ノウハウ（自社開発アルゴリズム、特許などの知的財産）はあるか。**強力だがありがたくない経験則: 大きな泥だんご**。システムで最も入り組んだ設計の場所は中核である可能性が高い（全面書き換えは大きな事業リスク／パッケージに置換不能／修正・拡張に必ず事業リスクが伴う、という性質が中核と一致する） |
| **一般** | パッケージ製品・外部サービス・OSS を探す。競合も同じものを使えて、それが自社の不利益にならない領域 |
| **補完** | 置換できないが競争優位も直接生まない部分。**ソースコードが粗削りのまま**＝変更機会が少なく技術者の関心を集めなかった部分。中核と違い、まずい設計でも大問題にはならない |

**全部を洗い出す必要はない**。中規模企業でもおそらく不可能である。事業全体を俯瞰したうえで、
**現在取り組んでいるシステムに最も関係する業務領域に注目する**。

## 5. カテゴリーは移り変わる

特定するだけでは不十分で、**別カテゴリーに発展する可能性も含めて検討する**。

| 遷移 | きっかけ | 例 |
|---|---|---|
| 中核 → 一般 | 同等以上の外部サービスが安価に登場 | 自社の経路最適化 → 他社のサービスに置換 |
| 一般 → 中核 | パッケージでは事業要求を満たせず自社開発に戦略投資 | Amazon の IT 基盤 → AWS |
| 補完 → 一般 | 自社の単純 CRUD を上回る OSS / 製品が登場 | 契約管理を OSS へ乗り換え |
| 補完 → 中核 | 補完ロジックの最適化でコスト削減や新収益が生まれた | 販売報奨金の計算が事業の実験対象になった |
| 中核 → 補完 | その複雑さが事業収益に貢献しなくなった | 収益を生まない複雑さを取り除き最小限のロジックだけ残す |
| 一般 → 補完 | 汎用品に合わせる連係コストが見合わない | OSS を捨てて自社開発に戻す |

**補完 → 中核の兆候**: 補完領域の業務ロジックが複雑になってきたこと。定義上、補完のロジックは単純（CRUD や ETL）である。

- 複雑になっているのに利益に貢献しない → **不必要な業務の複雑さ**。取り除く
- 複雑になることで収益が増えている → **中核へ変化する兆候**。設計方針を見直す

**カテゴリーが変わったら見直すもの**

- **連係方法** — 中核になったならモデル変換装置で自身のモデルを守る、または共用サービスを提供する
- **互いに独立** — 選べるのは補完か一般だけ。中核に変わったら機能重複を放置できず、利用者と供給者の関係へ変える
- **開発体制** — 補完→中核なら開発を社内に戻す。中核→補完なら外部委託し、社内 R&D を中核に集中させる

## 6. アンチパターン

- 組織図の部門名だけで粗く分類し、細部に隠れた中核を見落とす
- 中核の業務領域を外部委託・パッケージ購入で済ませる
- 経験ある技術者を補完的な業務領域に浪費する
- 中核の開発を「完了」と考える
- 業務領域と区切られた文脈を 1:1 に固定する
- 実装のたいへんさを無視する。実装がたいへんなら、それは**事業モデルの発展や設計判断の進化につながる重要な兆候**である

## 7. 問いかけリスト

1. 我々の事業領域は何か。顧客に提供しているサービスを一文で言えるか
2. その業務領域は競合と何を差別化しているか。無くなると損益が変わるか
3. その業務領域だけで商売になるか。誰かが金を払うか
4. 自作と外部調達、どちらが簡単で安いか
5. そのコードは CRUD 画面の集まりか、複雑なアルゴリズム／業務ルールか
6. この業務領域は、同じアクター・同じ外部システム・密接に関係するデータを共有するユースケース群になっているか
7. これ以上分割して、設計判断が変わる発見はあるか。無ければ止める
8. ソフトウェアが関与しない競争優位（デザイン、人の判断、交渉力）を中核のソフトウェアと混同していないか
9. この中核を内製し、最も有能な技術者を割り当てているか
10. 業務エキスパートは誰か。その領域の信頼できる情報源に到達できているか
11. 補完のはずの領域で、業務ロジックが複雑化していないか。それは利益に貢献しているか
