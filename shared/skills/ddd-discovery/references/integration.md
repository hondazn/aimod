# 文脈どうしの連係

区切られた文脈は独立して進化できるが、独立してはいない。接合部分には必ず**契約**が存在する。
契約が必要な理由は、文脈が違えばモデルと言葉が違うからである。
連係する際は「**どちらの文脈の同じ言葉を使うか**」が設計課題になる。

連係方法は**チーム間の協力関係**によって3グループに分かれる — 緊密な協力 / 利用者と供給者 / 互いに独立。

## 1. 6つの連係パターン

| 連係パターン | 原語 | 力関係 | 選ぶ条件 |
|---|---|---|---|
| **良きパートナー** | Partnership | 対等・双方向 | 1チームが複数文脈を開発、または2チームに共通目標があり相手の成功が自分の成功になる。両チームが協力に習熟し、頻繁に同期する。技術的には頻繁な継続的インテグレーション。**物理的に離れたチームでは難しい** |
| **モデルの共有** | Shared Kernel | 事実上の共同所有 | コードの重複コスト > チーム間の調整コスト のときに限る。モデルが頻繁に変わるほど重複コストが大きくなるため、**採用するのは中核の業務領域**。共有範囲は「どちらの文脈にも実装が必須な部分」に限定し、理想的には契約と境界を越えるデータ構造だけ |
| **従属する関係** | Conformist | 上流が強い | 下流が上流のモデルをそのまま受け入れられる場合。上流の契約が業界標準で安定している、または上流の提供内容が下流のニーズを十分満たす |
| **モデル変換装置** | Anti-Corruption Layer | 上流が強い | 下流が上流モデルを受け入れられない場合。①下流が**中核の業務領域**を含む（供給側モデルに引きずられると中核のモデルが歪む）②上流のモデルが非効率・使いにくい（変更がやっかいで危険な既存システムとの連係で起きがち）③供給側の契約が頻繁に変更される |
| **共用サービス** | Open-Host Service | 下流が強い | 供給側が利用者を保護したい場合。公開インターフェースを内部モデルから切り離し、内部実装と公開モデルを別タイミングで変更できるようにする。公開する言葉を**公開された言葉**（Published Language）と呼ぶ。複数バージョンを並行提供して段階移行を助けられる |
| **互いに独立** | Separate Ways | なし | ①意思疎通の問題（組織が大きい、部門間で利害対立）②**一般的な業務領域**で一般的な解決手段を簡単に組み込める（ロギングフレームワーク等）③モデルの違いが大きく従属では対応できない、または重複実装のほうがモデル変換装置より安い。**中核どうしをつなぐ場合は避ける** |

**中核どうしに「互いに独立」を使ってはいけない理由**: 中核を重複実装するのは、
「中核は最も効率的・最適化された方法で実装する」という事業戦略そのものに背くからである。

## 2. 各パターンの補足

**共用サービスはモデル変換装置の逆転**である — 変換を利用側ではなく提供側で行う。
公開インターフェースは内部の同じ言葉に合わせる必要はなく、連係用途に特化した言葉を定義して
利用側が使いやすい契約を提供する。

**モデルの共有は「1文脈＝1チーム所有」原則と矛盾する例外**である。やむを得ず使う。
成立する状況は、地理的分散や利害対立で良きパートナーが成立しないとき、既存システムの段階的置き換え
（一時的な移行手段としてのコードベース共有）、あるいは1チームが複数文脈を所有していて境界を明確にしたいとき。

実現する場合は、単一リポジトリなら同じソースを使い、分かれているなら独立モジュールに切り出す。
いずれも**変更のたびに全利用文脈で結合テストを自動実行**し、変更は即時反映する
（遅れるとデータ不整合や実行時エラーになる）。

## 3. 文脈の地図

システム全体をどういう文脈に切り分け、どう連係させるかを描いた図。得られる洞察は3つある。

- **全体的な設計** — コンポーネントと実装モデルの全体像
- **意図の伝わり方** — 協力的なチームはどこか、モデル変換装置や互いに独立のように親密でないのはどこか
- **組織上の課題** — ある上流チームに対し全下流チームがモデル変換装置を作っている、
  あるチームが互いに独立に囲まれている、といった兆候の意味を問う

**運用**: プロジェクト開始時に作成し、文脈の追加・変更のたびに描き直す。全チーム共同で更新し、
各チームが自分の連係状態を反映する責任を持つ。Context Mapper 等でコードとして管理できる。

**限界**: 作成は大変である。1つの文脈が複数の業務領域を対象とすると、複数の連係方法を同時に使うことがある。
業務領域が1つでも、モジュール間で異なる連係方法が必要になることがある。

**既存システムを診断するときの悪臭**

- [ ] 同じコンポーネントに複数のチームが関わっている
- [ ] 中核の業務領域の実装が重複している
- [ ] 中核の業務領域の開発を外部に依頼している
- [ ] 統合が失敗しがちで摩擦が発生している
- [ ] 外部サービスや既存システムに影響された、ぎこちないモデルになっている

## 4. 組織の変化に追随する

| 変化 | 対応 |
|---|---|
| チームが増えた | 広く区切った文脈を分割し、チームごとに文脈を持たせる |
| 拠点分散などで意図の伝達が悪化した | 良きパートナー → 利用者と供給者（従属／モデル変換装置／共用サービス）へ |
| 地理的距離や組織の政治力学で連係がどうしても機能しない | 利用者と供給者 → 互いに独立へ。非友好的な調整に消耗するより、各チームが重複開発するほうが費用対効果が高いこともある |
| 業務領域が補完 → 中核に変わった | 互いに独立を続けられない。機能重複を放置できないので利用者と供給者の関係へ |

**既存システムで連係方法を選び直すときの指針**

| 方法 | 使いどころ |
|---|---|
| 利用者と供給者 | 良きパートナー前提で設計されたが、組織拡大でその協力関係が維持できなくなったコンポーネント |
| モデル変換装置 | 既存システムのモデルが下流に悪影響を及ぼしている／上流の公開インターフェースが頻繁に変更される |
| 共用サービス | 実装変更の影響がシステム全体に波及し多数の利用者に及ぶ場合。外部公開 API と内部モデルを分離する |
| 互いに独立 | 大組織で共通機能に複数チームが取り組み摩擦が起きるとき。その「争いの種」が中核でないなら、独立開発で衝突を避けるのも選択肢 |

## 5. 境界を越えるイベントの種類

イベント駆動型アーキテクチャでは、**イベントが第一級の設計要素**である。
どのカテゴリーを選ぶかで疎結合か密結合かが決まる。

**イベントソーシングとイベント駆動型アーキテクチャは別物**である。前者はサービス**内部**の実装方法
（集約の状態変化の捕捉）、後者はサービス**間**の通信方法であり、内部実装をそのまま外に出す仕組みではない。

| カテゴリー | 内容 | 目的・特徴 |
|---|---|---|
| **イベント通知** | 起きたことだけを伝える最小限。詳細は受信側が取りに行く | 連係の複雑さの緩和。**反応に必要な全情報を含めてはいけない** |
| **イベントによる状態転送**（ECST） | 状態変更を反映した全データ。完全スナップショット or 更新フィールドのみ | データの非同期複製。受信側がローカルキャッシュを保持できる |
| **業務イベント**（ドメインイベント） | 業務領域で起きた重要な出来事＋それを説明する全データ | 業務領域の活動をモデル化・説明すること自体が目的 |

**結婚の例**: 「婚姻届が提出された」＋詳細リンク＝通知／「個人情報が変更された（新しい姓）」＝ECST
（理由は不明。結婚か離婚かわからない）／「結婚した（相手 ID, 予定される姓）」＝業務イベント。

**選び分けの原則**

- **一貫性の要求で選ぶ** — 結果整合性で足りるなら ECST。
  受信側が発信側の最新の書き込みを読む必要があるなら、**イベント通知を発行し受信側が最新状態を問い合わせる**
- **イベント通知が好ましい状況** — セキュリティ（機密情報をメッセージ基盤に流さず、取得時に追加の権限チェックができる）／並行性（非同期なので届いた内容は古い可能性がある。明示的に問い合わせれば最新が取れる）
- **業務イベントは集約の状態を表現しない**。ライフサイクル途中の出来事を表すだけなので、
  購読していない別の業務イベントが同じフィールドを変えている可能性がある。
  **業務イベントだけでは集約の状態をローカルにキャッシュできない**
- **業務イベントをそのまま他文脈との通信に使うのは控えめに。公開する業務イベントを限定する。**
  特にイベント履歴式（イベントソーシング）の集約は、内部イベントをそのまま出すと実装の詳細が漏れる
- イベントは区切られた文脈の**公開インターフェースの不可欠な要素**である。
  共用サービスを実装するなら、イベントが公開された言葉を反映するようにする

**最悪のケースを想定する** — ネットワークは必ず遅延する／サーバーは最悪のタイミングで故障する／
イベントは順番通りに届かない／イベントは重複する。
対策は、送信箱（Outbox）で確実に送出し、購読側で重複排除と順序の並べ直しができることを保証し、
補償が必要な業務プロセスにはサーガ／プロセスマネージャーを使うこと（実装は `/ddd-modeling` を参照）。

## 6. 分散した大きな泥だんご

> イベントを秘伝のスパイスとして振りかけても疎結合にはならない。
> むしろモジュラーモノリスを分散した大きな泥だんごに変えかねない。

実例。顧客管理（イベント履歴式）／販売促進／広告最適化／レポート出力の4文脈。
販売促進と広告最適化が顧客管理の**すべての業務イベントを購読**してそれぞれ顧客状態を投影し、
レポート出力は広告最適化の計算完了を待つため5分遅延して起動していた。

| 生じた結合 | 内容 | 解消方法 |
|---|---|---|
| **時間的な結合** | 広告最適化の計算がレポート出力より先に完了していなければならない。5分遅延では順序を保証できない | 広告最適化が**イベント通知**を発行し、レポート出力が受信時に必要なデータを取りに行く |
| **機能的な結合** | 2文脈が同じ投影ロジックを重複実装。同じ理由で同時に変更が必要になる | **投影ロジックを発信側にカプセル化**し、コンシューマー駆動契約を採用する |
| **実装の結合** | 購読側が発信側のイベント履歴式モデルの全業務イベントに依存。イベント追加やデータ構造変更で購読側も変更必須 | **公開する業務イベントをごく一部に制限する**、または業務イベントとは異なる種類のイベントを公開する。受信側が必要とするモデルを発信側が投影し、公開された言葉に含めて **ECST** として提供する |

## 7. 分析系データの境界（データメッシュ）

データメッシュは、ある意味で**分析系データのドメイン駆動設計**である。
分析系データのモデルと所有権の境界を定義し、境界内部を外部から保護する。

**従来手法の何が問題か**

- **データウェアハウス**: 全社の業務系システムから ETL で抽出し単一の分析系モデルへ。
  **事業全体を単一モデルで表現しようとする点が「全社共通の単一モデル」と同じ失敗**である
- もう一つの根本問題: **ETL が業務系システムのデータベースを直接参照する**＝公開インターフェースではなく
  内部実装の詳細に依存している。テーブル設計の小さな変更で ETL が壊れる。
  結果として「分析側の ETL を壊さないため業務系システムを変更しない」事態が起き、
  **DDD ではモデルを継続的に進化させるためこの密結合はさらに深刻になる**
- **データレイク**: 生データを保管して変換は後回し。スキーマレスで品質保証がなく、
  規模が大きくなると「レイク」が「沼」になる

**4原則**

1. **データを業務の視点で分割する** — 単一の巨大な分析系モデルの代わりに複数の分析系モデルを
   データの発生源と整合させる。**分析系モデルの所有境界は区切られた文脈の境界と自然に一致する**
2. **データをプロダクトと考える** — 公開 API と同じ扱いをする。出力ポートが見つけやすい／
   内容と形式を明確に定義したスキーマ／高い信頼性と SLA の定義・監視／複数バージョン提供と破壊的変更の管理。
   実践には開発チーム内に**データ指向の専門家**が必要
3. **自律性を高める** — 相互運用可能なデータプロダクトの管理基盤を、専任チームが整備する
4. **エコシステムを構築する** — 各文脈のデータオーナーと基盤チーム代表で構成する**連合型の統治体制**が
   全社のルール作りと順守に責任を持つ

**DDD との対応**

- 本質は同じ — 境界を明確にし、実装の詳細をカプセル化し、適切な公開インターフェースを定義する
- **同じ言葉と業務知識の習得は分析系モデルの設計でも基本中の基本**。従来の分析系モデルではここが欠落していた
- 業務系とは別の分析系モデルとして外部に公開するやり方は、**まさに共用サービス**である。
  分析系モデルがもう一つの公開された言葉になる
- **CQRS** を採用すれば同じデータから複数モデルを容易に生成でき、複数バージョンを並行提供できる
- 文脈間のモデルを結びつける際は、**業務系で使った連係方法がそのまま適用できる**

## 8. 問いかけリスト

1. この2つの文脈のチームは、相手の成功が自分の成功になる関係か
2. 両チームは頻繁に同期でき、地理的に近いか
3. 重複実装のコストと、共有・調整のコストのどちらが大きいか
4. 共有するとして、範囲は「双方に必須な部分」だけに絞れているか
5. 上流の契約は業界標準で安定しているか。下流のニーズを十分満たすか（→ 従属）
6. 下流は中核の業務領域を含むか。上流モデルは使いにくいか、頻繁に変わるか（→ モデル変換装置）
7. 供給側として、内部モデルの変更を下流から隔離したいか（→ 共用サービス＋公開された言葉）
8. その一般的な業務領域を共通サービス化する意味は本当にあるか。各文脈で個別に組み込むほうが安くないか
9. 中核どうしを互いに独立でつなごうとしていないか
10. 文脈の地図で、モデル変換装置や互いに独立が集中している箇所はないか。それは組織の問題を示していないか
11. 内部の業務イベントをそのまま外部に公開していないか
12. 受信側は発信側の「最新の書き込み」を読む必要があるか（→ 通知＋問い合わせ）、結果整合で足りるか（→ ECST）
