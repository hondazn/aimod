# 汎用観点の蓄積（planner の探索・受け入れ条件設計に照らす）

レビュー往復や実測手戻りから昇華した、プロジェクト非依存の本質的な観点。
planner は計画を書く前にこのリストを一巡し、該当する観点を受け入れ条件・変更対象リストに反映する。

運用ルール:

- 追加するのは**汎用的・本質的な形に昇華した観点**のみ。個別事例の列挙はしない（事例は台帳・スキル本文の実例欄に残す）
- 1観点 = 見出し1行 + 数行の説明。似た観点が既にあれば統合する
- 出典セッションを末尾に1行で残す（昇華の妥当性を後から検証できるように）

---

## 副作用の失敗経路は悉皆で設計する

実行する全ての外部コマンド・副作用（プロセス起動、git 操作、ネットワーク、ファイル書込）について「失敗したら何が起きるか」を設計に含め、検証にも含める。成功経路だけの設計は、失敗の黙殺（exitCode 無視・例外の握り潰し）として実装に現れる。各失敗に fail-open / fail-closed のどちらを選ぶかは、守るべきもの（公開物の品質か、処理の継続か）から導き、理由を書く。

出典: 2026-08-03 kojo保守可能化（exitCode検査の同型指摘がR3〜R5で計5回）

## 検証は「誤実装が落ちること」を基準に書く

テストの価値は正しい実装が通ることではなく、**ありうる誤実装が落ちる**こと。境界（ゼロ回・順序・短絡）、全文一致（断片一致では別物が通る）、参照同一性、失敗注入をこの基準で選ぶ。「このテストを通したまま壊す実装が書けるか」を自問し、書けるなら判定力が足りない。

出典: 2026-08-03 kojo保守可能化（plan-reviewer指摘の大半がこの型）

## 外部システムの暗黙制約は最小実測で固定する

名前の長さ・文字種・レート・パスの解釈など、外部ツールの制約は文書化されていないことが多い。設計がそれに依存する場合は、机上の想定ではなく最小の実測（1コマンド・1リクエスト）で確認してから固定する。バージョン範囲指定（semver）も「同一である」ことの保証にはならない — 保証が要る箇所は完全固定する。

出典: 2026-08-03 kojo保守可能化（herdrエージェント名32文字制約・^1.62.1のキャッシュ保証破れ）

## 設計が参照する実データは現物を読む

計画が参照する既存データ（台帳・設定・履歴・命名）は、スキーマの想定ではなく現物を読む。長く運用されたデータには世代差（旧命名規則・欠損フィールド・手動修正の痕跡）があり、想定だけで書いた処理は最初の1件で壊れる。

出典: 2026-08-03 kojo保守可能化（台帳の旧命名 app-YYYYMMDD-* が実在しないリポジトリを対象化）

## 手順書は実行主体の視点で完結させる

エージェントや人に渡す手順（プロンプト・AGENTS.md・README）は、書き手が暗黙に補っている工程（push・認証・後片付け）を実行主体が知らない前提で書く。手順の最後が「作業が外から見える状態」（push 済み・デプロイ済み・報告済み）に到達しているかを確認する。

出典: 2026-08-03 kojo保守可能化（保守手順の git push 漏れ。デプロイは成功したがリポジトリが ahead 1）
