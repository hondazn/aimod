# round-slicer — seiren ループのマルチエージェント運転

## 概要

seiren の開発ループ（探索→モデル化→TDD→学習）を、herdr-multiagent-dev の役割分担（planner / builder / reviewer / fixer）に写像して回す合成スキル。自分（メインエージェント）は指揮者 + 学習判定者に専念し、実装とレビューは別ベンダーのエージェントに分担させる。核心は3つ:

1. **ラウンド分割**: 大きな依頼は planner がユースケース単位の「ラウンド」に切り、1ラウンド = seiren ループ一周として直列に回す
2. **分類付き合否**: reviewer の判定を二値（合格/不合格）から「不合格 + 分類」に拡張し、分類を seiren の戻り先（Refactor / モデル化 / 探索）へルーティングする
3. **有界ループ**: seiren のループは無限だが、無人運用では戻り回数とタイムボックスに上限を課す。「やめる判断」が品質担保

**REQUIRED BACKGROUND:** seiren（ループ意味論の正本）、herdr-multiagent-dev（役割設計・操縦・防御層・判定パースの正本）。開始前に `test "${HERDR_ENV:-}" = 1` を確認する。

## When to Use

- 複数ユースケースの開発を、実装とレビューを別エージェントに分担して半自動〜無人で進めたい
- seiren の規律（TDD・学習して戻る）を保ったままマルチエージェント化したい
- **使わない**: 自分1人で開発するなら seiren を直接使う。役割分担だけ欲しくループ規律が不要なら herdr-multiagent-dev を直接使う。単発の調査委譲は codex-investigate

## 全体フロー

```mermaid
flowchart TD
    S[ラウンド分割<br/>planner=自分: 依頼をユースケース単位に切る] --> A
    A[探索・モデル化<br/>planner: PLAN.md に受け入れ条件を書く] --> PR[plan-reviewer<br/>planner と別ベンダー]
    PR -->|不合格| A
    PR -->|合格| B[builder<br/>TDD 契約付き実装 + 自己検証]
    B --> R[reviewer<br/>fatal + 受け入れ条件のみ。不合格時は分類必須]
    R -->|合格| DONE[回収・台帳記録・/git-commit<br/>→ 次ラウンドへ]
    R -->|不合格:内部構造| FX[fixer: Refactor 相当の修正<br/>3回まで]
    R -->|不合格:API境界| A2[モデル化へ戻る<br/>planner が PLAN.md の設計を修正]
    R -->|不合格:要求前提| AB[打ち切り: 回収・台帳記録の上<br/>ユーザーへ報告]
    FX --> R
    A2 --> B
```

各エッジの実行（起動・送信・受理検証・settled 待ち・回収）は herdr-multiagent-dev のセッションライフサイクルに従う。

## 段階 → 役割の写像

| seiren の段階 | 役割 | 担当 | 備考 |
|---|---|---|---|
| ラウンド分割・探索・モデル化 | planner | 自分 | PLAN.md に受け入れ条件を明記。計画の質が全ラウンドの上限になる |
| （計画の検証） | plan-reviewer | planner と別ベンダー | 受け入れ条件の検証可能性・スコープ妥当性のみ |
| Red-Green-Refactor | builder | cursor 等 | プロンプト契約で TDD を義務付け（下記） |
| 学習の判定（一次） | reviewer | builder と別ベンダー | fatal + 受け入れ条件 + 不合格時の分類 |
| 学習の判定（最終）・ルーティング | 自分 | — | reviewer の分類を鵜呑みにせず、根拠を読んで戻り先を最終決定する |
| Refactor への戻り | fixer | builder と同系 | **3回まで**（本スキルは herdr-multiagent-dev の「1回だけ」を上書きする） |

**planner は常に自分が務め、`agents.yaml` の `planner` エントリは round-slicer では使わない**（自分がループの指揮・最終判定を握るのが本スキルの前提）。herdr-multiagent-dev の `agents.yaml` から使うのは plan-reviewer / builder / reviewer / fixer の4役の割当だけ。

### planner の探索規律

全役割が受け入れ条件の充足だけを見る構造上、**条件自体の盲点は誰も検出できない** — 盲点を減らせるのは planner の探索だけ。計画を書く前に、蓄積された汎用観点 references/principles.md を計画に照らし、さらに次を実測・確認する（各実例は kojo ドッグフーディングでの実際の手戻り）:

- **現物を読む**: 既存資産へ遡及変更する計画では、変更が触れる現物（対象ファイルの実装・スタイル・実行環境）を必ず読んでから設計を決める。受け入れ条件は「変更の存在」だけでなく、現物との相互作用を踏まえて書く
  （実例: 固定フッターを「`</body>` 直前に挿入」と決めた計画が、対象アプリの body がセンタリング flex/grid であることを見ておらず、全ラウンド合格後にレイアウト崩れが発覚）
- **検証コマンドを main で実測する**: 受け入れ条件に使う検証コマンド（型検査・テスト等）は、探索段階で現状の main に対して実行し、通ることを確認してから条件にする。通らないなら既存問題の扱い（スコープ追加 or 条件の限定）を計画に明記する
  （実例: 「tsc exit 0」を条件にしたが main 自体が既存型エラーで exit 1。builder のブロッカー報告 → 指揮者実測 → スコープ追加の一往復が発生）
- **既存テストへの波及を予見する**: 変更対象リストには、変更が壊す既存テスト（プロンプト変数の全置換検証・スタブの応答形式など）を予見して含める。本体だけのリストは builder のスコープ逸脱申告を誘発する
  （実例: テンプレ変数の追加で「未置換変数なし」検証が必ず壊れる／関数の発行コマンド列変更でスタブの追随が必要 — 2ラウンド連続で同型のリスト漏れ）
- **本番実行経路のスモークを条件に含める**: テストランナーと本番の実行経路が異なる場合（例: vitest と tsx では esbuild 変換の挙動が違う）、受け入れ条件に本番と同じ経路での実走スモークを1本含める
  （実例: vitest 全緑でも本番の tsx 実行では page.evaluate が esbuild の `__name` ヘルパー未定義で全滅。テスト実行のみの条件では構造的に検出不能だった）
- **新規に発する文字列を既存の分類器・パーサと突き合わせる**: 計画が新設する文字列（note・ログ・判定行など）を既存の分類器・パーサ（部分一致パターン・正規表現）が処理する場合、机上で一致を確認し、不一致なら分類器側の変更を変更対象リストに含める
  （実例: 新設 note「永続化検証不能(環境起因)」が classifyFailure の env パターン「視覚検証不能(環境起因)」に部分一致せず capability へ誤分類される構成だった。plan-reviewer が計画段階で検出し、パターンの汎化をスコープ追加）

### 意図と確度の明記

全役割が受け入れ条件の充足だけを見る構造への上流対策として、planner は PLAN.md に次を明記する:

- **意図の1段落**: 受け入れ条件の上に「意図」（誰が・どんな場面で・なぜ使うか）を置く。依頼に明示があれば転記して「（明示）」、なければ推定して「（推定）」と付記する。条件を満たしつつ意図から逸れる実装（ドリフト）を、reviewer と指揮者が検出可能になる
- **受け入れ条件の確度ラベル**: 各条件に「確定」（依頼・実測から導いた条件）か「推定」（planner の判断で置いた条件）を付記する。plan-reviewer への契約プロンプトには「『推定』の条件は検証可能性のみ審査し、表現の厳密化の深掘りはしない」と伝える。同種指摘の無限後退（上限4回到達の実例）への事前手当で、機械検証の適用除外宣言と同じ「事前に審査強度を宣言する」原則の適用

### フォールバックと独立性

`agents.yaml` の役割リストは**候補リスト**であり、割当時（初回・フォールバック発動時とも）に次の独立性制約でフィルタし、満たさない候補はスキップして次へ進む:

- **plan-reviewer**: planner（= 自分）と別ベンダーであること。**本スキルは複数の CLI（claude / cursor-agent / codex）から実行されうるため、「自分のベンダー」は固定せず実行時に自認して判定する**（例: 自分が Claude 系なら `claude-code` 候補を、Codex 系なら `codex` 候補をスキップ）
- **reviewer**: そのラウンドで builder が**実際に使った**エージェントと別ベンダーであること（設定上の主担当ではなく、フォールバック後の実割当と比較する）
- **fixer**: 実際の builder と同系であること

制約を満たす候補が尽きたら、その役割は割当不能として**ラウンドを打ち切る**。独立性を毀損したまま無人で続行しない（クロスレビューの独立性が品質ゲートの核であるため）。

## 判定契約の拡張（分類付き独立行契約）

reviewer への契約: 「最終行に必ず次のいずれか**とだけ**書く。不合格の場合はその前に理由と根拠（該当ファイル・テスト結果）を箇条書き」:

```
合格
不合格:内部構造   … 受け入れ条件は満たすが実装の質に fatal がある → fixer
不合格:API境界    … インターフェース・境界の切り方が原因 → モデル化へ戻る
不合格:要求前提   … 受け入れ条件・要求自体に矛盾や誤りがある → 打ち切り・報告
```

パースは herdr-multiagent-dev の独立行契約（末尾行から走査、部分一致禁止）を分類対応に拡張する:

```typescript
const VERDICT_LINE = /^[•\-*\s]*(合格|不合格[:：](内部構造|API境界|要求前提))[。．\s]*$/;
// 一致なし・分類なしの「不合格」単独は「判定不明」= 不合格:内部構造 として扱い fixer で確かめる
```

**分類はルーティングの提案であって決定ではない。** 自分が reviewer の理由・根拠を読み、誤分類（例: 実は設計問題なのに内部構造と報告）と判断したら戻り先を上書きする。上書きしたことと理由は台帳に記録する。

## builder への TDD 契約

herdr-multiagent-dev のプロンプト契約の型に、TDD の義務を追加する:

```
あなたは builder です。作業ディレクトリ: <絶対パス>
PLAN.md の受け入れ条件 <番号> を実装してください。
ルール:
- 先に受け入れ条件を失敗するテストで表現し、実行して失敗を確認してから実装する
- テストが通ったら、振る舞いを変えずに内部を整理する（Refactor）
- スコープ外のファイルに触らない: <限定リスト>
- 完了前に <テストコマンド> を実行して全件通ることを確認
完了報告には、実行したテストコマンドとその結果の要約を含め、
最終行に「実装完了」とだけ書いてください。
```

## 有界ループの規律

seiren は「問題なしと言えるまでループを抜けない」が、無人運用では上限が要る:

| 戻り先 | 上限 | 超過時 |
|---|---|---|
| fixer（内部構造） | ラウンドあたり 3回 | 打ち切り |
| モデル化（API境界） | ラウンドあたり 1回 | 打ち切り |
| 探索（要求前提） | 0回（即打ち切り） | 要求の問題は無人で解けない。ユーザーへ報告 |
| plan-reviewer 不合格 | 4回 | 打ち切り |

- **役割の厳守: 指揮者はコードを直接修正しない**。fixer の上限内で収束しない不合格は、指揮者が肩代わりするのではなく打ち切りが正しい終了経路。指揮者の介入は「戻り先の最終決定・上書き承認・計画（ドキュメント）の修正」に限る
- **plan-reviewer の不合格が2回を超えたら、修正・再送を機械的に繰り返す前に前提を疑う**。不合格理由を並べてパターンを見る: 毎回異なる新規指摘なら計画の設計自体（スコープの切り方・受け入れ条件の粒度）に問題がある可能性が高く、計画を根本から書き直す。同種指摘の深掘り（検証の完全機械化の無限後退など）なら、指揮者が実装品質への影響を評価し、影響なしと判断すれば指摘を計画に反映した上で上書き承認して先へ進んでよい。どちらの判断も理由と併せて台帳に記録する
- **機械検証の適用除外は計画に最初から明記する**: コンポジションルート（CLI main 等の数行の結線）の単体テスト化や、テンプレート編集の「非改変」のような diff 性質の全文ハードコード検証は、要求すると完全機械化の無限後退に入りやすい。これらは受け入れ条件で「reviewer と指揮者が git diff を直接読んで確認する」と担保方法ごと宣言し、plan-reviewer への契約プロンプトにも適用除外として伝える。事後の上書きより事前の宣言のほうがレビュー往復が少ない
  （実例: kojo Phase A で2ラウンドが同型の無限後退により上書き承認に至った。うち1ラウンドは上限4回に到達）
- 打ち切りは失敗ではなく**正常な終了経路**。ラウンドを失敗として台帳に記録し、後続ラウンドが独立なら続行、依存するなら全体を止めてユーザーへ報告する
- **打ち切り時も回収・片付けを省かない**: 起動中の全ペインについてログ退避 → pane close を行う（herdr-multiagent-dev のライフサイクルに従う）。ここを省くとペインが残留し、失敗原因の調査材料も失われる
- ラウンド全体のタイムボックス（例: 2時間）は herdr-multiagent-dev のセッション規律を継承する

## 台帳

herdr-multiagent-dev の台帳（役割→エージェント+モデル）に加え、ラウンドごとに記録する:

- ラウンド ID・対象ユースケース・結果（合格 / 打ち切り:分類）
- 戻りの履歴（reviewer の分類、自分が上書きした場合はその理由）
- フォールバックの履歴（発動理由と、独立性制約でスキップした候補）
- 分類別の頻度はスキル改善の根拠になる: API境界での戻りが多いなら planner の設計精度、内部構造が多いなら builder への契約を疑う

## 振り返り（ラウンド横断の学習）

全ラウンド完了後（打ち切り終了を含む）、最終報告の一部として、そのセッションの台帳記録を材料に振り返りを行い、改善案をユーザーへ**提案**する。スキル・設定・テンプレートの書き換えは提案にとどめ、ユーザーの採否を待つ（採用されたものだけ反映し、feedback としてメモリにも記録する）。

- 材料: 台帳のラウンド記録（戻りの分類と頻度、フォールバック履歴、上書き判断とその理由、打ち切り理由）
- 観点:
  - **分類別の頻度**: API境界の戻りが多い → planner の設計精度を疑う。内部構造が多い → builder への契約を疑う。要求前提 → ラウンド分割・要求整理の粒度を疑う
  - **判定の質**: reviewer / plan-reviewer に誤分類・同種指摘の無限後退・スコープ逸脱はなかったか。指揮者の上書きは妥当だったか
  - **盲点**: 合格したのに後から問題が発覚したラウンドはないか。あれば「どの段階の観点に何が欠けていたか」を特定する（例: 受け入れ条件は満たしたが実環境との相互作用を見ていなかった）
  - **操縦コスト**: 送信失敗・ペイン残留・タイムボックス超過・フォールバック発動などの機構的ロス
  - **レビュー往復の削減**: plan-reviewer / reviewer の往復が多かった場合（目安: 2回超）、指摘群を並べて共通の根を見つけ、次回はどの段階に何を足せば往復が減るかを提案する。観点として追加する場合は、個別事例の列挙ではなく**汎用的・本質的な形に昇華**して references/principles.md に蓄積する
- 出力: 「うまくいったこと / 引っかかったこと / 改善案」を簡潔に。改善案には反映先（本スキルの規律 / agents.yaml / プロンプト契約 / テンプレート・検証基盤 / 対象リポジトリの issue）を明示する

## 次のステップ

合格したラウンドは `/git-commit` でコミットしてから次ラウンドへ。

全ラウンド完了後、振り返りの前に**ドリフト照合**を1回行う: 指揮者が成果物全体を PLAN.md の意図（および元の依頼）と照合し、「条件は満たすが意図から逸れている点」がないかを確認して結果を台帳に記録する。逸脱があれば追加ラウンドとして切り出すか、ユーザーへ報告する（全ラウンド合格後にレイアウト崩れが発覚した実例のような、ラウンド単位の合格が拾えない全体不整合の最終防衛線）。

その後、振り返りを行い、必要なら `/create-pr` へ繋ぐ。
