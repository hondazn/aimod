# 問題を理解すること

## ユーザー入力

```text
$ARGUMENTS
```

## このスキルの目的

解き方を考える前に、問題そのものを正しく把握しなければならない。

ソフトウェア開発では、曖昧な要求・不明確なゴール・暗黙の制約が常態である。
「実装に着手できる問題定義」を導き出すための構造化された対話を行う。

ゴールは「すぐに解ける状態」にすることではなく、「何を解くべきかを正確に理解した状態」にすること。

---

## 進め方

### 1. ユーザー入力を把握する

入力の種類で問いかけの出発点を変える:

| 入力 | 出発点 |
|------|--------|
| 具体的な問題文・Issue | 問題の構造分析 |
| 漠然とした課題感 | 問題の言語化 |
| 実装タスク | 前提条件と制約の洗い出し |
| デバッグ・調査 | 観察事実と期待の乖離の明確化 |

### 2. 4つの問いで問題を構造化する

以下の4つの問いからユーザーの状況に合うものを選び、**1つずつ順番に**問いかける。
各質問には**自分の推奨回答を添え**、ユーザーがそのまま受け入れる・修正する・却下するだけで前に進めるようにする。
コードベースや Issue を調べれば答えられる問いは、ユーザーに聞かずに自分で調査する。

#### (1) 未知のものは何か — What is the unknown?

「何を作るか」ではなく「何がまだわかっていないか」を特定する。
— 完了状態の定義、問題の単一性（複数の問題が混ざっていないか）、表層の症状と根本原因の区別。

#### (2) 与えられているものは何か — What are the data?

手元の情報・リソース・既存資産を棚卸しする。
— 既存コード・ライブラリ、観察可能な事実（ログ・エラー・再現手順）、過去の類似事例。

#### (3) 条件は何か — What is the condition?

未知と既知を結ぶ制約・要件を明らかにする。
— 技術的制約、非機能要件、時間的制約、変えてはいけないもの、条件同士の矛盾の有無。

#### (4) 条件を分解できるか — Can you separate the parts of the condition?

問題の構造を部品に分ける。
— 独立した小問題への分解、必須/推奨の区別、段階的リリース可能な分割、MVP の特定。

### 3. 設計の決定木を歩く

問いかけへの回答から派生する設計判断を1つずつ掘り下げる。判断間の依存関係を意識し、先に決めるべきものから順に解決する。
各判断について推奨案を提示し、ユーザーのフィードバックを待ってから次へ進む。

### 4. 理解を検証する

対話が進んだら、以下で理解の深さを測る:

- **言い換え** — こちらが問題を別の表現で述べ直し、ユーザーに確認する
- **図示** — データの流れ・コンポーネント関係・状態遷移を視覚化できるか
- **類推** — 過去に解いた似た問題から手がかりを得られないか

### 5. 問題定義を整理する

対話で得られた理解を以下の形に整理して提示する:

```
## 問題定義

**未知のもの** — [解くべきこと]
**与えられているもの** — [手持ちの材料]
**条件** — 必須: ... / 推奨: ...
**分解** — 1. [小問題] 2. [小問題] ...
**残っている不明点** — ...
```

---

## 次のステップ

問題定義がまとまったら、状況に応じて次のスキルへ引き継ぐ:

- **解法の戦略を練る** → `/devise-plan`（上の問題定義をそのまま入力にできる）
- **コードの構造・型・境界を決める** → `/design-code`
- **問題定義を Issue として記録する** → `/create-issue`

---

## 注意事項

- 「解く」のではなく「問題を理解する」スキル。解法の提案は理解が十分になってから
- 「わからない」は最も重要な発見の一つ。推測で埋めず「未確認」と明示する
- 全ての応答は日本語で行う
