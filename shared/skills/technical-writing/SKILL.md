# 日本語技術文書の規範

疲れた読み手が一読で理解できることを目標にする。文書の型・段落の役割・一文の積載量・多義性の有無を、この順で問う。

上位に立つ3つのルールがある。

- **働いていない語を削る。** その語が無くても文が成り立つなら、その語は消える
- **短い日常語を使う。** 長い語は、その長さに見合う精度を買っていなければならない
- **ルールが文を悪くするなら、別の方法で直すか、そのままにする。** ルールは読み手のためにある。全ルールを守った結果、機械が書いたような文になったなら、それは失敗である

## いつ効くか / いつ効かないか

効く: 設計文書、PR 本文、Issue、SKILL.md、社内向け解説記事、コミットメッセージ。

効かない:
- 文章を実際に書き直す作業手順（新規作成 / 校正 / 診断のモード分岐）→ `natural-writing`
- 成果物ができた後の削り → `less-is-more`
- コード内コメント → `coding-standards`「どこに何を書くか」
- 製品 UI の文言 → プロダクトのコピー規約

## 文書の型を先に決める

**1つの文書に1つの型。** 2つの問いで決まる。行動のための文書か、理解のための文書か。学ぶための文書か、作業のための文書か。

| | 学ぶため | 作業のため |
|---|---|---|
| **行動** | チュートリアル | 手順書 |
| **理解** | 解説 | リファレンス |

- **チュートリアル** — 書き手が教師で、学び手の成功が書き手の責任。何を学ぶかではなく何を作るかで始める。各ステップが目に見える結果を出す。説明は一節とリンクに留める
- **手順書** — 人が抱えている問題を解く。読み手の能力を前提にし、教えない。行動だけを書く。題は作業で付ける（「レーダーの校正手順」ではなく「レーダーを校正する」）
- **リファレンス** — 記述だけをする。指示も説得も意見も書かない。乾いて、網羅的で、断定的に。対象の構造をそのまま写す
- **解説** — 一つの主題に絞り、製品から離れても読める。設計判断・歴史・制約・代替案を書く。**意見を書いてよいのはここだけ**

型を混ぜない。手順書にリファレンス表を入れない、リファレンスで手取り足取り教えない、手順書で議論しない。分けてリンクする。

## 段落と論証の構成

- 一つの段落に一つの話題だけを置く。場面が複数混ざった長い段落は、一歩ずつに分割する
- 段落の最初の文を読めば、その段落が何の話か分かるようにする
- 段落の先頭で、前の段落との論理関係を接続表現で示す
- 新しい概念を導入するとき、いきなり辞書型の断定（「X は Y である」）で始めない。先に対象を置き、次にその働きを述べ、必要なら三文目で定義する
- 論証は一方向に進める。結論を出してから反論を処理し、結論を言い直す構成にしない
- 読み手が立てそうな誤った解釈は、明示的に否定してから本当の理由を述べる
- 「A ではなく B」と否定するときは、否定の根拠を一文添える

## 論証の厳密さ

- **推量を機械的に断定へ変えない。** 「かもしれない」「だろう」は、根拠なく主張を弱めている場合だけ削る。事実未確認・推定・読み手の疑念を表す場合は、その不確実性を保つ
- **異なるものを「同じ」とまとめない。** 区別すべき対象を一括りの言葉でくくらない
- **複数の要因がある事象を、単一の原因に還元しない**
- **章・節をまたいで、同じ概念の扱いを一致させる**
- **因果を主張するときは、その機構を一文で示す。** 「A だと B になる」だけ書いて理由を省略しない
- **検出・保証・解決を「必ず」できるかのように書かない。** 条件付きで正確に述べる
- **挙げた例が主張の全体を支えているか確認する。** 支えないなら主張の範囲を例に合わせて狭める

## 読み手の負荷

- 後で参照する必要のない固有名（ファイル名・関数名・識別子）を出さない
- 抽象的な言い回しの指す内容が文脈から一意に決まらないなら、その場で括弧で特定する。読み手に前を読み返させない
- 新しい例を追加して読み手が保持すべき文脈が増えるときは、前の例と何が違うのか、なぜもう一つ必要なのかを前置きする
- 節の問い・帰結に関係しない過剰な詳細を省く。議論に必要な具体は残す

## 演出の抑制

全面禁止ではなく節度の規範である。修辞は、それが効果を生む箇所でのみ使う。

- 溜めや修辞疑問で導出を演出するのは、緊張が議論に効く要所に限る
- 短い決め台詞を独立した段落にする演出を多用しない
- 太字強調を多用しない。誤読を防ぐ否定や節の帰結など、論理の要所に限り一節に一、二箇所
- 転回点を過剰に劇的にしない。事実を述べる一文で足りる場合が多い
- 「重要なのは〜である」のような前置きで主張を予告しない。主張をそのまま書く
- 指す内容が一意に決まらない比喩を使わない。平易な動詞でそのまま言う

## 空文の排除

論点を増やさず「ちゃんと書いている感」だけを付ける言い回しがある。書き上げたらこの節で点検する。

- **予告と総括** — 「重要なのは〜である」「本章では〜を扱う」「まとめると」「〜に他ならない」
- **姿勢の宣言** — 「正面から扱う」「正面から回収する」。中身の代わりに姿勢だけを述べる
- **空虚な形容** — 「不可欠」「核心的」「鍵となる」「多角的」「包括的」
- **空虚な動詞** — 「掘り下げる」「深掘りする」「言語化する」「触れる」
- **接続の型** — 「〜において」「〜という側面から」「〜の観点から」（新情報なし）、「さらに」「また」の連打
- **中身のない強調** — 「非常に」「極めて」「大いに」

全一覧と置換先は `references/empty-phrases.md`。

## 冗長の排除

- 同じ主張を言い換えて繰り返さない。一つの主張は一度だけ書く
- 隣接する節が同じことを別の角度で述べているなら、片方に吸収する
- 場面を描写した直後に、その内容を要約し直さない
- 同じ論理的役割を持つ並列の事実は、文を分けて重ねず一文にまとめる
- 読み手が自力で補える中間段階の説明は書かない
- 接続や評価のためだけの文を置かない
- 想像上の読み手との問答を修辞として使わない。主張はそのまま述べる
- 同じ規則・同じ事実が複数の置き場にないか。目立つ語で grep し、1箇所に絞る

## 削る前に命題を数える

冗長を削る前に、その箇所が運ぶ命題を列挙する。行為者と行為、条件・時制・順序、様相（義務・許可・禁止）、否定の保証と例外、所有・副作用・失敗モード・帰結。

形容と反復と叙述は、**全ての事実節が生き残り、かつ結果がより明確になるときだけ**削る。字数が減ったこと自体は改善ではない。

削りすぎの型は3つある。詳細と修正例は `references/overcorrection-traps.md`。

- **事実節を道連れにする** — 命題が同じ行に複数あるなら、文ではなく節を削る
- **根拠の語を落とす** — 数値は残しても「実測」を消すと、出典の無い数字になる
- **仮説を出荷済みに昇格させる** — 予定を現在形で書かない

## 使う前に確かめる語

次の語は禁止語ではない。使う前に、より正確な表現が無いかを問う語である。契約・境界・面・語彙。

問いは「その語が指すもの（規則・API・フィールド集合・型・検証・時点・失敗状態）を直接書けないか」。書けるなら直接書く。呼び出し側との契約やセキュリティ境界を指すときは、その語が正しい。

## 点検の範囲

範囲を先に決める。指定が無ければ、リポジトリの慣例から妥当な範囲を仮決めして宣言してから始める（範囲を聞くために作業を止めない）。リポジトリ全体を勝手に点検しない。

除外は必ず含める。凍結された記録（アーカイブ済みの文書）、生成物、外部から取り込んだファイルは、対象を明示されない限り点検も編集もしない。除外は包含の指定より後に置き、後から含め直せないようにする。

## 文書の置き場

同じ事実を2箇所に書かない。目立つ語で grep し、1箇所に残して他はリンクする。

| 層 | そこに置くもの |
|---|---|
| `shared/instructions.md` | 作業種別を問わず常に効く汎用ルールだけ |
| スキル本文 | その作業の判断基準・手順・アンチパターン |
| スキルの補助ファイル | 本文からしか参照しない長大な参照表・例 |

媒体ごとの一般則（コード本体・コメント・テスト・コミットログ・git 履歴）は `less-is-more`「置き場」が持つ。

上限に当たったら順に試す。①別の置き場へ移す ②圧縮する ③本当に語数が要る場合だけ上限を上げ、その差分を正当化する。低すぎる上限は上限のバグであり、上限は削減目標ではない。

## 設計判断を残すとき

その案が何に勝ったかを書く。勝った相手が書かれていない決定は、後で蒸し返される。

新しい記録を書く前と後に、同じ決定・機構・却下案を扱う既存の記録を探し、上位互換（全体・一部）をその場で分類する。実装済みで将来の判断に効かないものは畳み、効くものは残して相互リンクする。却下案は、それが今も魅力的な誤りであり続ける間だけ残す。

## Markdown の整形

1段落を物理1行で書く（折り返しはエディタのソフトラップに任せる）。手で折り返すと、1語の修正で段落全体が差分になる。コードブロック・表・リストの構造はそのまま保つ。

相互参照は機械が検証できる形にする。相対パスでリンクし、散文で「〜を参照」と書かない。

## 見出しの付け方

- その節が答える問い、または扱う対象を指す句にする
- 作業の手順だけを述べる見出しや、情報量のない見出しにしない
- 節の結論を言い切る「セリフ」にしない。見出しの時点で読み手がオチを知る状態を避ける

## 適用例

Before:

> 設定ファイルのパラメータの設定は config.json 経由で行われます。なお、--write を付けて実行すると
> 現在の値を反映してコミット済みの値が更新されますが、これは値を下げるときのみ行うべきである
> ことに注意することが重要です。超過した場合、CI が失敗します。

After:

> `budget.mjs` は `budget.json` からコミット済みの上限を読み、対象ファイル数を数える。
> 数が上限を超えると CI が落ちる。`budget.mjs --write` は上限を下げるときだけ実行する。

効いたルールを逐条で挙げる。「設定は行われます」が「`budget.mjs` は読む」になり、行為者が明示された（段落と論証）。実ファイル名が名前の役割を果たしている（読み手の負荷）。五重の名詞連結が平の節に分かれた（論証の厳密さ）。「注意することが重要です」の前置きが消えた（空文の排除）。失敗条件が、それを説明する手順の前に移った（読み手の負荷）。埋もれていた「下げるときのみ」が「だけ」を動詞の隣に置いた命令になった（冗長の排除）。「超過した場合」に主語（数）が付いた（論証の厳密さ）。

## 判定テスト

- 「この文書は1つの型か」— 手順書に背景説明が、リファレンスに手取り足取りが混ざっていないか
- 「各段落の最初の文を読めば、その段落が何の話か分かるか」
- 「因果を主張した箇所で、なぜそうなるのかの機構を一文で示したか」
- 「この記述を削ると、事実の命題が1つ消えるか」— 消えるなら、節だけを削るか書き直す
- 「根拠の語（実測・出典）を落としていないか」— 数値だけ残して出典を消していないか
- 「同じ規則が2箇所に書かれていないか」— 目立つ語で grep したか
- 「この文が更新するのは、対象そのものか、それとも文書自身か」— 文書自身なら削る
- 「この文を他プロジェクトのドキュメントにそのまま置けるか」— 置けるなら、この文はこの文書について何も言っていない
- 「ルールを守った結果、機械が書いたような文になっていないか」— なっているなら、そのルールはこの文には効いていない
