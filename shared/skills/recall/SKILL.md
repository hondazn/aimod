# 過去セッションからの再開 — 履歴ではなく実状態を返す

transcript は「そのとき何をしたか」の記録であり、**現在の真実ではない**。ユーザーが知りたいのは今どこにいるかで、ブリーフの価値は現状の把握と履歴の突き合わせで決まる。

## いつ効くか / いつ効かないか

効く: 「前にやった作業の続き」「このリポジトリで何をしていたか」「どこまで進んだか」「経緯を思い出したい」「あの変更どうなった」。数日以上離れた作業の再開。セッションを跨いだ未決の確認。

効かない:
- 特定の1セッションの続きを書く → そのセッションをそのまま再開する
- スキル自体の改訂（実ログ → スキル改訂） → `reflect`
- タグの根拠を証拠として認めるかの判断 → `evidence-discipline`
- 大きな出力の委譲設計 → `delegation-discipline`

## 探索対象と範囲

対象は `~/.claude/projects` と `~/.codex/sessions` の JSONL。**Cursor と opencode の transcript には非対応。**どちらかで作業したセッションが話題なら、探索せず非対応だと明示する。空の結果を「作業なし」として返さない。

JSONL の `cwd` メタデータが作業中ワークスペースと**完全一致**するものだけを読む。別プロジェクトの会話は読まない。既定の窓は直近7日。ユーザーが範囲を指定したらその範囲だけを見る。「全部」を勝手に「直近N件」へ狭めない。[references/scope.md](references/scope.md) に、現状の把握を探索より先に置く理由と境界を書く。

## 手順

1. 現状を先に取る。`git status` / `git log` / `gh pr list` でブランチ・未コミット差分・PR の実状態を掴む。探索の窓とワークスペースを固定し、ユーザーに言い返す。ユーザーが既に状態（パス・ブランチ・変更）を渡しているなら、探索は省いてブリーフだけ書く。
2. transcript を列挙する。`scripts/find-transcripts.mjs` をこの SKILL.md からの相対で解決し、`node` で実行する。

   ```
   node scripts/find-transcripts.mjs --host claude --host codex --workspace "$PWD" --limit 20
   ```

   `--host` は繰り返し指定できる。`--limit` を必ず付け、mtime 降順の先頭から窓に入る分だけを使う。
3. 読む範囲を絞る。トピックが指定されていれば先に grep し、一致した transcript とその該当箇所だけを読む。現セッション、サブエージェントのログ、テスト・評価用のセッションは除く。3本以上あるなら `delegation-discipline` に従ってサブエージェントへ分け、親には所見だけを戻す。1〜2本なら自分で読む。
4. タグを実状態で検証する。transcript の自己申告は信用せず、`git` / `gh` で確認できた状態だけを書く。確認できなかったスレッドはタグを付けずに残し、確認できていないことを記す。推測でタグを埋めない。
5. 出力契約に沿ってブリーフを書く。指定トピックから外れたスレッドは、現在の作業を妨げる場合だけ載せる。

## 出力契約

カプセル → スレッド → 問題 → 次の一手の順で書く。詳細は下に置くか、切る。

| 節 | 内容 | 上限 |
|---|---|---|
| カプセル | この作業が何で、全体のどこにいるか | 5行 |
| スレッド | 1行1件。状態タグを必ず1つ付ける | 1画面に収まる分 |
| 問題 | 繰り返し報告されている症状、出荷後に revert された修正 | 5件 |
| 次の一手 | 最も有用な具体行動 | 1つ |

スレッド行のタグは次の6つだけ。1行に2つ付けない。タグの付かない行は未完成として扱う。

| タグ | 意味 | 検証 |
|---|---|---|
| `[merged #N]` | PR #N がマージ済み | `gh pr view N` |
| `[open PR #N]` | PR #N が open | `gh pr view N` |
| `[in flight <branch>]` | ブランチ上で進行中 | `git branch` / `git log @{u}..` |
| `[verified, uncommitted]` | 動作確認済みで未コミット | `git status` / `git diff` |
| `[reverted #N]` | PR #N の変更が revert 済み | `git log` |
| `[planned, not started]` | 計画のみで作業なし | transcript + `git log` |

カプセルとスレッド行が1画面を超えるなら、削るのは詳細であってスレッドではない。スレッドの根拠は transcript を、共有記録の根拠は PR 番号・Issue 番号で示す。

## サボった兆候

- transcript の「PR #12 をマージした」を `gh` で確認せずそのまま書いた
- タグなしのスレッド行がある、または1行にタグを2つ付けた
- 探索の窓とワークスペースを宣言せず「最近」で済ませた
- 別ワークスペースの transcript を読んだ
- Cursor / opencode のセッションを探索したかのように書いた
- カプセルが5行を超え、そのしわ寄せでスレッド行を削った
- 隣接機能や無関係なチケットをブリーフに混ぜた
- 生の transcript を親セッションで全部読み、その上で要約を重ねた
- 「次の一手」が複数ある、または実行可能な行動になっていない

## 判定テスト

- 「スレッド行のタグを、`git` / `gh` の生出力で説明できるか」— できないならタグを外す
- 「探索の窓とワークスペースを先に宣言したか」
- 「ユーザーは既に状態を渡していないか」— 渡しているなら探索は無駄
- 「カプセルは5行以内か。超えたとき、削ったのは詳細かスレッドか」
- 「『次の一手』は1つで、次にそのまま実行できる具体性があるか」
- 「問題の節に、繰り返し報告された症状か revert された修正が入っているか」
- 「Cursor / opencode のセッションが話題なら、非対応だと明示したか」
