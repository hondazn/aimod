# テスト分離 — 並行実行で落ちない資源の扱い

テストが単独では緑、並行実行では赤になるなら、テストが資源を排他的に所有できていない。

**プロセスの分離は、ポート・予測可能なパス・外部サービス・DB・ソケット・継承した子プロセスを分離しない。**

## いつ効くか / いつ効かないか

効く: CI で非決定的に落ちるテストの調査と修正。ポート・一時ファイル・環境変数・時刻・サブプロセス・teardown を触るテストの追加。実行順で結果が変わるテスト。共有ホストの資源を掴む fixture のレビュー。

効かない:
- テストの書き方・TDD・再現テストの規律 → `coding-standards`
- 赤を報告する前の証拠の強度と、並行実行中の赤を単独で測り直すこと → `evidence-discipline`
- 委譲先や並列作業の構成の設計 → `delegation-discipline`

## 前提: 並行実行の層

設定が否定しない限り、次の層は重なると仮定する。

1. 同一ファイル内のテスト
2. 別ファイル、または別ワーカープロセス
3. 同一ジョブ内の独立したテスト・ゲートプロセス
4. 同一ホストを共有する別ジョブ

直列化が守れるのは層1だけである。層2〜4のプロセスは止められない。

## 資源ごとの契約

獲得する資源ごとに、次の5点を言えるようにする。言えない資源は所有できていない。

| 項目 | 求めるもの | 例 |
|---|---|---|
| owner | 生成・公開・停止を担う唯一の主体 | fixture が起動したサーバ |
| 原子的割当の機構 | 空き確認と獲得が不可分な allocator | `listen(0)` / `mkdtemp` |
| 観測可能な ready 信号 | 外から観測できる利用可能の事象 | listening イベント / ready ファイル |
| 登録された cleanup | 獲得直後に登録し、失敗時も走る | `try/finally` / `afterEach` |
| 静止の完了信号 | 新規入力を止め、所有作業の終了を待つ | close の完了 / 子プロセスの exit |

## 割当

空きを確認して後から獲得しない。所有者の allocator に一度で割り当てさせる。

- ネットワーク: loopback に `listen(0)` で bind し、listening を観測してから割り当てアドレスを読む。空きポートを走査して後で bind しない
- 一時領域: テストごとに `mkdtemp` で私有ルートを作る。予測可能な共有パスを取らない
- DB・ソケット・セッション・出力先: テストごとの一意名前空間を与える
- 既存が許されないパスは exclusive creation で作る

記録用の安定 ID（保存済み URL・期待パス文字列）と一時的な転送アドレスを混ぜない。安定値は期待値のまま残し、実資源への変換は fixture の内側で行う。パーサ入力や期待値としてしか使わないリテラルは獲得資源ではない。

## process-global 状態

`process.env`、cwd、fake timers、locale/timezone、module mock、レジストリ、console hook、`globalThis`、global fetch は排他的な可変資源として扱う。注入した依存かインスタンス固有のアダプタを優先し、変更が要る場合:

- 変更前の値が「無かった」か「あった」かを記録する
- その正確な状態を復元し、復元を変更の直後に登録する（`try/finally`、必要なら `afterEach` の二重系）
- 所有する最小の呼び出し・リクエストだけを intercept する
- 復元を検証する。変更後の読み取りは復元の証明にならない。テスト終了時の観測で確かめる

## 同期は状態で取る

固定 sleep は setup 完了や cleanup 静止の証拠にならない。

- 明示的な ready 事象・ハンドシェイク・状態遷移・所有 promise を待つ
- 競合は barrier や deferred promise で決定的な地点に置く。繰り返し実行は競合テストではない
- timeout は待ちを bound するためだけに使い、assert を成立させる条件にしない
- scheduler 依存の順序は、それが製品の振る舞いでない限り assert しない
- 時刻が主題なら clock を注入・fake 化し、real timer を必ず戻す
- timeout は実測した競合に対して予算化する。hook の予算もテストと同じだけ上げる（setup と teardown は同じ競合を払う）

## teardown は静止まで待つ

`abort()` / `close()` / `kill()` を呼んで完了信号を待たないのは未完了の teardown。

cleanup は新規コールバックを止め、listener を外し、global hook を戻し、所有作業を終了させ、子プロセスの exit・サーバの close・ワーカーの終了を await する。失敗した試行の残骸も残さない。遅れて完了する処理があるなら、それが別のテストを書き換えないことを示す。

## 隠さず所有で直す

1つの fixture が非分離だからとスイート全体を直列化しても、層2〜4からは守れない。まず排他範囲を狭めるか、資源の割当を変える。

次は根因修正ではない。ローカルで決定的に落ちるテストに対して提示しない。

| 隠し方 | 何を隠すか |
|---|---|
| 待つ状態を特定しない timeout 延長 | awaited 状態の不在 |
| リトライ追加 | 非決定的な獲得 |
| 全ファイルの直列化 | 別プロセスとの衝突 |
| 例外・unhandled rejection の握り潰し | 失敗そのもの |
| assert の弱体化 | 検出漏れ |
| 不安定値の正規化 | 出力の非決定性 |
| cleanup や assert の前の sleep 追加 | 静止の未確認 |

外部プロバイダの文書化された一過性に対するリトライだけは有効で、例外は外部境界に留める。待つ作業を特定した上で既存予算に戻す timeout 引き上げは隠しではない。

## 修正を証明する

- 通常の回帰は、修正前に落ちることを観測する
- 新しい static / corpus のガードには negative control を付ける。拒否したい入力を一時的に混ぜ、意図した失敗が出ることを見る
- 競合は barrier で重なりを証明する
- ポート・ソケット・共有パス・サブプロセスは、プロセス間分離が修正の一部なら独立プロセスを並行実行して確かめる
- 外部状態・イベント・ファイル・ログ・exit・dispose を検証する。コンポーネントの自己申告を信じない

stress 実行は決定論的な回帰を補うもので、置き換えない。

## サボった兆候

- 空きポートを走査して見つけ、あとで bind している
- テストの一時ディレクトリが固定パスを共有している
- `process.env` や cwd を変更し、復元を検証していない
- teardown が `close()` / `kill()` を呼んだだけで完了を待っていない
- setup 完了を sleep やポーリング間隔で代用し、落ちるたびに timeout を延ばす、リトライを足す、スイートを直列化する
- 「何度か回して通った」を安定として報告している
- 新しいガードを足したが、破る入力で落ちることを示していない
- 共有資源の owner が誰か言えない

## 判定テスト

- 「このテストは何を所有しているか。owner・割当機構・ready 信号・cleanup・静止信号を5つとも言えるか」
- 「空きを確認してから獲得していないか。獲得は1回の原子的操作か」
- 「記録用の安定値と実行時の一時アドレスを混ぜていないか。変換は fixture の内側にあるか」
- 「この sleep は何の完了を待っているか。それを直接観測できる事象は何か」
- 「teardown は静止を待ったか。遅れて完了する処理が別のテストを書き換えないと言えるか」
- 「直列化やリトライは、所有の欠陥を隠していないか」
- 「このガードを破る入力で落ちることを見たか」
- 「この分類は、修正案ではなく記録された証拠から出したか」
- 「timeout は実測した競合に対する予算か。待つ状態を特定できるか」
