# flake の分類と診断

既存の非決定的な失敗を調べるときの手順。診断だけを求められた場合は読み取り専用で、原因と証拠の報告までにする。修正・再実行・CI 設定の変更は、別に依頼された場合だけ行う。

## 証拠を凍結する

記録する項目: リポジトリ / ワークフロー / ジョブ / commit SHA / ランナーの種類 / 時刻 / 失敗したテストとコマンド / 最初の安定した失敗シグネチャ。インフラのメッセージとテスト出力は分けて保存する。

複数の失敗実行と成功実行を比較する。同一 SHA の実行を優先し、それが無理なら比較対象の間でテストと CI 設定が同一であることを確かめる。1回の成功再実行はインフラ障害の証明にならず、1回の timeout は製品の競合の証明にならない。

失敗が同じホスト・資源名前空間で重なっているかを、ログとメタデータから判定する。ログの貼り付けでなく、根拠となる実行へのリンクを残す。

## 8分類

最終的な修正ではなく、記録された証拠から分類する。

| # | 分類 | シグネチャ | 確かめ方 |
|---|---|---|---|
| 1 | ホスト資源の衝突 | 同一ポート・ソケット・DB・予測可能パス・キャッシュ・外部名前空間を独立プロセスや別ジョブが獲得する | 同一識別子の同時獲得を示す。または原子的な一意割当で衝突が消えることを示す |
| 2 | ライフサイクル未完了 | teardown が子・ワーカー・ストリーム・サーバ・コールバックの静止前に戻り、遅れた出力や変更が別テストに現れる | dispose 後に新規入力が止まり、所有作業の終了を待つことを示す |
| 3 | プロセス全体の汚染 | 結果がテスト順に依存する。`process.env`・cwd・fake timers・globals・mock・locale・module 状態の漏れ | 復元の証拠。単独実行と順序を変えた実行を比較する |
| 4 | 負荷依存の同期 | sleep・ポーリング間隔・event-loop 1周への仮定が ready や完了の代用になっている | 待つべき状態を特定し、事象待ちに置き換えて再現を消す |
| 5 | プラットフォーム・起動経路の不一致 | OS・shell・ファイルシステム規則・ソース/ビルドモード・実行入口に一貫して従う | 時刻精度・環境変数名の大小・ハンドル解放・権限の差を確認する |
| 6 | 製品の並行性欠陥 | テストが資源を制御し、明示的な重なりで決定的に再現し、出荷コードの競合を露出する | barrier で重なりを証明する |
| 7 | 外部プロバイダの一過性 | 失敗が live API・ネットワーク境界に帰属し、文書化されたリトライ方針に一致する | プロバイダ側の記録と突き合わせる |
| 8 | ランナー基盤 | checkout・依存取得・ディスク・ホストプロセス・ランナーサービスがテストコマンドと独立に失敗する | ランナー自身の直接証拠を要求する。ホスト指標が無い環境では無いと明記し、ログが持つ情報で分類する |

証拠が複数の独立した事実を支えるなら、それぞれを報告する。timeout・signal・exit code・assert を1つの推測に潰さない。

## 再現のはしご

所有しているテストファイルか、絞り込んだテスト名から始める。シグネチャが再現する最初の段まで並行度を上げる。

1. テストプロセス1つ
2. 同一プロセス内の並行テスト・並行ファイル
3. 独立したテストランナープロセス複数
4. 所有リポジトリのゲートを設定済みの並行度で
5. 問題のホスト資源を共有する別ジョブ・別ランナープロセス

実行中の設定・環境スイッチ・ソース/ビルドモード・プラットフォームを一致させる。別の失敗を作るために本番の timeout を下げたり、無作為な負荷を足したりしない。

手元のホストで実行できないプラットフォームのシグネチャなら、到達できる最後の段で止める。その限界を記録し、別プラットフォームの成功実行で置き換えない。CI を再現に使う場合は、1回に1つの容疑 owner だけ変えて帰属を保つ。

競合が疑われるなら、確率的なタイミングを争点の遷移に置いた barrier に変える。ホスト衝突が疑われるなら、同一識別子の同時獲得を示すか、原子的な一意割当が衝突を除くことを示す。

## owner で直す

修正が許可されたら、割当・ready の公開・global 状態の変更・teardown を所有するコンポーネントを直す。snapshot の正規化・リトライラッパ・広い timeout・全体直列化・弱い assert に隠さない。

記録用の fixture データと live 資源の割当を分ける。記録済み URL は安定のまま、fixture が transport を OS 割当ポートへ写してよい。安定した期待パスは assert のままでよく、共有書き込みディレクトリにする必要はない。

## 調査の終了条件

- 元のシグネチャに、支持された分類がある
- 最小の関連トポロジで再現する。再現できないなら外部証拠が十分で、再現の限界が明示されている
- 許可された修正が negative control（または修正前の状態）で落ち、同じトポロジで通る
- 資源の owner が要求する並行プロセス・復元・静止 teardown の証明が通る
- 残る CI チェックは、観測した状態のまま passing / pending / skipped / failing として報告する

「たまたま通るまで回して安定と呼ぶ」ことをしない。選んだ証拠が結論を確立したら止める。分類を妨げる事実が欠けているなら、それを報告する。
