# ビフォー・アフター例集

具体的な校正例を通じて、自然な日本語の書き方を学ぶ。各例には「なぜそう直すのか」の判断根拠を添えている。

After に原文に無い数値や体験が入る例には、その出どころを「書き手から得た事実」として示している。この欄が無い状況で同じ数値を書いてはならない。材料が無いときの直し方は例7と例12にある。

## 1. AI臭い導入の除去

### Before
```
本記事では、プログラミング学習の効果的な方法について
詳しく説明していきたいと思います。
プログラミングは現代社会において非常に重要なスキルであり、
多くの人々がその習得を目指しています。
```

### 書き手から得た事実
```
3ヶ月間、毎日30分コードを書いた。それが仕事の自動化に直結した。
```

### After
```
プログラミングを学び始めて3ヶ月。
毎日30分のコード練習が、仕事の自動化に直結した。
```

### 判断根拠
- 「本記事では〜説明していきたいと思います」→ 読者はすでにこの記事を開いている。何を書くかの宣言は不要
- 「非常に重要なスキル」「多くの人々」→ 情報量ゼロ。誰が読んでも書ける文
- 著者の実体験から始めることで「この人の話を聞こう」と思える冒頭になる。体験は書き手から得たものだけを使う

## 2. 過剰修飾の削減

### Before
```
このツールは非常に優れた機能を持っており、
極めて効率的な作業を実現することができます。
まさに画期的なソリューションと言えるでしょう。
```

### 書き手から得た事実
```
導入後、作業時間が半分になった。特にファイル整理の自動化が役に立った。
```

### After
```
このツールで作業時間が半分になった。
特にファイル整理の自動化が役に立っている。
```

### After（事実が無い場合）
```
このツールを使うと、作業を効率よく進められます。
```

### 判断根拠
- 「非常に」「極めて」「まさに」→ 3つの強調語が3文に1つずつ。根拠なく盛っている印象
- 「画期的なソリューション」→ 抽象的な評価。読者は「具体的に何が？」と思う
- 「作業時間が半分」「ファイル整理の自動化」→ 読者が効果を実感できる。ただし書き手が測った値があるときだけ使える
- 事実が無いなら強調語を削るだけにとどめ、「どれくらい短くなったか」を書き手に確かめる

## 3. 曖昧表現の具体化

### Before
```
この方法は効果があるかもしれません。
一般的には良い結果が得られると思われます。
基本的にはおすすめできると言えるでしょう。
```

### 書き手に確かめた結果
```
試した3人のうち2人が目標を達成した。経験者向けで、初心者には別の方法を勧めたい。
```

### After
```
この方法で3人中2人が目標を達成した。
ただし、経験者向け。初心者には別のアプローチを勧める。
```

### 判断根拠
- 「〜かもしれません」「〜と思われます」「〜と言えるでしょう」→ 3文連続の断定回避。読者は「結局おすすめなの？」と感じる
- 推量のどれが確かな事実かは原文からは分からない。書き手に確かめてから言い切る
- 対象者を「経験者向け」「初心者には別」と明示することで、曖昧さなく推薦できる

## 4. テンプレート表現の個性化

### Before
```
コミュニケーションが大切です。
チームワークを意識することが重要です。
日々の努力が必要です。
```

### 書き手から得た事実
```
週1回15分のミーティングを始めたら、チームの雰囲気が変わった。
「困ってること何かある？」と聞くようにしたら、問題に早く気づけた。
```

### After
```
週1回の15分ミーティングでチームの空気が変わった。
「困ってること何かある？」の一言で、問題が早期に見つかる。
```

### 判断根拠
- 「大切」「重要」「必要」→ 同じ構文パターンが3回。フォーマットで文章を埋めている状態
- 抽象的な心構えは読者の行動を変えない。具体的な行動（週1回15分、一言の問いかけ）とその効果を書くことで、読者が「試してみよう」と思える
- 著者の体験として書くことで、テンプレート感が消える

## 5. 感情押し付けの事実化

### Before
```
この素晴らしい技術は、驚くべき進歩を遂げています。
感動的な成果が次々と生まれており、
誰もが興奮せずにはいられません。
```

### 書き手が示した資料
```
5年で処理速度が100倍。医療診断では、専門医の精度を超えた分野がある。
```

### After
```
この技術は5年で処理速度が100倍になった。
医療診断の精度が人間の専門医を超えた分野もある。
```

### 判断根拠
- 「素晴らしい」「驚くべき」「感動的」「興奮せずにはいられません」→ 4つの感情表現。読者の感情を押し付けている
- 感情は事実を読んで読者が抱くもの。「100倍」「専門医を超えた」という事実のほうが、「驚くべき」という形容詞より読者の感情を動かす
- 読者の感情を代弁する（「誰もが興奮」）のは特に避ける。読者は自分の感情を決められたくない

## 6. 文体統一

### Before（混在）
```
まず、設定画面を開きます。
次に、オプションを選択する。
最後に、保存ボタンを押してください。
```

### After（統一: です/ます調）
```
まず、設定画面を開きます。
次に、オプションを選択します。
最後に、保存ボタンを押します。
```

### After（統一: だ/である調）
```
まず、設定画面を開く。
次に、オプションを選択する。
最後に、保存ボタンを押す。
```

### 判断根拠
- 3文中、1文目「〜ます」、2文目「〜する」、3文目「〜ください」と3つの文体が混在
- 短い手順文でも文体の揺れは目につく。読者は無意識に「雑に書かれた文章だ」と感じる
- どちらの文体に統一するかは文書の目的と読者による
- 手順書（決まり）なので「〜します」にそろえた。読み手への依頼として書く文書なら「〜してください」にそろえる

## 7. 長文の分割

### Before
```
このプロジェクトは、当初の予定よりも大幅に遅れており、
その原因としては、要件の変更が頻繁に発生したことと、
チーム内のコミュニケーション不足があったと考えられ、
今後は週次のレビューを導入することで改善を図りたいと思います。
```

### After
```
このプロジェクトは当初の予定より大幅に遅れている。
原因は、要件の変更が頻繁にあったことと、チーム内のコミュニケーション不足だと考えている。
今後は週次のレビューを導入して改善したい。
```

### 書き手に確かめたい点
```
- 「大幅に」「頻繁に」の実際の値（遅れの期間、変更の回数）があれば、本文に入れて具体化できる
```

### 判断根拠
- 原文は1文で4つのこと（遅延の事実、原因1、原因2、対策）を言っている。事実・原因・対策の3文に分ける
- 「と考えられ」は書き手の見立て。「と考えている」として推量の強さを保つ。断定にしない
- 「図りたいと思います」は意向。「改善したい」として意向のまま残す。予定の「導入する」に上げない
- 「大幅に」「頻繁に」を数値に置き換えたいが、原文に値が無い。作らずに書き手に確かめる

## 8. 専門用語の配慮

### Before
```
APIエンドポイントをRESTfulに設計し、
JWTによる認証を実装してCORSを設定した。
```

### After（一般読者向け）
```
外部サービスとの接続口（API）を設計した。
ログイン認証の仕組みと、異なるサイト間での
データやり取りの許可設定も実装した。
```

### After（技術者向け）
```
RESTful APIを設計。認証はJWT、CORS設定も完了。
```

### 判断根拠
- 同じ事実でも、読者によって最適な表現が異なる
- 一般読者向け: 専門用語を噛み砕き、括弧で原語を添える。何をしているかがわかることを優先
- 技術者向け: 専門用語はそのまま使い、冗長な説明は省く。簡潔さを優先
- 読者が誰かわからない場合は、一般読者向けに書くのが安全

## 9. 複合的な校正

実際の校正では複数の問題が同時に存在する。ここでは複合的なケースを示す。

### Before
```
本日は、弊社の新しいプロジェクト管理ツールについて
ご紹介させていただきたいと思います。
このツールは非常に画期的なもので、
チームの生産性を大幅に向上させることが可能です。
基本的には、どなたでも簡単に使えるものとなっておりますので、
ぜひ一度お試しいただければ幸いです。
```

### 書き手が示した製品資料
```
主な機能: 進捗ダッシュボード、ドラッグ操作での担当者変更、Slack への自動通知。
導入チームの実績: 週次の進捗確認が30分から5分に短縮。
無料トライアル: 30日間。
```

### After
```
新しいプロジェクト管理ツールを紹介します。

特徴は3つ。タスクの進捗が一目でわかるダッシュボード、
ドラッグ操作だけで担当者を変更できるUI、
Slackへの自動通知。導入チームでは週次の進捗確認が
30分から5分に短縮されました。

無料トライアルが30日間あります。
```

### 判断根拠
- **AI臭い導入の除去**: 「ご紹介させていただきたいと思います」→「紹介します」に簡潔化
- **過剰修飾の削減**: 「非常に画期的」→ 削除し、代わりに資料にある3つの特徴を列挙
- **冗長表現の刈り込み**: 「向上させることが可能です」「ものとなっております」→ 簡潔な表現に
- **具体化**: 「大幅に向上」→ 資料の実績「30分から5分に短縮」
- **テンプレート的な締めの排除**: 「お試しいただければ幸いです」→ 資料にある具体的な情報（30日間無料トライアル）に

## 10. 比喩動詞と含み

### Before
```
設定を保存した瞬間に、古いキャッシュが静かに壊れます。
この調整が、検索の速さに地味に効いてきます。
原因の調査に丸一日溶かしてしまいました。
```

### After
```
設定を保存するとすぐに、古いキャッシュが気づかないうちに使えなくなります。
この調整が、検索の速さに目立たないながらも役立ってきます。
原因の調査に丸一日かかってしまいました。
```

### 判断根拠
- 「〜した瞬間に」→ the moment の直訳。「〜するとすぐに」
- 「静かに壊れる」→ 何が起きるのか一つに決まらない。キャッシュには「使えなくなる」と同じ広さの語を使う。「エラーを出さずに」とは書かない（エラーが出ないかは原文から分からない）
- 「地味に効く」→ 「目立たないながらも役立つ」。「地味に」の目立たないが確かな感じを残す
- 「溶かしてしまった」→ 「かかってしまった」。「〜てしまった」の後悔を残す

## 11. 文末の立場と時制

### Before（チームの運用ルールとして書かれた文書）
```
障害を検知したら、まず当番に連絡しましょう。
復旧後は、原因を Issue に残しておくことが大切です。
```

### After
```
障害を検知したら、まず当番に連絡します。
復旧後は、原因を Issue に残します。
```

### 判断根拠
- 依頼に「チームの運用ルールとして」とある。決まりの文書なので、決まりそのものを「〜しましょう」「〜が大切です」で書かず「〜します」にそろえる
- 読み手への心得として書く文書なら、原文の「〜しましょう」のままでよい

### Before（変更内容の報告）
```
認証方式を JWT に変更します。また、失敗時は3回まで再試行します。
```

### After
```
認証方式を JWT に変更しました。また、失敗時は3回まで再試行します。
```

### 判断根拠
- 完了した変更が予定の「〜します」に読める。報告と分かるので「変更しました」にする
- 再試行はシステムの動作の説明。今回実装したかは原文から分からないので、過去形にそろえない

## 12. 材料が無いときの校正

### Before
```
本システムの導入により、業務効率が飛躍的に向上しました。
特に、承認フローの境界を明確にしたことが大きく効いています。
```

### After
```
このシステムを導入して、業務効率が大きく上がりました。
特に、承認フローの境界をはっきりさせたことが大きく役立っています。
```

### 書き手に確かめたい点
```
- 「飛躍的に」の実際の値（処理時間や件数）があれば、本文に入れて具体化できる
- 「承認フローの境界」は何と何を区別したものか。分かれば語を置き換えられる
```

### 判断根拠
- 「飛躍的に」は強調語だが、数値は原文に無い。作らずに強調だけ和らげ、値を書き手に確かめる
- 「境界」が何を指すかは原文から決まらない。「担当範囲」「承認の段階」などに勝手に決めず、語を残す
- 「大きく効いています」→ 比喩動詞を「役立っています」に直す。「大きく」「特に」の比重は残す
- 本文に「※要確認」などの注記を挟まず、確認は別欄に置く

## 13. 校正の思考プロセス（実演）

以下は、文章を校正する際の実際の思考を再現したもの。

### 入力文

```
今回は、効果的な会議の進め方について考えてみたいと思います。
会議は多くのビジネスパーソンにとって非常に重要なものですが、
一般的には無駄が多いと感じている人も少なくないのではないでしょうか。
効率的な会議を実現するためには、いくつかのポイントを
押さえることが必要です。
```

### 思考の流れ

```
1. 全体を読む
   → ブログ記事の冒頭。読み手への説明。本題（ポイントの中身）はまだ無い。

2. 構造と主張の確認
   → 主張は3つ。会議は重要／無駄が多いと感じる人は少なくない（推量）／効率化にはポイントがある。
   → 推量の強さ（「〜のではないでしょうか」）は保つ。

3. AI臭さを検出
   → 「今回は〜考えてみたいと思います」: 冗長な導入
   → 「非常に重要なもの」: 過剰修飾
   → 「一般的には」: 条件のないヘッジ
   → 「いくつかのポイントを押さえることが必要です」: 予告だけの文

4. 文体チェック
   → です/ます調で統一されている。問題なし。

5. 具体化の余地
   → 「多くのビジネスパーソン」「無駄」「いくつかのポイント」はどれも抽象的。
   → ただし数値や中身は原文に無い。作らない。

6. 判断
   → 導入と強調語、「一般的には」は削る。
   → 予告文は、続く中身があれば1文にまとめるが、入力に中身が無いので残す。
   → 中身と数は書き手に確かめる。

7. 原文と並べて読み比べる
   → 主張3つは残っている。推量は推量のまま。足した数値・事例は無い。
```

### 校正結果

```
会議は多くの人にとって大事な場ですが、
無駄が多いと感じている人も少なくないでしょう。
効率よく進めるために、押さえたいポイントがいくつかあります。
```

```
---
**主な変更点**
- 「今回は〜考えてみたいと思います」→ 削除（何を書くかの宣言は読者にとって不要）
- 「非常に重要なもの」→「大事な場」（根拠のない強調を外した）
- 「一般的には〜のではないでしょうか」→「〜でしょう」（条件のないヘッジを外し、推量の強さは保った）

**残した箇所**
- 「押さえたいポイントがいくつかあります」: 予告だけの文だが、続く中身が入力に無いため残した

**書き手に確かめたい点**
- ポイントの中身と数。分かれば予告文を中身と1文にまとめ、冒頭を具体的にできる
```
