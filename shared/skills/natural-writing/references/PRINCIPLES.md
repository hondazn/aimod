# AI臭さの検出・対処ガイド

SKILL.mdの表だけでは判断が難しい場合に、このファイルの詳細な検出パターンと対処例を参照すること。

以下の「良い例」にある数値や事例は、原文か書き手から得た事実である前提で書いている。手元に無い事実は作らない（SKILL.md「最優先: 意味を保ち、足さない」）。

## AI臭さの典型パターンと対処

### 冗長な導入

```
【検出パターン】
- 「〜について説明します」
- 「〜を見ていきましょう」
- 「それでは早速〜」
- 「まずはじめに〜」
- 「本記事では〜」

【なぜ問題か】
読者はすでにタイトルやリンクを見てこの文章に辿り着いている。
「何について書くか」を改めて宣言する必要はない。
本題が遅れるほど、読者は離脱する。

【対処】
削除して本題から始める。冒頭は具体的な事実、問い、またはエピソードで。
```

### 過剰な修飾

```
【検出パターン】
- 「非常に」「極めて」「大変」の多用
- 「〜と言っても過言ではありません」
- 「実に」「まさに」「本当に」の連発

【なぜ問題か】
強調語を重ねても説得力は上がらない。むしろ「根拠がないから言葉で盛っている」
という印象を与える。本当に重要なことは、事実で語れるはず。

【対処】
削除するか、原文にある根拠に置換。
悪い例: 「非常に効率的なツールです」
良い例: 「作業時間が半分になるツールです」（書き手が測った値がある場合）
根拠が無い場合: 「効率的なツールです」と強調語だけ削る
```

### 曖昧な断定回避

```
【検出パターン】
- 「〜かもしれません」の連発
- 「〜と思われます」の多用
- 「〜ではないでしょうか」の繰り返し

【なぜ問題か】
1回なら適切な留保だが、連発すると「自信がない」「責任を取りたくない」
という印象になる。読者は「結局どうなの？」と感じる。

【対処】
校正では強さを勝手に変えない。どれが確かな事実かを書き手に確かめる。
書き手が「経験者には効く、初心者には勧めない」と答えたなら、条件を明示して言い切る。
悪い例: 「便利かもしれません」
良い例: 「初心者には便利だ」（対象が書き手から分かっている場合）
```

### パターン化した構文

```
【検出パターン】
- 「〜という点で重要です」
- 「〜が大切です」「〜が必要です」の連続
- 「〜することが可能です」

【なぜ問題か】
同じ構文の繰り返しは、内容ではなくフォーマットで文章を埋めている証拠。
読者は3回目あたりで「またこのパターンか」と感じ、中身を読まなくなる。

【対処】
原文にある行動・結果に言い換える。無ければ繰り返しを1文にまとめる。
悪い例: 「コミュニケーションが重要です」
良い例: 「週1回の1on1で認識のズレが減った」（書き手の体験として得ている場合）
```

### 感情の押し付け

```
【検出パターン】
- 「素晴らしい」「驚くべき」「感動的な」
- 過度に肯定的な表現
- 読者の感情を代弁する表現（「誰もが興奮せずにはいられません」）

【なぜ問題か】
「すごい」と書かれても読者は「すごい」と感じない。
感情は事実を読んで読者自身が抱くもの。押し付けられると逆に冷める。

【対処】
事実を書き、判断は読者に委ねる。
悪い例: 「驚くべき成果を上げました」
良い例: 「前年比200%の成果が出た」（数値が原文や資料にある場合）
```

### 前置きのラベルと否定対比

```
【検出パターン】
- 「重要なのは〜」「結論から言うと〜」「ここで注目すべきは〜」
- 「A ではなく B です」の繰り返し

【なぜ問題か】
前置きは主張を予告するだけで、本題を遅らせる。
否定対比は、誰も主張していない A を立てて B を際立たせる修辞になりやすい。

【対処】
前置きだけを削り、評価は述語に移す。
「結論から言うと、このボタンを押すだけで完了します」→「このボタンを押すだけで完了します」
「重要なのは、見た目ではなくデータ構造です」→「見た目ではなく、データ構造が重要です」
A が誤解されやすい点を正しているなら否定は残す。「A に加えて B」「A より B」に変えない。
比較から方針へ移る「結論として」のように、つながりを担う前置きは残す。
```

### 予告だけの文

```
【検出パターン】
- 「注目すべき点があります」「次の点が挙げられます」「理由は以下の通りです」

【なぜ問題か】
中身のない文が1つ挟まり、読み手は次の文まで何の話か分からない。

【対処】
予告の重みを述語に残して、中身の文と1文にまとめる。
「開発で意識したい点があります。定期的な進捗共有が推奨されます。」
→「開発で意識したい点として、定期的に進捗を共有することが推奨されます。」
まとめると意味が変わるなら残す。
```

### 比喩動詞と含み

```
【検出パターン】
- 「安全側に倒す」「地味に効く」「時間を溶かす」「1つずつ潰す」「静かに壊れる」

【なぜ問題か】
指す動作が一つに決まらず、読み手が意味を補う。

【対処】
ふだんの動詞に直し、比喩に込められていた含みは別の言葉で残す。
「この工夫が、後々の運用で地味に効いてくる」→「この工夫が後々の運用で目立たないながらも役立ってくる」
「設定の反映に丸一日溶かしてしまった」→「設定の反映に丸一日かかってしまった」
含みの例: 「うっかり」の不注意、「ようやく」の待ちくたびれた感じ、「〜てしまった」の後悔。
定着した慣用句（骨が折れる、手を焼く）は直さない。目安は、AIが広まる前の人の文章でもふつうに見かけるかどうか。
```

### 擬人化

```
【検出パターン】
- 「コードが語る」「システムが願う」「ドキュメントが仕様を語っている」

【なぜ問題か】
道具や概念に意志を持たせると、実際に何が起きているかがぼやける。

【対処】
内容の所在や動作として書く。
「このドキュメントが API の仕様を語っている」→「このドキュメントに API の仕様が書かれている」
「このツールはログを集めます」のように、道具の働きを述べている文は非生物主語でも残す。
直すときに、元に無い条件（「〜を使えば」）や可能（「〜できます」）を足さない。
```

### コピー調

```
【検出パターン】
- 「資料を、全員へ。」「作業を、もっと確かに。」
- 助詞の後で読点を打って間を作る文

【なぜ問題か】
広告の文体で、誰が何をするのかが書かれない。実務文では動作と判断が要る。

【対処】
原文と資料から分かる動作・判断を、文の働きに合う述語まで書く。
読点だけ消して同じ型を残さない。動作が原文から分からないなら述語を作らず、確かめる。
見出しなら「保存先の指定」のように、扱う話題が分かる短い語句にする。
```

### 装飾記号

```
【検出パターン】
- 絵文字
- ダッシュ「——」「―」で挟んだ挿入
- 文末や見出し直後の装飾としての全角コロン（「ポイントは以下：」）
- 同じ意味を繰り返すカッコ（「修正前のAI生成文（素の出力）」）

【なぜ問題か】
書式で強調しても内容は増えない。AI普及後の技術記事では、ダッシュや太字が目に見えて増えている。

【対処】
ダッシュは句読点や助詞でつなぐ。外して1文にすると前の理由や条件が後ろまで掛かるなら、2文に分ける。
装飾のコロンは句点で閉じるか、前置きごと削る。「日時：10時」のようなラベルと値の区切りは残す。
言い換えだけのカッコは削る。
英単語や数値の前後の空白は、原文の書式に合わせ、一律に足したり削ったりしない。
```

## 文末の立場と時制

| 立場 | 原文 | 直した文 | 理由 |
|---|---|---|---|
| 勧め | まずログを確認しておきます。次に設定を見直します。 | まずログを確認しましょう。次に設定を見直しましょう。 | 読み手への助言が、書き手の予定に読める |
| 決まり | 障害時は、まず当番に連絡しましょう。 | 障害時は、まず当番に連絡します。 | チームの運用ルールそのものを書いている |
| 説明（報告） | 認証方式を JWT に変更します。 | 認証方式を JWT に変更しました。 | 完了した変更が予定に読める。完了したと分かる場合だけ直す |
| 説明（現状） | 失敗時は3回まで再試行します。 | そのまま残す | システムの動作の説明。過去形にそろえない |
| 混在 | エラー処理を組み込みました。また、通信失敗時には自動で再試行が行われます。 | そのまま残す | 実施済みの事実と動作の説明を区別している。再試行も今回実装したとは決めない |

変更報告では、「どの設定・実装を、どう改めたか」を書き手の行為として述語まで書く。「指針を改定しました」と宣言した後に方針を並べるだけでは、何を変えたかが読めない。改定前の内容が分からないなら、比較や改善幅を作らない。

## 文体統一ルール

### です/ます調

丁寧で親しみやすい。ブログ、説明文、メール、カスタマー向け文書に適する。

```
文末: 「〜です」「〜ます」「〜でしょう」「〜しましょう」「〜ください」
```

### だ/である調

客観的で力強い。論文、報告書、技術文書、社内ドキュメントに適する。

```
文末: 「〜だ」「〜である」「〜となる」「〜といえる」「〜すべきだ」
```

### 混在を防ぐルール

1. 文書の最初の数文で使われている文体を基準とする
2. 引用文・会話文を除き、本文は一貫させる
3. 箇条書き内も本文と統一する
4. 見出しと本文で文体を変えない
5. 原文を校正する場合、原文の文体に合わせる
6. 文体をそろえても、文の働き（助言・決まり・予定・説明）は変えない

## Markdown の太字

日本語の Markdown では、`**` のすぐ内側が記号（「」（）、。やバッククォート）で、すぐ外側が文字のとき、太字にならず `**` がそのまま表示されることがある（CommonMark の delimiter run の規則による。実際の表示は処理系で異なる）。太字を残すなら、次の順で直す。

1. かっこごと太字にしているなら、かっこの内側だけを太字にする: `次に**「文書の立場」**を決めます。` → `次に「**文書の立場**」を決めます。`
2. 太字の終わりが句点なら、句点を外に出す: `これは**必須です。**詳しくは下に書きます。` → `これは**必須です**。詳しくは下に書きます。`
3. 1と2ができないなら、`**` の外側の文字に接する側に半角スペースを1つ入れる: `立場は**「勧め」か「決まり」**で決めます。` → `立場は **「勧め」か「決まり」** で決めます。`

太字そのものは減らす方向で扱う。技術記事なら1,000字あたり1〜2箇所が目安。

## 文書の種類ごとの注意

### 技術記事・設計文書

- 太字は論理の要所に絞る。箇条書きは並列が明確なものは残し、思考の流れを分断しているものだけ地の文にする
- 短い記事で、本文を繰り返すだけの「まとめ」見出しを置かない
- 「近年、AI技術の発展は目覚ましく」のような前置きを削り、解決したい課題や前提から始める
- 硬い漢語が続く箇所はふだんの動詞に直す（「整合性を担保する」→「矛盾が生じない状態を保つ」）。専門用語は分野で定着した語のまま使う
- 原文に無いコマンド・コード・原因・条件を足さない。「失敗時に値を代入しない」処理を「false を代入する」と書き換えるような、動作の改変をしない

### 業務文書（PR・仕様書・報告・提案）

- 受動態で主体がぼやけている箇所は、原文や資料から分かる場合だけ責任主体を書く（「開発チームで合意した」）。分からない担当者や役職を作らない
- 「適宜対応する」は、資料にエラーコードや再試行回数などの条件があるときだけ具体化する
- 議事録では、発言者・作業の実行者・担当を引き受けた人を区別する。書かれていない担当を割り当てず、「担当未定」とも書かない
- 依頼文は内容・条件・期限を保って語調を整える。期限を「都合がよければ」にしない

### エッセイ・個人発信

- 体験に無理な教訓をつけない。「美味しかった」「疲れた」といった素直な実感を残す
- 「深淵」「極致」のような熟語を平易にする（[CATALOG.md](CATALOG.md) 4節）
- 原文に無い五感の描写（冷房の温度、周囲の音）を足さない
- 出来事・観察・感情・推測の順と時制を保つ。後から分かったことを最初から知っていたことにしない
- 最後の段落で社会や未来への提言を無理に置かない
