# 既存の仕組みを説明すること

コードを変えずに、いま動いている形を読み手が歩ける説明にする。
ファイル一覧や推測の物語ではなく、入口から出口まで辿った記録を渡す。

## いつ効くか / いつ効かないか

効く: 既存サブシステムの流れ、置き場、所有、レイヤの問い。変更前のウォークスルー。

効かない:
- 何を解くか・何を作るか → `understand-problem`
- これから書く型と境界 → `design-code`
- なぜこう設計されたか（動機・捨てた案） → `evidence-discipline`
- 出荷前に何が壊れるか → `evidence-discipline`

依頼が「どう動くか」と「なぜそうなったか」の両方なら、先にこのスキルで仕組みを渡し、意図は `evidence-discipline` に委譲する。混ぜて書かない。

## 進め方

### 1. 対象を固定する

ユーザーが指しているものを一文で言い直す。曖昧なら、推奨する解釈を添えて **1問だけ** 聞く。推測で走らない。

観測で決まること（ファイルの場所、呼び出し関係）は聞かない。

### 2. 辿り方を決める

単一モジュール・狭い関数なら、自分で読む。

複数ファイルや横断機能なら、直交する 2〜4 スライスに分けて読み取り専用の委譲にする。スライスの例: データと状態 / リクエスト経路 / 設定と計測。同じファイルを全員に読ませない。委譲の設計は `delegation-discipline`。

迷ったら単独で辿る。壁に当たってから並列にする。

### 3. 入口から出口まで辿る

ファイル名から推測しない。実コードを読む。入力（または発火）から出力（または副作用）まで、飛ばした段が無いと言えるまで止める。

### 4. 説明を渡す

実装しない。提案やリファクタは求められない限り書かない。

## 渡すもの

質問に合わせて節を落とす。並べる順は変えない。

**概要。** 何であり、何をするか。読み続けるかを決める 1〜2 段落。

**重要概念。** 理解に要る型・サービス・抽象だけ。網羅しない。

**流れ。** 何が発火し、どこを通り、どこで分岐し、データがどこへ行くか。散文。参照はファイルと関数名。コードブロックは、その断片が無いと誤解するときだけ。

**置き場。** 作業を始めるのに要るディレクトリとファイル。全ファイル一覧にしない。

**つまずき。** 非自明なこと、歴史で歪んだ見た目、既知の鋭い角。

## サボった兆候

- ファイル一覧を貼って説明したつもりになっている
- 「おそらく」「ファイル名から見て」で流れを繋いでいる
- 呼び出し元の grep 結果だけを返している
- 対象が曖昧なまま読み始めた
- 説明の途中でコードを書き始めている

## 判定テスト

- 「入口から出口まで、飛ばした段を言えるか」— 言えるならまだ辿り切っていない
- 「ファイル名から推測した段はあるか」— あるならその段を読み直す
- 「ユーザーに聞いたのは、観測では決まらない一問か」
- 「コードを書いていないか」
- 「なぜこうなったかを、コード形状から書いていないか」— 書いていれば `evidence-discipline` の領分を侵している

## 参照

- 委譲と並列探索の設計 → `delegation-discipline`
- 意図の証拠と出荷前の安全事実 → `evidence-discipline`
- 問題定義 → `understand-problem`
- 実装前の構造決定 → `design-code`
