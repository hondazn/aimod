# コードを設計すること

## このスキルの目的

実装に手を付ける前に、コードの構造を決める段階である。
「何を解くか」は understand-problem が、「どう解くか」の戦略は devise-plan が担う。
このスキルは **「その戦略をコードでどう表現するか」** — 型・インターフェース・モジュール・
データフロー・状態・エラーの設計判断を導き出す。

ゴールは「完璧な設計図」ではなく、**実装者が迷わず書き始められる設計判断の集合**を得ること。
コードは書かない。疑似コードやシグネチャのスケッチは使うが、動くコードは書かない。
「正しい設計」は存在しない。トレードオフを明示し、選んだ理由を説明する。

---

## 前提

問題定義（何を解くか）、あれば解法戦略（devise-plan の出力）がすでにある状態を想定する。
問題定義がなければ、まず問題を簡潔に整理してからこのスキルに入る。
戦略が未定でも問題定義から直接コード設計に入ってよいが、戦略レベルの迷いが残っているなら先に `/devise-plan` を使う。

---

## 進め方

### 1. 設計の出発点を決める

コードベースを調査し、設計の出発点を据える。

- **既存コードの構造を読む** — 対象領域の現在のモジュール構成・命名規則・抽象化パターンを把握する。新しい設計はこの地続きに置かれるべきで、既存の慣例を無視した設計は統合時に摩擦を生む。サブシステム全体の流れが要るなら `explain-system`。
- **変更が触れる現物を読む** — 既存資産への遡及変更では、対象の実装・スタイル・実行環境を読んでから設計を決める。設計が参照する既存データ（台帳・設定・履歴・命名）も、スキーマの想定ではなく現物を読む。長く運用されたデータには世代差（旧命名規則・欠損フィールド・手動修正の痕跡）があり、想定だけで書いた処理は最初の1件で壊れる。
- **変更の影響範囲を見積もる** — 変更が触れるファイル・モジュール・レイヤーの広がりを把握する。影響範囲が設計判断の重みを決める。出荷前に何が壊れるかの証明は `evidence-discipline`。
- **先例の無い一方向は2案から選ぶ** — 境界・公開 API・新規のインタラクションで、コードベースに先例が無く、1つの形が後から覆しにくいなら、構造の異なるスケッチを2つ書いて並べてから選ぶ。同じ形の言い換えは2案に数えない。機械的な実装や、制約が1案に決めるときは書かない。実装の bake-off が要るなら `delegation-discipline`。

### 2. 5つの設計観点で判断を導く

以下の観点から状況に合うものを選び、**1つずつ**ユーザーと探索する。
各判断について推奨案を添え、ユーザーが accept / modify / reject できるようにする。
コードベースの既存パターンを調べれば判断できるものは、自分で調査して推奨案に反映する。

#### (1) 境界と責務 — どこで切るか

モジュール・関数・クラスの境界をどこに引くか。
各部品が何に責任を持ち、何に責任を持たないか。

考えるべきこと [design-principles §1, §2]:
- 変更理由が異なるものは分ける（単一責任）
- 実行順で切らない
- 外部依存（DB・API・ファイルシステム）との接触面を薄く保つ
- 「この部品だけ差し替えたい」と思う箇所が境界の候補

#### (2) 型とインターフェース — コントラクトをどう定める

モジュール間の境界で交わすデータの形を決める。
入力・出力の型を厳密に定義することで、実装の自由度を内側に閉じ込める。

考えるべきこと [coding-standards「カプセル化とAPI設計」]:
- 不変条件を型で表現できないか（不正な状態を構築不能にする）
- `string` や `any` で逃げている箇所を特定し、専用の型を検討する
- エラーを型で表現するか例外で表現するかの方針

#### (3) データフロー — データがどう流れるか

入力から出力まで、データがどのモジュールをどの順で通過するかを描く。
変換・合流・分岐のポイントを明確にする。

考えるべきこと [coding-standards「関数型コアと命令型シェル」「CQS」]:
- 同じデータを複数箇所で取得していないか（単一の情報源）
- 変換は何段あるか、各段の入出力は何か
- 外部からの入力はどこでバリデーション・正規化するか

#### (4) 状態管理 — 何が変わり、誰がそれを知るか

可変状態の所在と、その状態を変更・参照するアクターを明確にする。
状態が少ないほど設計は単純になる。

考えるべきこと [coding-standards「関数型コアと命令型シェル」]:
- 状態を持つ必要が本当にあるか（導出可能な値は状態にしない）
- 状態の所有者は誰か、変更権限は誰にあるか
- 状態遷移のパターンは有限か（状態マシンで表現できないか）

#### (5) エラーと回復 — 失敗をどう扱うか

正常系だけでなく、失敗が起きる場所・失敗の伝播経路・回復の方針を決める。

考えるべきこと [ddd-modeling references/communication.md]:
- 実行する全ての外部コマンド・副作用（プロセス起動、git 操作、ネットワーク、ファイル書込）について「失敗したら何が起きるか」を悉皆で設計に含める。成功経路だけの設計は、失敗の黙殺（exit code 無視・例外の握り潰し）として実装に現れる
- 各失敗に fail-open / fail-closed のどちらを選ぶかは、守るべきもの（成果物の品質か、処理の継続か）から導き、理由を書く
- 回復可能なエラーと回復不能なエラーを区別する
- エラーはどこでハンドリングするか（発生点か、呼び出し元か、最上位か）
- 部分的な失敗が起きたとき、全体の整合性をどう保つか
- 再実行しても安全か（冪等性）— リトライ・重複実行・途中失敗からの再開を前提に設計する

### 3. 設計判断を検証する

設計判断の検証には `design-principles` と `coding-standards` のチェックリストを活用する。
ただし「整理・リファクタリング」系の項目は既存コードの存在が前提なので、
設計段階では結合・認知負荷・ドメイン整合の観点を使う。
特に以下を確認する:

- **結合の均衡** — 統合強度・距離・変動性の3次元で評価し、「複雑性 × 高変動性」の組を避ける [design-principles §1]
- **認知負荷** — この責務分割なら、実装時に 循環的複雑度7・変数7 の閾値に収まる見込みがあるか [coding-standards「認知負荷の閾値」]
- **ドメイン整合** — サブドメイン種別に対して適切な実装パターンを選んでいるか [ddd-modeling references/logic-patterns.md]
- **既存コードとの一貫性** — プロジェクトの慣例から逸脱していないか。逸脱するなら、その理由は明確か
- **新規に発する文字列・フォーマットの突合** — 設計が新設する文字列（ログ・判定行・イベント名など）を既存の分類器・パーサ・正規表現が処理する場合、机上で一致を確認したか。不一致なら消費側の変更も設計に含める
- **YAGNI** — 今必要でない抽象化や拡張ポイントを入れていないか
- **テスト容易性** — この設計でユニットテストは書けるか。テストが難しい箇所は設計の歪みを示唆している

### 4. 設計をまとめる

対話で得られた設計判断を整理して提示する。含める要素と雛形は `references/output-template.md` にある。境界と責務・型とコントラクト・データフロー・状態管理・エラー方針・既存コードとの整合・検討した代替案・未決事項の8つを埋める。

---

## 判定テスト

- 「この設計でユニットテストが書けるか」— 書けないなら設計の歪みを示している
- 「実行する外部コマンド・副作用のそれぞれについて、失敗したら何が起きるか書いたか」— 成功経路だけの設計になっていないか
- 「今必要でない抽象化や拡張ポイントを入れていないか」
- 「設計が新設する文字列・フォーマットを、既存の消費側が処理できるか確認したか」
- 「一方向で先例が無い形に、構造の異なる2案を並べたか」— 並べていないなら、1案で固定していないか

## 参照スキル

- **`design-principles`** — 結合・凝集・モジュール性・構造投資の経済学。境界と分割の判断理論
- **`coding-standards`** — 認知負荷の閾値・CQS・カプセル化など、実装規律とチェックリスト

- **`ddd-discovery` / `ddd-modeling`** — ドメイン境界・実装パターン選択・通信パターンの詳細

## 次のステップ

設計がまとまったら、状況に応じて次のスキルへ引き継ぐ:

- **重要な設計判断を記録に残す** → `create-issue` があればそれを使う。無ければ `gh issue create`
- **実装に着手** → 完了後はコミットし、必要なら PR を作る。`git-commit` / `create-pr` があればそれを使い、無ければ `git commit` / `gh pr create`
