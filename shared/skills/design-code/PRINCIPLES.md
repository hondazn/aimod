## 1. 結合 — ソフトウェアのコストを支配する力

> **cost(ソフトウェア) ≈ cost(変更) ≈ cost(大きな変更) ≈ 結合** — コンスタンチンの等価性 [TF]

### 1.1 結合の定義

- **結合 = 知識の共有 + ライフサイクルの共有** [BC]。境界を越えて共有する知識が多く暗黙的なほど、些細な変更がシステム全体へ波及する。
- 結合は変更の種類（Δ）に対して定義される。「何に対して結合しているか」を言わなければ意味がない [TF]。
- 結合は悪ではなくシステムを成立させる接着剤。問題は「本質的結合か偶有的結合か」「バランスが取れているか」[BC]。

### 1.2 結合の3次元モデル [BC]

| 次元 | 意味 | 評価 |
|------|------|------|
| **統合強度** | 共有知識の量・暗黙度 | コントラクト(弱) → モデル → 機能 → 侵入(強) |
| **距離** | 変更を実装する空間的コスト | 同一メソッド(近) → 同一クラス → 別パッケージ → 別サービス → 別システム(遠) |
| **変動性** | 変更の発生頻度 | 汎用/支援(低) → コア(高) |

**均衡結合モデル（本書の集大成式）**:
- 強度が高いなら距離を近く、低いなら遠くする
- 変動しないものとは多少強く結合してもよい
- **避けるべきは「複雑性（高強度×遠距離 or 低強度×近距離）× 高変動性」の組だけ**
- メンテの痛み = 強度 × 距離 × 変動性 — どれか1つを最小化すれば相殺できる

### 1.3 統合強度の4段階 [BC]

| レベル | 説明 | 例 |
|--------|------|-----|
| **侵入結合** | 非公開メンバー・他サービスDBへ直接アクセス | リフレクション、他サービスのDBクエリ |
| **機能結合** | ビジネスロジック・不変条件が相互関連 | ルール重複（DRY違反＝対称機能結合） |
| **モデル結合** | 同じドメインデータモデルを共有 | 内部モデルをそのまま公開 |
| **コントラクト結合** | 統合専用モデル（DTO/契約）で通信 | 公開APIスキーマ |

### 1.4 コナーセンス [BC]

結合の微視的評価。強い順に:
- **動的**: 同一性 > 値 > タイミング > 実行順序
- **静的**: 位置 > アルゴリズム > 意味（マジックナンバー）> 型 > 名前

原則: **下げられるなら下げ、下げられないなら近くに置く**。

### 1.5 結合と凝集 [TF]

- **凝集**: 一緒に変わる要素を同じ場所に集め、一緒に変わらない要素を別の場所に移す。
- **カスケード結合**: 1つの変更がさらに変更を呼び連鎖的に波及する。コストの大半はここから生じる。
- **結合 vs 分離のトレードオフ**: 分離にもコストがある。触れない部分は無理に分離しない。

## 2. モジュール性 — 複雑性の制御

### 2.1 モジュールの設計原則

- **深いモジュールを作る** [BC] — 公開インターフェースに対し実装の比率が高いほど良い。IFを読むのと実装を読むのに差がなければ浅すぎる。
- **変わりうる決定を隠蔽する（情報隠蔽）** [BC] — 変更されうる決定を1モジュールに閉じ込め、再検討時にそのモジュールだけが影響を受けるようにする。
- **フラクタルアーキテクチャ** [CFH][BC] — 良いコードはどのズームレベルでも自己相似で、各レベルが独立して「頭に収まる」。均衡結合モデルも全スケールで再帰適用する。

### 2.2 認知負荷の制約 [CFH]

すべての判断基準は **「人間のワーキングメモリ ≒ 7±2 チャンク」** という制約に帰着する。

| メトリクス | 閾値 | 根拠 |
|------------|------|------|
| コードブロックサイズ | 横80文字 × 縦24行 | VT100由来、「頭に収まる」サイズ |
| 循環的複雑度 | 7以下 | 分岐数。8に達したらリファクタリングのトリガー |
| 変数の数 | 7個以下 | ローカル変数＋引数の合計 |

### 2.3 境界と責務の設計

- **変更理由が異なるものは分ける（単一責任）** — 無関係な機能の同居はライフサイクル結合を生み付随的変更を強いる [BC]。
- **外部依存との接触面を薄く保つ** — DB・API・ファイルシステムとの接点をポート/アダプターで分離する [CFH]。
- **制約で自由度を減らす** [BC] — 無効な状態を表現可能にしない。不変条件はコンストラクタ/メソッドで強制する。

## 3. ドメイン駆動設計 — ビジネスから設計を導く

### 3.1 戦略的設計

**サブドメインの3分類と投資レベル [DDD]**:

| 種別 | 特徴 | 実装方針 | 変動性 [BC] |
|------|------|----------|-------------|
| **コア** | 競争優位の源泉、複雑、頻繁に変化 | 最良の人材で内製、高度なパターン | 高 |
| **汎用** | 複雑だが解決済み（認証・決済等） | 既製品を購入・採用 | 低 |
| **補完** | 単純、差別化を生まない | 単純に作る（CRUD等） | 低 |

**ユビキタス言語 [DDD]**:
- ドメインエキスパートと開発者が全員で共有する単一の言語を、会話・ドキュメント・コード・テストすべてで使う。
- 一語一義の徹底: 同義語禁止・多義語禁止。曖昧さは別コンテキストに分離する。
- モデルは現実のコピーではなく特定の問題を解くための単純化・抽象。

**境界づけられたコンテキスト [DDD]**:
- ユビキタス言語が一貫していられる最大の範囲がコンテキスト境界。
- サブドメインは「発見」するもの（問題空間）、コンテキストは「設計」するもの（解決空間）。両者は1:1とは限らない。
- 1コンテキストは1チームが所有（複数チームで共有しない）。

**コンテキストマップ [DDD]**:

| パターン | 関係性 | 用途 |
|----------|--------|------|
| パートナーシップ | 協力・双方向 | ゴールが一致するチーム間 |
| 共有カーネル | 協力・共同所有 | 重複コスト > 分割コストの最小範囲に限定 |
| 順応者 | 顧客-供給者 | 上流に交渉力がない場合 |
| 腐敗防止層 (ACL) | 顧客-供給者 | 外部/レガシーから自分を守る |
| 公開ホストサービス (OHS) | 顧客-供給者 | 消費者を内部変更から守る |
| 別々の道 | 非統合 | 統合コストが見合わない場合 |

### 3.2 戦術的設計

**実装パターンの選択基準 [DDD]**（上から順に判定）:

1. 監査証跡が必要 かつ 複雑 → **イベントソーシング式ドメインモデル**
2. ビジネスロジックが複雑（不変条件・ルールが多い） → **ドメインモデル**
3. ロジック単純だがデータ構造が複雑 → **アクティブレコード**
4. 単純なCRUD → **トランザクションスクリプト**

**ドメインモデルの構成部品 [DDD]**:

- **値オブジェクト**: 値で識別、不変、IDなし。プリミティブ強迫を排除する。
- **エンティティ**: IDで識別、状態が変わってもID不変。
- **集約**: エンティティ/値オブジェクトの集まりで整合性の境界。
  - 集約ルートが唯一の入口。外部からの参照はルートのみ。
  - 状態変更は集約の公開メソッド（コマンド）経由のみ。
  - ビジネスルール（不変条件）を全受信コマンドで検証して守る。
  - 1トランザクションで変更するのは1集約のみ。
  - 集約は小さく保つ。他集約はIDで参照する。

**アーキテクチャの対応 [DDD]**:

| 実装パターン | アーキテクチャ | テスト戦略 |
|-------------|---------------|-----------|
| トランザクションスクリプト | レイヤード | 逆ピラミッド（E2E中心） |
| アクティブレコード | レイヤード | ダイヤモンド（統合テスト中心） |
| ドメインモデル | ポート&アダプター | ピラミッド（単体テスト中心） |
| イベントソーシング | CQRS | ピラミッド |

### 3.3 通信パターン [DDD]

- **アウトボックスパターン**: DB変更と同一トランザクションでイベントをoutboxに保存し、リレーが後で発行。二重書き込み問題を解決。
- **サーガ**: 複数集約/コンテキストにまたがる長期プロセスをイベント＋コマンドで調整。失敗時の補償アクションを持つ。
- **冪等性**: at-least-once配信を前提に、消費側は冪等に設計する。
- **内部イベントの非公開**: 内部ドメインイベントを外部にそのまま公開しない。公開用イベントを別途設計する。

## 4. アーキテクチャと構造の原則

### 4.1 関数型コアと命令型シェル [CFH]

副作用・I/Oを最外周（シェル）に押し出し、中心（コア）を純粋関数＝参照透明に保つ。

- 同じ入力には常に同じ出力を返し、観測可能な副作用を持たない関数。
- コアがテスト容易・推論容易になり、変数（状態）の数が減る。

### 4.2 コマンドクエリ分離 [CFH]

- **コマンド**: 副作用を持ち void を返す。
- **クエリ**: データを返し副作用を持たない。
- 両方を兼ねるメソッドを作らない。呼び出し側の推論コストが下がる。

### 4.3 カプセル化とAPI設計 [CFH]

- **検証せずにパースする (Parse, don't validate)** — 入力を一度パースして「不正な状態を表現できない型」へ変換し、以降は再検証不要にする。
- **ポカヨケ** — 誤用を物理的に不可能（またはコンパイルエラー）にするAPI設計。
- **名前を外側から付ける** — メソッド・APIの名前は呼び出し側（利用者）の視点で付ける。
- **コミュニケーション階層** — 意図の伝達手段を価値の高い順に: ① 良いAPI（型） → ② 分かりやすいメソッド名 → ③ 良いコメント → ④ 自動テスト → ⑤ Gitコミットメッセージ → ⑥ ドキュメント。
- **デメテルの法則** — 内部のさらに内部（孫オブジェクト）へ手を伸ばさない。

### 4.4 横断的関心事 [CFH]

- ロギング・計測・キャッシュなどはビジネスロジックに混ぜず、デコレーターで包む。
- ストラングラーパターンで段階的に置き換える（ビッグバン書き換えを避ける）。

## 5. コード整理 — 構造と振る舞いの分離 [TF]

### 5.1 根本原理

- **構造の変更（整理）と振る舞いの変更を同じコミット/PRに混ぜない。**
- 整理はリファクタリングのサブセットで、(1)小さく、(2)可逆、(3)中断可能。
- 設計の根底は経済学: 今日の1ドルは明日の1ドルより価値がある（→あとに整理）、不確実性が高いほどオプション価値が高い（→先に整理）。

### 5.2 整理テクニック（15のミニリファクタリング）

| テクニック | 内容 |
|-----------|------|
| ガード節 | ネストした if を早期 return に平坦化 |
| デッドコード | 使われないコードは消す（Git で戻せる） |
| シンメトリー | 同じことをするコードは同じ書き方に統一 |
| 新IF・旧実装 | 欲しいインターフェースを先に作り古い実装を包む |
| 読む順番 | 読み手が理解しやすい順に並べ替え |
| 凝集の順番 | 一緒に変更する要素を物理的に近づける |
| 宣言と初期化を近接 | 使う直前で宣言・初期化 |
| 説明変数 | 複雑な式の一部を意図が分かる名前の変数に抽出 |
| 説明定数 | マジックナンバーをシンボリック定数に。ただし意味の違う同値を共通化しない |
| 明示パラメーター | マップ一括渡しをやめ必要なデータを明示的引数で |
| ステートメント小分け | 意味単位で空行等に分ける |
| ヘルパー抽出 | まとまりのあるコードブロックを名前付きルーチンに |
| ひとかたまり | 過剰抽象をインライン化して大きな塊に戻してから再整理 |
| 説明コメント | コードから読み取れない「なぜ」だけを書く |
| ガラクタ削除 | コードと同じことを言うだけのコメントを消す |

### 5.3 整理のタイミング判断

- **先に整理**: 整理すると今からの作業が単純になり、すぐ見返りがある時。`cost(整理) + cost(変更) < cost(変更)` が成り立つなら。
- **あとに整理**: 今すぐの振る舞い変更を優先。時間価値が支持する。
- **改めて整理**: 大きな塊を小出しに。
- **整理しない**: 二度と触れないコードのみ（ほぼ無い）。

## 6. テストと開発プロセス

### 6.1 テスト駆動開発 [CFH]

- **Red → Green → Refactoring**: 失敗するテストを書く → 最小実装で通す → 重複除去・設計整理。
- テストが書きにくいなら設計が悪いというフィードバック（テストの声を聞く）。
- テストとプロダクションコードは別々にリファクタリングする。

### 6.2 テスト設計 [CFH]

- **Arrange-Act-Assert**: テストを「準備→実行→検証」の3フェーズで構造化。
- **バグは必ずテストで再現してから修正する。**
- **悪魔の代弁者**: 意図的に間違った実装でテストを通そうと試み、通せたらテスト不十分。

### 6.3 テスト戦略の選択 [DDD]

実装パターンに応じてピラミッドの形を変える:
- ドメインモデル → テストピラミッド（単体テスト中心）
- アクティブレコード → テストダイヤモンド（統合テスト中心）
- トランザクションスクリプト → 逆ピラミッド（E2E/統合中心）

### 6.4 バーティカルスライス [CFH]

- 水平層でなく、入力から永続化まで貫く最小の縦切りで実装する。
- 最初にウォーキングスケルトン（アーキテクチャ全体を貫く最薄のend-to-end）を通す。
- アウトサイドイン開発: 境界（HTTP等）から始めて内側（ドメイン）へ進める。

### 6.5 コミットとPR [CFH][TF]

- **50/72ルール** [CFH]: コミットメッセージのサマリーは50字以内、本文は72字折り返し。「なぜ」を書く。
- **構造と振る舞いを別PRに** [TF]: 整理PRと機能PRを分ける。
- **バッチは小さく** [TF]: 大バッチは衝突・マージコストが指数的に増加。

## 7. トラブルシューティング [CFH]

- **科学的手法**: 仮説を立て、実験（再現）で検証する。推測で直さない。
- **二分法 / git bisect**: コードや履歴を半分に割り続けて欠陥を特定。
- **ラバーダッキング**: 問題を声に出して説明することで自分で気づく。
- **STRIDE脅威モデル**: Spoofing / Tampering / Repudiation / Information disclosure / Denial of service / Elevation of privilege。

## 8. 進化と再均衡化

### 8.1 設計の進化 [DDD][BC]

- サブドメイン種別の遷移に合わせて実装パターンを段階的に昇格/降格する。
- 最初から完璧な境界を引こうとせず、理解の深化に合わせて再分割する。
- まず広めの境界（モノリス）から始め、理解が深まってから分割する。

### 8.2 均衡の再調整 [BC]

崩れの要因と対処:

| 崩れ | 対処 |
|------|------|
| 統合強度が増加 | 距離を縮める or 強度をリファクタで戻す |
| 上流の変動性が増加 | 距離を縮める or 強度を下げる |
| 距離が増加（分解・組織変更） | 強度を下げる（モデル結合→コントラクト結合） |

再均衡で解けないときは新しい抽象を導入する（フラクタル）。

### 8.3 構造変更の経済学 [TF]

- 構造変更は可逆性が高いのでデメリットが少なく、判断のほとんどは「やる」側に倒れる。
- **オプショナリティ**: 不確実性が高いほどオプション（将来の選択肢）の価値が高い。良い設計＝振る舞いを足すたびに次のオプションが増える状態。

## 9. アンチパターン集

### 結合・モジュール性 [BC][TF]

- **侵入結合**: 非公開メンバーへのリフレクション、他サービスDBへの直接アクセス
- **ロジックの重複（DRY違反）**: 同一ルールを複数箇所に実装し同期漏れで矛盾
- **内部モデルの鏡写しDTO**: 知識を隠さない浅い統合モデル
- **「メッセージング＝疎結合」幻想**: モデル結合のまま非同期化しても疎結合にならない
- **大域的複雑性だけの最適化**: 全部を1モノリスに統合
- **局所的複雑性だけの最適化**: 機械的に細分化し分散した泥団子に
- **無関係機能の同居**: 1クラスに通知・支払い・単位変換が混在

### DDD [DDD]

- **貧血ドメインモデル**: データだけのオブジェクト＋外部の手続きにロジックが散る
- **プリミティブ強迫**: 金額・電話番号をintやstringの生値で扱う
- **万能・巨大モデル**: 1つのモデルで全業務を表そうとする
- **過大/過小な集約**: 大きすぎ（競合・性能劣化）／小さすぎ（不変条件を守れない）
- **二重書き込み**: DB＋メッセージバスを別々に書く（→アウトボックスで解決）
- **分散モノリス**: 境界が細かすぎて密結合な分散システムに

### コード品質 [CFH][TF]

- **長いメソッド・大きなコードブロック**: 80/24・複雑度7・変数7のいずれかを超過
- **コマンドとクエリを兼ねるメソッド**: 副作用の有無が不明
- **繰り返しのバリデーション**: 至る所で同じ妥当性チェック（→Parse, don't validate）
- **ビジネスロジックに混入した横断的関心事**: ロギング等の直書き
- **テストと本番コードの同時リファクタリング**: 安全網が消える
- **推測でのデバッグ**: 再現テストなしに原因を当て推量で修正
- **振る舞い変更と構造変更の混在**: 同一コミット/PRに混ぜる

## 10. 統合チェックリスト

### 結合・モジュール性

- [ ] 公開している知識は利用者に必要な最小限か？ 実装詳細を漏らしていないか？
- [ ] この結合は本質的か偶有的（消せる）か区別したか？
- [ ] 統合は公開インターフェイス経由か？ 侵入結合はないか？
- [ ] 共有しているのはデータだけか、振る舞いまで共有していないか？
- [ ] 同一ロジックを複数箇所に実装していないか（DRY違反）？
- [ ] 強い結合は近距離、弱い結合は遠距離になっているか？
- [ ] コア（高変動）の境界で共有知識を最小化しているか？
- [ ] 非同期化の前にコントラクト結合になっているか？

### 認知負荷・コード構造

- [ ] メソッド/ブロックは80×24に収まっているか？
- [ ] 循環的複雑度は7以下か？
- [ ] 変数（ローカル＋引数）は7個以下か？
- [ ] 各メソッドはコマンドかクエリの一方か？
- [ ] 不変条件はカプセル化で保護されているか？ 不正な状態を作れないか？
- [ ] 入力はパースで型に押し込めているか（Parse, don't validate）？
- [ ] 名前は利用者視点で付けられているか？
- [ ] 副作用は外周に押し出され、コアは参照透明か？

### DDD・ドメイン設計

- [ ] サブドメイン種別（Core/Supporting/Generic）と投資レベルが整合しているか？
- [ ] 同じ用語が複数の意味を持つのに同一コンテキストに同居していないか？
- [ ] 実装パターンの選択がロジックの複雑さに沿っているか？
- [ ] 集約ルートが唯一の入口で、状態変更がコマンド経由のみか？
- [ ] 1トランザクションで変更する集約は1つか？
- [ ] イベント消費は冪等か？

### 整理・リファクタリング

- [ ] 振る舞いの変更と構造の変更が同じコミット/PRに混在していないか？
- [ ] 各整理は可逆で中断可能なスライスになっているか？
- [ ] `cost(整理)+cost(変更) < cost(変更)` が成り立つと言えるか？
- [ ] 過剰抽象で逆に読みにくくなっていないか？
- [ ] デッドコード・冗長コメントは残っていないか？

### テスト・プロセス

- [ ] テストとプロダクションコードを別々にリファクタリングしているか？
- [ ] バグは再現テストを書いてから修正したか？
- [ ] テスト戦略の形が実装パターンに合っているか？
- [ ] コミットは小さく、メッセージは「なぜ」を説明しているか？
