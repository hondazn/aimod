# 計画を立てること

## このスキルの目的

問題を理解した後、解法の着想を得て実行可能な計画に落とし込む段階である。このスキルのゴールは「最善の設計」ではなく「実行に移せる筋の通った計画」を得ること。

---

## 前提

問題定義（未知のもの・与えられているもの・条件）がすでにある状態を想定する。なければ、まず問題定義を簡潔に整理してからこのスキルに入る。

---

## 進め方

### 1. 5つの戦略で解法の着想を得る

以下の戦略から状況に合うものを選び、**1つずつ**ユーザーと探索する。各戦略について推奨案を添え、ユーザーが accept/modify/reject できるようにする。**聞く前に分類する。** 観測すれば答えが出る問い（既存実装の形・所要時間・性能・ライブラリの挙動）はユーザーのものではない。最小の実測で答えを出し、結果を提示する。可逆な実行の許可は問わない。ユーザーに問うのは実験では決まらない選好 — どこまでやるか、何を捨てるか、どちらの体験を選ぶか— と、不可逆な操作だけにする。

#### (1) 類似問題への帰着

同じ「未知のもの」を持つ既知の問題に帰着できないか探す。— コードベース内の類似実装、チームが過去に解いた問題、既知のデザインパターン、ライブラリが提供する解法。

#### (2) 補助問題の導入

元の問題が直接解けないとき、より簡単な関連問題をまず解く。— 条件の一部を外した簡易版、一つのケースだけ扱うプロトタイプ、ハードコードで動く最小版。

#### (3) 逆向きに考える

望む結果から逆算して、必要なステップを導き出す。— 最終的な API の形から内部設計を逆算、テストを先に書いて実装を導く（TDD）、ユーザー操作から必要な状態遷移を逆引き。

#### (4) 問題を変形する

問題を別の形に言い換えることで、解法が見えることがある。— 抽象度を上げる（一般化）、具体例に落とす（特殊化）、等価な別の問題に変換する、制約を緩めて上界を見る。

#### (5) 分割して征服する

問題を独立した部分問題に分解し、それぞれに解法を割り当てる。— レイヤー分割、フェーズ分割（段階的リリース）、関心の分離、依存関係の少ない順に並べる。

### 2. 計画を整理する

対話で得られた戦略と判断を、問題の性質に合った形で整理する。形式は問わないが、以下の要素を含める:

- **意図** — 誰が・どんな場面で・なぜ使うか。依頼に明示があれば転記して「（明示）」、なければ推定して「（推定）」と付記する。条件を満たしつつ意図から逸れる実装を、後段のレビューで検出可能にする
- **仮説（採用した戦略と理由）** — この解き方で解けるはずだという見立てと、なぜそれを選んだか
- **スコープ** — 触るもの・触らないもの。触るものには本体だけでなく、変更が壊す既存テストや追随が要るスタブ・検証を含める
- **ステップと順序の根拠** — 何をどの順でやるか、なぜその順序か。各ステップは、実行者が次に打つコマンドか開くファイルを迷わない粒度で書く。実行者（エージェント・人）が暗黙の工程（push・認証・後片付け）を知らない前提で書き、最後のステップは「作業が外から見える状態」（push 済み・デプロイ済み・報告済み）に到達させる
- **受け入れ条件（判定器）** — 各条件は「何を測って、どの値なら合格か」の 1 行で書く。数値にできない条件は、欠陥を注入して落ちることを確かめる手順を条件そのものに書く。「〜に相当する記述があること」のような含みのある表現を残すと、実行者が文言を推測して判定器を書き、判定がその推測に依存する。「崩れていない」「はみ出していない」のような目視項目のうち、二値で判定できる性質（あふれ・重なり・要素の有無・順序）は測定値の比較に置き換え、主観に残すのは選好（好み・美しさ）だけにする。散文の成果物では、**禁止**（「〜と書いてはいけない」）を手書きの文言リテラルで照合しない。書き手が言い換えた瞬間に空振りする。構造マーカー（見出し・箇条書きの行頭・識別子）か、複数の語の共起で見る。逆に**要求**（「〜と書け」）は逐語で指定する
- **不確実性（未確認）** — わかっていないこと、検証が必要なこと。依頼・実測から導けず自分の判断で置いた完了条件には「（推定）」を付け、それを確かめる問いをここに書く

### 3. 計画に書いたことを実走する

計画は仮説であり、机上で読み返しても正しさは増えない。渡す前に、手を動かして確かめられるものはすべて確かめる。

- **手順として書いたコマンドをすべて一度実行する。** 完了条件に使う検証コマンド（型検査・テスト等）に限らない。構文が通ることと実行できることは別で、未実走のコマンドは実行者のところで初めて落ちる。実走できないものは「未検証」と明示する。不可逆な操作（push・デプロイ・外部への送信・削除）は本番に対して実走せず、dry-run か使い捨ての対象で通し、それもできなければ「未検証」とする
- **受け入れ条件の現在値を測って書く。** 「今 N、完了時に M」の形にすると、実行者の合格の主張と事実が食い違ったときに分かる。検証コマンドが現状で通らないなら、既存問題の扱い（スコープ追加 or 条件の限定）を計画に明記する
- **条件の否定形を 1 つ作って落とす。** 満たしていない成果物を使い捨てコピーか一時ディレクトリに 1 つ用意し、書いたコマンドがそれを落とすことを確かめる。作業ツリーには残さない。落とせない条件は判定器になっていない

---

## 判定テスト

- 「計画に書いたコマンドをすべて実走したか」— 未実走のものを「未検証」と明示したか
- 「問題定義の条件をすべて使ったか」— 使っていない条件があるなら、計画か条件のどちらかが間違っている
- 「最後のステップは、作業が外から見える状態に到達しているか」— push 済み・報告済みまで書けているか
- 「目視・主観の完了条件が残っていないか」— 二値で判定できる性質は測定値の比較に置き換えたか
- 「受け入れ条件の現在値と、否定形を落とした結果を書いたか」— 測っていない条件は、判定器が動くか未確認のまま渡している

## 次のステップ

計画がまとまったら、状況に応じて次のスキルへ引き継ぐ:

- **各単位を書く直前に、その単位の境界・型・データフローを決める** → `/design-code`（単位ごとに。タスク全体の設計文書はまとめない）
- **計画を Issue として記録する** → `create-issue` があればそれを使う。無ければ `gh issue create`
- **実装に着手** → 完了後はコミットし、必要なら PR を作る。`git-commit` / `create-pr` があればそれを使い、無ければ `git commit` / `gh pr create`
