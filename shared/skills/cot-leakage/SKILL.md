# CoT 漏れの除去

推論の過程が成果物に混ざる。設計セッションで振った decision 番号、変更の物語、去ったレビュアーへの弁明、制御フローの逐次説明。書いた本人には読めるが、HEAD の読者には解決できない。その混入を見つけ、事実を残して言い換える。

## 中心の1問

**HEAD の読者が、セッション記録・PR スレッド・未コミット草案のどれにもアクセスせず、全ての参照を解決し全ての主張を検証できるか。**

できないなら、生き残る事実をリポジトリの視点で言い換えてから残りを消す。できるなら漏れではない。ただし **resolvability だけではこのスキルの基準を満たすに過ぎない**。README・docs・JSDoc のような現状面では、解決可能な変更の物語も依然として漏れである（分類 3）。

## いつ効くか / いつ効かないか

効く: PR 本文、レビューコメント、SKILL.md、README、設計文書、コードコメント、コミットメッセージ — 後から単独で読まれる保存物を書く・直す・監査するとき。「セッションの話が混ざっている」「(decision 7) って何」「この文章は HEAD だけで読めるか」と言われたとき。

効かない:
- 冗長の最終削り → `less-is-more`
- AI 臭・著者の声 → `natural-writing`
- 文書の型・論証・読み手の負荷 → `technical-writing`
- コード内コメントの置き場と量 → `coding-standards`
- 主張の裏取りと証拠の強度 → `evidence-discipline`

## 8分類

| # | 分類 | 典型形 | 処置 |
|---|---|---|---|
| 1 | 死んだ設計セッション参照 | `(decision 7)`, `(audit C2)`, `plan §1.4`, `T4`, `P-I`, 「設計台帳」 | コミット済みの所有者がいるなら名前とパスで引用。いなければ引用を消し、事実節を自立させる |
| 2 | スタック・PR 視点 | 「このスタックの後続 PR」「本 PR で追加」「前のコミット」 | 出荷済みの機構か拡張点を現在形で書く。先送りは `TODO(name):` か issue 参照へ |
| 3 | 変更の物語と版スタンプ | `used to`, `no longer`, 「以前は」「旧 X」, `v1`, `this cut`, `today`, 「今は」 | 現在の挙動を書く。修正済みの回帰は現在形の反実仮想にする |
| 4 | レビューの振り付け | 「レビューで却下」「レビュアーが確認した」「本ノート v5」 | 残った決定と根拠を事実として書く。誰がいつ言ったかを消す |
| 5 | レビュアー宛ての自己弁護 | 「この cast は安全である。単に…」「〜だから正しい」 | コードを安全にしている不変条件を書く。コードが示しているなら削除する |
| 6 | 復唱・導出の実況 | 「まず X し、次に Y する」、テストの逐次説明 | 削除する。自明でない契約か不変条件だけ残す |
| 7 | ヘッジと計画の残骸 | 「とりあえず大丈夫だろう」「今のところ十分」「〜のはず」 | `TODO`/`FIXME` へ昇格するか実際の上限を書く。ヘッジは消す |
| 8 | 執筆言語の混入 | 日本語文中に残った未翻訳の英語説明、セッション区切り | 翻訳するか削除する |

主な例は [leaked-wording-examples.md](references/leaked-wording-examples.md) を分類ごとに引く。

## 手順

1. スコープを決める。対象の面と触らない場所を先に列挙する。
2. 読み取り専用で監査する。[recall-batteries.md](references/recall-batteries.md) のパターンを走らせ、ヒットは意味で判定する。パターンは定義ではなく、最も濃い文章は素読みもする。
3. passage の事実節を列挙する。**事実節を含む passage は削除だけで済ませない。**各事実節を HEAD で自立するよう言い換えてから、周囲の叙述を消す。
4. 事実節を持たないもの（監査コード、制御フローの実況）はそのまま削除する。
5. 所有者優先で直す。生成物は源を直して再生成する。

## 削ってはいけないもの

| 残すもの | 例 | 理由 |
|---|---|---|
| issue 参照 | `#1470` | HEAD で解決する。README でも残す |
| 先送りのマーカー | `TODO(name):` | 先送りの正規の置き場 |
| 外部規格の節番号 | `RFC 9110 §10.1.5` | リポジトリ外で解決する |
| 現状の否定形で書いた回帰の固定 | 「X が無いと Y になる」 | 現在の挙動を固定する |
| 実測を表す語 | `measured`、「実測: 512 nests ≈ 0.15s」 | 測定と推測を分ける |
| suppression の正当化 | `oxlint-disable … -- 理由` | 必須の散文。理由が偽なら直す |
| 公開 API の契約 | 不変条件、`@returns` | 保守者が壊してはならない |
| コミット済み文書が所有する § 番号 | 自リポジトリの設計文書 | 所有者が実在する |

## やりすぎの型

漏れの削りすぎは残しすぎより高くつく。いずれも実際に起きた誤りである。

| 型 | 誤り | 正しい |
|---|---|---|
| 義務を承認に反転 | 「スロット移行待ちの例外」→「公認された例外」 | modality を保つ。「移行待ち」は義務 |
| 仮説を出荷済みに格上げ | 「将来の IPC シェルは…」から future-marker だけ削る | 「IPC シェルは存在しない。存在すれば…」と仮説だと明示する |
| 事実の巻き添え削除 | 1文を丸ごと削る | 節単位で消す。叙述と負荷の高い結合が同居するときは結合を残す |
| 出所を落として数値だけ残す | 「measured」を削って「3.1 MiB」だけ残す | `measured` を残す |

## サボった兆候

- 分類名を当てただけで、事実節の言い換えを書いていない
- 事実節を含む passage をまるごと削った
- `(decision N)` だけ消して、その中の事実を残していない
- 修正後の文章に「以前は」「no longer」がまだある
- issue 参照・`measured`・suppression の理由を、漏れと誤判定して削った
- 生成物を直接編集し、源を直していない
- batteries がゼロヒットだったことを、較正せず「漏れなし」と報告した
- 追加した文章自体が「ここでは〜を扱う」と文書の話題になっている

## 判定テスト

- 「HEAD の読者は、セッション記録・PR スレッド・未コミット草案なしに、この参照を解決できるか」
- 「この passage の事実節は何か。それぞれ HEAD で自立しているか」
- 「消したのは叙述か、事実か」
- 「『以前は』を現在形の反実仮想に置き換えたか」
- 「このコメントはレビュアーに宛てているか、保守者に宛てているか」
- 「このヘッジには TODO の持ち主がいるか。いなければ書いたか」
- 「ゼロヒットのパターンを、既知の陽性に一致するまで較正したか」
- 「修正は所有者に入れたか。生成物を手で直していないか」
