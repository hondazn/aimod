# 漏れ表現の Before / Fixed 例

分類ごとの較正材料。文面のテンプレートではなく、判定の原則を掴むために使う。括弧内は英語面で同型の典型語。

## 1. 死んだ設計セッション参照

（`(decision N)`, `(audit C2)`, `design §N`, `plan §N`, `T4` / `W3` / `P-I`）

### 所有者がコミット済みの決定

- **Before:** 「経費精算の承認は上長1名で足りる（decision 14）。」
- **Fixed:** 「経費精算の承認は上長1名で足りる。これは承認経路を短くする決定で、所有者は `docs/design/approval-flow.md`。」

番号は HEAD で解決しない。決定の名前と所有者のパスが解決する。所有者のパスはファイル内で1度はリンクとして示し、以降は検索可能な名前だけでもよい。

### 所有者がいない決定

- **Before:** 「会員番号は再利用しない（decision 6: 欠番を許す）。」
- **Fixed:** 「会員番号は再利用しない。欠番は許す。」

`decision 6` を所有する成果物が無いので引用は消す。ただし事実節（欠番を許す）は引用と一緒に消さず、自立させて残す。

### 監査コード

- **Before:** 「在庫の引き当ては冪等である（監査 B4）。」
- **Fixed:** 「在庫の引き当ては冪等である。同じ注文 ID を二度適用しても在庫は1度しか減らない。」

リポジトリに監査文書は無い。コードはセッションの速記で命題を持たない。本文の事実は残し、括弧だけを消す。

### 未コミット草案の節番号

- **Before:** 「層構成は設計 v2 §2.3 に従う。`src/domain/` が純粋な核。」
- **Fixed:** 「`src/domain/` が純粋な核である。」

コミットされていない草案の `§N` は解決しない。対照: 「RFC 9110 §10.1.5 に従って脱出する」は残す。外部規格はリポジトリ外で解決する設計であり、自リポジトリのコミット済み文書も § 番号を所有している。

### 計画フェーズの記号

- **Before:** 「`src/web/` は画面層（T3）。バッチは P-II 移行が持つ。」
- **Fixed:** 「`src/web/` は画面層。バッチは `src/batch/` にある。」

フェーズ記号は、実現しなかった計画を指す。記号を、そのフェーズが生んだものに置き換える。

## 2. スタック・PR 視点

（`this PR`, `this branch`, `this stack`, `later PRs`, `previous commit`）

### 保存文書の中のスタック位置

- **Before:** 「将来の決済代行がこのインターフェースを実装する（カード実装はこのスタックの後続 PR）。」
- **Fixed:** 「決済代行は注文処理を変えずにこのインターフェースを実装できる。」

保存文書はスタックを見られない。拡張点の契約を残し、未着手の仕事は PR 自体・`TODO`・issue のいずれかへ移す。

### README の中の「本 PR」

- **Before:** 「本 PR で請求書一覧にカーソルページネーションを追加する。」
- **Fixed:** 「請求書一覧はカーソルでページネーションする。」

README はどの PR より長生きする。機構を現在の事実として書く。

## 3. 変更の物語と版スタンプ

（`used to`, `no longer`, `previously`, `the old X`, `this cut`, `v1`, `today`）

### PR 番号付きの武勇伝

- **Before:** 「消費税率は以前コードに直書きされていた。税率マスタがそれを直した（PR #312）。」
- **Fixed:** 「消費税率は税率マスタから来る。マスタに行が無い商品は課税で失敗する。」

生きている事実は2つ（現在の機構と、今も成り立つ失敗時の挙動）。どちらも現在形で残す。バグの経歴は PR とその変更履歴文書の領分である。

### 削除の叙述

- **Before:** 「`legacy_flag` 列は削除の版で消えた。通知は今はイベント経由で飛ぶ。」
- **Fixed:** 「通知はイベント経由で飛ぶ。」

`legacy_flag` を知らない読者にとって、その不在は情報にならない。削除された過去と対比する「今は」は版スタンプである。

### 修正済みの回帰 → 現在形の反実仮想

- **Before:** 「重複した会員番号は以前そのまま登録されていた。」
- **Fixed:** 「一意制約が無いと、重複した会員番号がそのまま登録される。」

回帰の固定は生き残る。ただし制約を名指しする現在形の反実仮想として書く。`used to` はリポジトリ考古学に固定してしまう。

### 指示語の版スタンプ

- **Before:** 「CSV 取込はこの版では同期。非同期経路はロードマップ。」
- **Fixed:** 「CSV 取込は同期である。」（先送りは呼び出し箇所の `TODO(csv-import):` が持つ）

`this cut` / `v1` / `today` はマージした瞬間に古びる。変更履歴節の中の歴史的な段階名（「最初の版は X を出荷した」）は現状面でも安全だが、指示語の形はどこでも禁止である。

## 4. レビューの振り付け

（`rejected in review`, `review round`, `reviewer`, `as of v5`）

### レビュー判定をそのまま散文に

- **Before:** 「レビューで却下: 会員情報の全件キャッシュ。取得は都度にする。」
- **Fixed（設計文書の「検討した代替案」節）:** 「**会員情報の全件キャッシュ。** 却下。会員情報は退会で変わるため、TTL を置いても古い状態を配る。」

代替案節は正規の置き場である。レビュアーとラウンドは根拠の一部ではない。

### 草案の通し番号

- **Before:** 「このノートの v4 時点で、取込は文字コードも検査する。」
- **Fixed:** 「取込は文字コードを検査する。」

実装済みの文書は出荷済みの現実を書く。改訂の履歴は git にある。

## 5. レビュアー宛ての自己弁護

（`the cast is safe — it simply…`, `this is correct because…`）

### 型の弁明

- **Before:** 「この変換は安全である。ORM が型を合わせており、単に宣言が緩いだけだ。」
- **Fixed:** 「ORM はこの値を DB の型に合わせて返す。宣言された型は実行時の保証より緩い。」

保守者が壊してはならない不変条件を書く。「単に…」は、HEAD では誰も唱えていない異議に答える声である。不変条件がコードから見えるなら、コメントごと削除する。

### レビュー権威への訴え

- **Before:** 「丸め順序をレビュアーが確認したので、この計算は正しい。」
- **Fixed:** 削除（丸め順序は関数の `@returns` に書く）

正しさの主張は不変条件かテストを引く。人を引かない。

## 6. 復唱・導出の実況

（`first we X, then we Y`, テストの逐次説明）

### 制御フローの実況

- **Before:** 「まず入力を検証し、次に正規化し、最後に保存する。」
- **Fixed:** 削除（下の3行が同じことをコードで言っている）

### テストの実況

- **Before:** 「このテストは会員を作り、2回ログインし、2回目の応答を待ち、監査ログが4件であることを検証する。」
- **Fixed:** 「2回のログインで監査ログはちょうど4件になる。成功と失敗をそれぞれ記録するため。」

残すのは自明でない検証の根拠だけ。実況はテスト本体の言い直しである。

## 7. ヘッジと計画の残骸

（`probably fine for now`, `should be enough`, `should suffice`）

### マーカーの無い先送り

- **Before:** 「とりあえず今は全件をメモリに載せてよさそう。」
- **Fixed:** 削除。先送りに `TODO(member-list):` が無ければ、`TODO(name): ページ単位で読む` を書く。

持ち主のいないヘッジは計画の残骸である。

### 曖昧なサイズ見積もり

- **Before:** 「同時接続 100 もあればほとんどの場合足りるはず。」
- **Fixed:** 「同時接続の上限は 100（実測: ピーク時 62）。超えた要求は 503 で明示的に失敗する。」

ヘッジを実際の上限と、超えたときの失敗挙動に置き換える。

## 8. 執筆言語の混入

（日本語面では未翻訳の英語説明・作業メモ片・セッション区切り。英語面では逆方向）

- **Before:** 「取込は server 側で動く。桁揃えは layout spec を参照。`---- 私有 ----`」
- **Fixed:** 「取込はサーバー側で動く。桁揃えは帳票定義 `invoice-layout` に従う。」

作業言語の断片とセッション区切りは転記の残骸である。`invoice-layout` は残す。リポジトリ外で解決する外部の出所である。

### 対訳フェンスの中の混入

- **Before（両ファイル）:** `// 更新这里 before returning`
- **Fixed（両ファイル）:** `// 返す前にここを更新する。`

片方を直したら、そのブロックをバイト単位で両言語ファイルへ写す。別々に翻訳すると、どちらも流暢でも対訳の契約が壊れる。

## keep の較正

削ってはいけないものを、実際に削った誤りの形で示す。

| keep | 例 | 見分け方 |
|---|---|---|
| issue 参照 | 「上限は描画後の値全体に掛かる（`#1470` が後続を所有する）。」 | issue はどの面からも HEAD で解決する |
| 死んだ名前呼び | 「（請求書レンダリング RFC 参照）」 | その文書は実在しない。解決性で判定し、形式で判定しない |
| suppression の正当化 | `// oxlint-disable-next-line no-non-null-assertion -- 1要素リテラルが index 0 を保証する` | 必須の散文。理由が偽なら直し、消さない |
| 実測値 | 「深さ上限（実測: 512 nests ≈ 0.15s。4096 でループが止まる）」 | `measured` が測定と推測を分ける |
| 実行時の old/new | 「古い接続が drain してから新しい接続が受ける」 | 引き継ぎ中の生きた2オブジェクト。リポジトリの状態ではない |
| 実行時の自然な時刻 | 「今日の日付は？」 | ランタイムの時計を問う。版スタンプではない |
| 外部の出所 | 「RFC 9110 §10.1.5」「帳票定義 `invoice-layout`」 | リポジトリ外で解決する設計 |

## やりすぎの型（再掲）

- **義務→承認の反転:** 「スロット移行待ちの例外」は義務。`sanctioned exceptions` に短縮すると modality が反転する
- **仮説→出荷済みの格上げ:** future-marker を消すだけでは、設計例が実装済みの主張になる。仮説だと明示する
- **事実の巻き添え:** 1文に叙述と負荷の高い結合が同居するときは、節単位で消す
- **出所の脱落:** `measured` を残す。無いと数値が定義として読まれ、再測定されない
