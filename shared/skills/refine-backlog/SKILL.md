# backlogアイデアの精緻化

## ユーザー入力

```text
$ARGUMENTS
```

## 目的

kojo の backlog アイデアの意図を「推定」（planner が実行時に推定する）から「明示」（人間が確認済み）に昇格させる。kojo の実行経路・factory コードには一切触れない — 人間の時間に寄せる上乗せ層であり、意図が無くても完全自動ランは成立する（planner が推定する）。

## 前提

- 対象は kojo リポジトリの `backlog/*.md`。`in-progress/`（実行中）と `suspended/`（人間対応待ち）は対象外
- frontmatter（`level` / `attempts` / `handover` / `issue`）は factory が管理する。**読んでも書き換えない**
- アイデアの構成: `# タイトル` → 説明1段落 → `## 意図` → `## 受け入れ条件の種`

## Phase 1: 対象の特定

`$ARGUMENTS` を解釈する:

- **既存ファイル名/スラグ** → `backlog/` から該当ファイルを読む
- **新規アイデアの説明** → 既存の連番に続く `NNN-slug.md` を新規作成する。スラグは既存 `backlog/*.md` と `ledger/ledger.jsonl` の app スラグと重複しないこと（replenisher と同じ規則）
- 特定できない場合は `backlog/` の一覧を提示して選んでもらう

## Phase 2: grill（意図の尋問）

説明と受け入れ条件の種を読み、AskUserQuestion で質問する（既存ファイルは 1〜2、新規作成は 1〜3 の3問）。**全問に、説明・受け入れ条件の種から推定した仮説を推奨回答として付ける**:

1. **Purpose**: このアプリは誰の・何の問題を解くか
2. **User Context**: どんな場面・どんなテンポで使われるか（例: 一日一回さっと開く / 開きっぱなしで常用）
3. **削ぎ落とし**（新規作成時のみ）: 何をやらないことで1日スコープに収まるか

既に `## 意図` がある場合は、その内容を推奨回答にして grill し、確定後に置き換える（再実行しても壊れない）。回答が説明や受け入れ条件の種と矛盾する場合は、その場で指摘して先に解消する。

## Phase 3: 書き込み

- `## 意図` セクション（1〜2文。誰が・どんな場面で・なぜ使うか）を説明段落の直後、`## 受け入れ条件の種` の前に書き込む
- 確定した意図と矛盾する受け入れ条件の種があれば、修正案を提示して合意の上で直す
- 新規作成時は受け入れ条件の種（検証可能な項目を3つ）も意図から導いて書く

## 出力例

```markdown
# サイコロジェネレーター

画面上のボタンをクリックすると1〜6の目が表示される静的単一ページアプリ。

## 意図

ボードゲーム中にサイコロを忘れた人が、スマホでさっと開いて数秒で振るための道具。
セットアップや説明なしに初見で使えることが価値。

## 受け入れ条件の種

- 「振る」ボタンをクリックするたびに1〜6のいずれかの目がランダムに表示される
```

## 使わない場面

- 完全自動ランに任せるとき（planner が意図を推定する。本スキルは必須工程ではない）
- kojo 以外のリポジトリの Issue 精緻化 → `refine-issue` を使う
