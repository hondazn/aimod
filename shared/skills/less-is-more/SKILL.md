# Less is More — 最終工程の削りパス

推論は冗長でよい。保存する成果物は本質だけ残す。

## 位置付け

- すべての作業の**最終工程**。成果物（コード・ドキュメント・設定など保存されるもの）を
  生んだら、完了報告の前に必ず実行する。規模は問わない（1行修正でも実行する）
- 会話の応答・思考過程は対象外
- コードの構造・設計品質は `coding-standards` / `design-principles` の領分。
  本スキルがコードに対して見るのは**コメントと余剰成果物**が中心で、構造のリファクタは行わない

## 判定

### 1. 置き場

**その媒体でしか表せないことだけを、その媒体に残す。**

| 媒体 | そこでしか表せないもの |
|---|---|
| コード本体 | how — いまどう動くか |
| コードコメント | why not — なぜ他の手を採らないか、採れないか |
| テストコード | what — 何が保証されるか |
| ドキュメント | 読み手が判断・操作するために要ること |
| コミットログ・PR 本文 | why — なぜ変えたか |
| git 履歴 | かつて — 以前どうなっていたか |

他の媒体で表せる記述は重複。**正しい置き場があるなら移し、無ければ消す。**
表に無い媒体でも問いは同じ —「これはここでしか表せないか」。

### 2. スコープ

**無くても今回の依頼が満たされるなら削る。** 記述だけでなく、追加したファイルそのものにも当てる。

### 3. 話題

**その記述が更新するのは、対象そのものか、それとも文書自身か。** 「本節では〜を扱う」「次は〜を見る」
のように話題が文書自身になっている記述は削る。**短く格好よく書き直して残すのが最大の混入経路**で、
リズムが良いことは残す理由にならない。

### 例外は慣習だけ

上の 1〜3 のどれかで消える記述でも、**コードベースの慣習として確立している**
（例: 全モジュールにある docstring、全エンドポイントにあるバリデーション）なら残す。

それ以外は削る。**迷ったら削る**（削った項目は記録する。「記録」の節を参照）。

## ボーイスカウトルール

今回書いたものに限らず、**触ったファイル全体**の既存の冗長も同じ基準で削る。
触っていないファイルは対象外（削るために探索しない）。

## モード

| モード | 動作 |
|---|---|
| 自動削除（デフォルト） | 削除まで実行 → 作業中に使った検証（テスト・lint 等）を再実行して green を確認 → 報告 |
| 候補提示 | 削除候補の一覧提示で止め、ユーザーの承認を待つ。「候補提示だけにして」等の宣言があったときのみ |

## 記録 — 削ったものを監査可能にする

- 最終報告に削った項目を一覧で明記する。**迷って削ったもの**は区別して示す
- コミットする場合は**作業本体と削りを別コミット**に分ける。ボーイスカウト分も削りコミット側に置く。
  作業本体の差分は依頼スコープに閉じたまま保たれ、削りは `git show` で後からいつでも監査できる
