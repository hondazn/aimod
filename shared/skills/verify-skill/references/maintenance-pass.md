# 保守モードの手順

機能マップはアプリが変わった瞬間から腐る。このパスは、`verify-<app>` スキル（または同等の機能マップ付きプロジェクトローカル検証スキル）を honest に保つための点検である。厳密さの単位は**機能**であって、文ごとではない。全機能ファイルを source から覆い、全機能を live で1回ずつ運転する。箇条書きを1行ずつ確定させる必要はない。

## 成果の選択

実行の最後に、次のどれかを明言する。

- **clean** — 全機能が source と live の両方で覆われ、出荷するものが無い。ブランチも変更束も作らない。
- **changed** — 証明済みの doc / harness / マップの修正を1つの変更束として出す。
- **blocked** — 網羅が終わらない、または証明済みの修正を安全に出せない。何が塞いだかを具体的に書く。

## edit scope

検証スキル自身のディレクトリ（その SKILL.md、`features/`、それが所有するハーネスのスクリプト）だけを編集する。実行中にプロダクトコードを編集しない。マップが説明する振る舞いをアプリがしなくなったなら、doc drift（マップを直す）か product gap（報告する。docs で上書きしない）のどちらかである。

## 証拠の規準

生成物の Evidence 節と、保守の live pass が従う規準。対象アプリに合わせて具体物を決める。

| 規準 | 内容 |
|---|---|
| 経路 | 実ユーザーの経路を運転する。内部の setter やテスト専用エンドポイントは証拠にしない |
| 範囲 | 操作と、その結果の状態を撮る。最後の画面だけでは足りない |
| 副作用 | 画面に見えるものと並べ、ファイル・行・送信メッセージを確かめる |
| モック | production の境界が既に外部系を隔離している箇所だけ。それ以外はモックしない |
| dry-run | dry-run やテストモードなら、何を skip したかをファイル・ネットワーク・git ref の観測で確かめる。名前を信用しない。ネットワークに出る dry-run もある |
| 後始末 | Cleanup はインスタンスと作業状態を消し、証拠は消さない。証拠は生成スキルが名指しした場所に残る |

## パス

### 0. 対象を特定する

launch / drive の節と機能マップを持つプロジェクトローカルスキルを探す。候補が複数ならどれかを聞く。1つも無ければ、対象をでっち上げずに生成モードへ回す。

### 1. 索引の衛生

機能マップの README を読み、兄弟ファイルを列挙する。欠け・余分・重複・死んだ項目を直す。軽い工程である。生成された在庫表は作らない。

### 2. source の波

機能ファイルごとに読み取り専用のサブエージェントを1体、同時に起動する。各子は source から「このユーザー向け機能はどう動くか」を説明し、ドリフト候補を引用付きで挙げ、live 検証の手順を1本、簡潔に返す。子はアプリを運転せず、ファイルを編集しない。

戻り値の形:

| 項目 | 内容 |
|---|---|
| 機能の要約 | ユーザーから見た振る舞い |
| source の入口 | 実在する `file:line` |
| ドリフト候補 | あれば引用付き、無ければ「無し」 |
| live 手順 | 1本 |

機能ファイルと子の対応が崩れないよう、各子には対象ファイル1本と、逐語のプロンプトを渡す。1体は落ちる前提で、返らなかったファイルを記録して続行する。

### 3. 突き合わせ

全機能ファイルに要約が返った状態から統合する。

- 重なる live 手順を、実務上できるだけ少ないアプリ状態にまとめる。
- 引用されたドリフトは抜き取りで確認する。clean な主張は再証明しない。
- 最近の変更をさらって、マップに無いユーザー向けの面を探す。具体的な source パスを示せて初めて「欠けている」と言える。

### 4. live pass

source が clean に見えても必ず回す。運転は統括者が1人で持つ。検証スキル自身の launch のモデルに従う。サーバや UI は常駐インスタンス1つを直列に運転し、短命な CLI は運転ごとに新しい隔離セッションを立てる。どちらかはこのパスではなく、生成スキルの Launch 節が決める。

機能ファイルごとに主要経路を1回ずつ実走する。失敗があっても、パス全体で3つの不変条件を守る。

1. **health check を飛ばさない。** 直前に不可解な挙動をしたインスタンスを運転しない。最初の Drive の前、セッションが単位なら新しいセッションごと、失敗した Drive の後に Doctor を回す。Doctor から見えない失敗（プロセスは生きているが UI が固まっている）では、祈らずに既知の状態へ戻すか起動し直す。
2. **証拠は後始末を越えて残る。** それまでに撮った証拠を、名指しされた場所で確かめる。仮定しない。
3. **Drive が起こしたものを残さない。** セッションが stuck でも exit 済みでも共有でも同じ。失敗した試行の残渣は、その試行の役目が終わった時点で消す。共有インスタンスでは、インスタンスではなく自分の残渣を消す。

追加の規則:

- スキルのドリフトが原因の Doctor 失敗はドリフトである。edit scope 内で直し、1回だけ retry する。直しが無効化したもの（その設定を読んだプロセスなど）だけを再起動する。それでも通らなければ `blocked` と呼ぶ。
- 到達できない機能は、具体的な前提（認証・権限・OS・外部状態）と試した経路を添えて初めて `verified-unreachable` と書く。マップがその前提を落としているなら、それはドリフトである。
- triage から出たハーネスの修正は、出す前に live で運転し直す。
- 最後の片付けは、その再証明を含む実行の最後の Drive の後に来る。何も実行を越えて残らない。証拠はスキルの定めに従って残る。

### 5. triage

| 分類 | 判定 | 行動 |
|---|---|---|
| **doc drift** | ユーザー視点の記述が誤り、または欠けている | マップを直す |
| **harness gap** | 動いている振る舞いをハーネスが運転できない | ハーネスを直す。helper の規準は生成と同じ（実行可能、呼び出し方を本文に記載） |
| **product gap** | アプリの振る舞い自体が壊れている | ユーザー向けに記録する。この変更束に入れない |

### 6. 出すか止めるか

- **changed** — 証明済みの修正を1つの変更束にする。出す前に変更したファイルを全て読み直す。
- **clean / blocked** — 変更束を出さない。成果と、覆えた範囲を正直に報告する。

実行の記録（覆った機能、到達できなかった前提、確認したドリフト、成果）は作業場所に簡潔に残す。コミットしない。

## 症状

| 症状 | 何が起きているか |
|---|---|
| 機能を source で読んだだけで clean と判定した | live pass を飛ばしている |
| 子エージェントがアプリを運転している、ファイルを編集している | source の波が読み取り専用になっていない |
| 変更束にプロダクトコードの修正が入っている | edit scope を越えている |
| product gap をマップの記述修正で吸収した | 壊れた振る舞いを docs で隠している |
| 「全機能 clean」と書き、到達できなかった機能を挙げていない | `verified-unreachable` を clean に混ぜている |
| 変更束が2つ以上に分かれた | 1つに絞るか、`blocked` として何が塞いだかを書く |
| 実行後にプロセスやポートが残っている | 最後の片付けが最後の Drive より前に走っている |
| 証拠の場所が空 | Cleanup が証拠を食べたか、場所を確かめずに仮定した |
