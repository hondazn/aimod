# 検証ハーネスの生成と保守 — アプリをユーザーの経路で運転する

「実装した」と「ユーザーの経路で動く」の間を埋めるのは、そのプロジェクト専用の検証ハーネスである。起動し、ユーザーと同じ入口から操作し、証拠を残し、自分が起こしたものだけを片付ける手順を `verify-<app>` というプロジェクトローカルなスキルに固定する。以後の受け入れ確認はそれを回すだけになる。生成物を書く相手は人間ではなく、アプリを一度も見たことのないエージェントである。冷えた状態で読み、そのまま運転できる粒度で書く。

## 2つのモード

| モード | いつ | 成果 |
|---|---|---|
| **生成** | `verify-*` が無い、または実態と合っていない | 対象リポジトリの `verify-<app>` スキル |
| **保守** | `verify-*` がある。アプリが変わった、マップが古い疑いがある | clean / changed / blocked の判定と、changed なら1つの変更束 |

「受け入れ確認をして」「E2E を通して」と言われ、ハーネスが無いなら生成から入る。`verify-*` が既にあるなら保守を回す。両方を同時にやらない。

## 効かない

- ブラウザ操作の録画と PR への証跡動画 → `e2e-video`（証拠の残し方はこのスキルが持つ）
- 証拠の強度の数え方、「未証明」の書き方 → `evidence-discipline`
- 機能の実装そのもの → プロダクトコードは触らない。壊れていれば報告する
- 既に検証手順が整っているプロジェクトの通常の受け入れ確認 → その手順を回す
- 読み取り専用サブエージェントを並べる形の設計 → `delegation-discipline`

## 生成

### 1. ユーザーではなくリポジトリに聞く

コードベースから答えを出す。観測できないことだけユーザーに聞く。

| 問い | 見る場所 |
|---|---|
| **面** — ユーザーが実際に触るのは何か | ルーティング、エントリポイント、README、画面定義 |
| **起動** — どう起動するか | README の quickstart、package scripts、Makefile。ポート、env、シード、認証 |
| **運転** — エージェントがどう操作するか | 既存の Playwright / Cypress / expect / PTY / curl できる口を先に探す |
| **観測 / 隔離** — 何が証拠として撮れ、2つ同時に起動できるか | 画面、端末記録、レスポンス本文、ログ、exit code、DB。ポート、データディレクトリ、プロファイル。共有インスタンスを二重に運転しない |

面は複数ありうる。主たる1つを選び、残りは註記する。そのままではビルドも起動もしないなら、先に直すか正確に報告する。壊れた土台の上に書いたスキルは誤った手順を教える。起動を妨げるだけの無関係な欠落（API が配信しない静的ディレクトリ、雛形の設定）は、検証用の足場と明示して生成スキルに作らせ、Cleanup で消す。

### 2. 生成物を書く

置き場はプロジェクトローカルのスキル置き場（`verify-<app>` ディレクトリ）。ホスト固有の絶対パスは書かない。frontmatter に `name: verify-<app>` と、アプリ名・面・使う場面を書いた `description` を置く。本文は次の必須セクションを持ち、プレースホルダを残さず調査で分かった実物を書く。

| セクション | 書くこと |
|---|---|
| **Launch** | 起動する正確なコマンドと、起動したと判定する条件（ログ行、ポートの応答、プロンプト）。短命な CLI / TUI はサーバを常駐させず、依存を一度入れてから運転ごとに隔離した PTY / tmux を立てる |
| **Doctor** | 読み取り専用の1コマンド。「運転する価値があるか」に答える — プロセス、ビルド版、ポートの所有、認証。少しでも怪しければ最初に回す |
| **Drive** | このリポジトリの実セレクタ・実コマンドによる操作手順。座標やタブ順より、ARIA ラベル・data 属性・プロンプト文字列・ルートパスを優先する |
| **Evidence** | 証拠として何をどこに残すか。規準 → [references/maintenance-pass.md](references/maintenance-pass.md) の「証拠の規準」 |
| **Cleanup** | 自分が起動したものだけを片付ける。プロセス名で kill しない。証拠は後始末を越えて残る |
| **Helpers** | 同梱スクリプトは実行可能にし、呼び出し方を本文に示す。読み手が逆解析する必要のあるものは helper ではない |

### 3. 機能マップを置く

`features/README.md`（索引と前提・運転の約束）と、ユーザー向け機能ごとのファイルを1本ずつ。最初は上位3〜5本でよい。ルート、コマンド、メニュー、docs から拾う。

各機能ファイルの H2 は **`Sub-features` / `How to get to it (user POV)` / `Driving it with <harness>` / `Gotchas` の4つだけ**にする。形と粒度は **[references/feature-map-example.md](references/feature-map-example.md)** に実例1本としてまとめてある。マップはそのリポジトリの検証の正本である。複数の入口を挙げているのに都合のよい1つだけを運転した証明は不完全である。

### 4. 証拠の規準

証拠は実ユーザーの経路で取り、操作と結果の状態を対で残し、副作用を画面の外でも確かめる。モックは production の境界が既に外部系を隔離している箇所だけ。dry-run やテストモードを使うなら、**何を skip したか**をファイル・ネットワーク・git ref の観測で確かめる（名前を信用しない。ネットワークに出る dry-run もある）。Cleanup はインスタンスと作業状態を消し、証拠は名指しした場所に残す。6項目の規準表 → [references/maintenance-pass.md](references/maintenance-pass.md) の「証拠の規準」。

### 5. 渡す前に自分で1回通す

Launch → Doctor → マップ済み機能を1つ Drive → 証拠を回収 → Cleanup、を実走する。1つでよい。マップは後の実行が残りを覆うためにある。Cleanup の後に、名指しした場所に証拠が残っていることを確かめる。証拠を食べる Cleanup はここで落ちる。失敗したら直し、失敗した試行の後にも生成した Cleanup を回して、壊れた試行がプロセスとポートを残さないようにする。**一度も実行していない生成物はドラフトであって、成果物ではない。**

## 保守

手順の詳細は **[references/maintenance-pass.md](references/maintenance-pass.md)**。要点だけ:

| 段 | やること |
|---|---|
| **対象の特定** | launch / drive の節と機能マップを持つプロジェクトローカルスキルを探す。候補が複数ならどれかを聞く。無ければ生成へ回し、対象を捏造しない |
| **索引の衛生** | README を読み、兄弟ファイルを列挙し、欠け・余分・重複・死んだ項目を直す |
| **source の波** | 機能ファイルごとに読み取り専用サブエージェントを並列で当て、source から振る舞いを説明させ、ドリフト候補を引用付きで挙げさせ、live 用の手順を1本返させる。子は運転も編集もしない |
| **突き合わせ** | 全ファイルに要約が揃った状態から、手順を重ねてアプリの状態をできるだけ少なくする。引用されたドリフトは抜き取り確認し、clean な主張は再証明しない |
| **live pass** | source が clean に見えても必ず回す。運転は統括者だけが持つ。機能ファイルごとに主要経路を1回ずつ実走し、検証スキル自身の Launch のモデルに従う |
| **出すか止めるか** | 成果は clean / changed / blocked のいずれかを明言する。changed は1つの変更束まで。出す前に変更したファイルを全て読み直す |

live pass の不変条件: 不可解な挙動の後に Doctor なしで運転しない（最初の Drive 前、新セッションごと、失敗した Drive の後）／撮った証拠は後始末を越えて名指しの場所で確かめる／Drive が起こしたものはその Drive の役目が終わったら残さない（共有インスタンスでは残渣だけ消す）。スキルのドリフトが原因の Doctor 失敗は edit scope 内で直し、1回だけ retry する。到達できない機能は、具体的な前提と試した経路を添えて初めて `verified-unreachable` と書く。ハーネスを直したら live で運転し直し、最後の片付けはそれを含む最後の Drive の後に行う。

triage は3つに分ける。

| 分類 | 判定 | 行動 |
|---|---|---|
| **doc drift** | ユーザー視点の記述が誤り、または欠けている | マップを直す |
| **harness gap** | 動いている振る舞いをハーネスが運転できない | ハーネスを直す。helper の規準は生成と同じ |
| **product gap** | アプリの振る舞い自体が壊れている | 記録してユーザーに渡す。この変更束に入れない |

**edit scope は検証スキルのディレクトリだけ。** その SKILL.md、`features/`、それが所有するハーネスのスクリプト以外を触らない。実行中にプロダクトコードを編集しない。アプリがしなくなった振る舞いをマップが説明しているなら、doc drift か product gap のどちらかである。docs で隠さない。実行の記録（覆った機能、到達できなかった前提、確認したドリフト、成果）は作業場所に簡潔に残し、コミットしない。

## サボった兆候

- 生成物にプレースホルダや例が残っている（実リポジトリのセレクタに置き換えていない）
- 生成したスキルを一度も実走せずに「できました」と渡している
- Cleanup がプロセス名で kill している、または証拠ごと消している
- 証拠が最終画面のスクリーンショット1枚だけで、操作と結果の状態が入っていない
- dry-run の名前を信用して skip 内容を観測せず、モックが production の境界の外まで広がっている
- feature map の H2 が4つ以外、または実装の詳細がマップに混ざっている
- マップの入口を1つだけ運転して「全経路を確認した」と書いている
- 保守で live pass を回さず、source の読みだけで clean と判定している
- source の波で子エージェントに運転・編集をさせている
- triage で product gap をマップの記述修正に吸収している
- 検証スキルのディレクトリの外を編集している
- 到達できなかった機能を、前提と試行経路を書かずに clean に混ぜている
## 判定テスト

- 「Launch / Doctor / Drive / Evidence / Cleanup / Helpers は全て埋まっているか」
- 「アプリを一度も見たことのないエージェントが冷えた状態で実行できるか。セレクタ・コマンド・パスは実物か」
- 「証拠は実ユーザーの経路から取り、操作と結果の状態を対で残したか」
- 「dry-run で何を skip したかを、名前ではなく観測で確かめたか」
- 「Cleanup は自分が起動したものだけを殺すか。証拠は後始末の後も名指しした場所にあるか」
- 「生成したスキルを1回通したか。未実行のドラフトを成果物として渡そうとしていないか」
- 「feature map の H2 は指定の4つだけか。実装の詳細が混ざっていないか」
- 「保守の live pass で、機能ファイルごとに主要経路を1回ずつ実走したか。Doctor を最初の Drive 前・新セッションごと・失敗した Drive の後に回したか」
- 「到達できなかった機能に、前提と試した経路を書いたか」
- 「doc drift / harness gap / product gap のどれかを、機能ごとに明言できるか」
- 「成果は clean / changed / blocked のどれか。changed なら1つの変更束に収まっているか」
- 「編集したのは検証スキルのディレクトリの中だけか」
