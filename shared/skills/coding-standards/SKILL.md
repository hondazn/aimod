# コーディング規律 — 書く最中に守ること

出典: [CFH] Code That Fits in Your Head (Mark Seemann) / [TF] Tidy First? (Kent Beck)。
境界・分割・整理タイミングの判断理論は `design-principles` スキルを土台とする。

## 基本ルール

- 関心の分離を保つ。状態とロジックを分離する
- 冪等性と耐障害性を重視し、再実行・部分失敗・異常入力でも安全に失敗・回復するよう設計する
- コントラクト層（API/型）を厳密に定義し、実装層は交換容易性を保ち再生成可能にする
- 静的検査可能なルールはプロンプトではなく、その環境の linter か ast-grep で記述する

## 認知負荷の閾値 [CFH]

すべての判断基準は「人間のワーキングメモリ ≒ 7±2 チャンク」に帰着する。

| メトリクス | 閾値 | 根拠 |
|------------|------|------|
| 循環的複雑度 | 7以下 | 分岐数。8に達したらリファクタリングのトリガー |
| 変数の数 | 7個以下 | ローカル変数＋引数の合計 |

## 構造の原則

### 関数型コアと命令型シェル [CFH]

副作用・I/Oを最外周（シェル）に押し出し、中心（コア）を純粋関数＝参照透明に保つ。
コアがテスト容易・推論容易になり、変数（状態）の数が減る。

### コマンドクエリ分離 [CFH]

- **コマンド**: 副作用を持ち void を返す。
- **クエリ**: データを返し副作用を持たない。
- 両方を兼ねるメソッドを作らない。呼び出し側の推論コストが下がる。

### カプセル化とAPI設計 [CFH]

- **検証せずにパースする (Parse, don't validate)** — 入力を一度パースして「不正な状態を表現できない型」へ変換し、以降は再検証不要にする。
- **ポカヨケ** — 誤用を物理的に不可能（またはコンパイルエラー）にするAPI設計。
- **名前を外側から付ける** — メソッド・APIの名前は呼び出し側（利用者）の視点で付ける。
- **コミュニケーション階層** — 意図の伝達手段を価値の高い順に: ① 良いAPI（型） → ② 分かりやすいメソッド名 → ③ 良いコメント → ④ 自動テスト → ⑤ Gitコミットメッセージ → ⑥ ドキュメント。
- **デメテルの法則** — 内部のさらに内部（孫オブジェクト）へ手を伸ばさない。

### 横断的関心事 [CFH]

- ロギング・計測・キャッシュなどはビジネスロジックに混ぜず、デコレーターで包む。
- ストラングラーパターンで段階的に置き換える（ビッグバン書き換えを避ける）。

## 整理テクニック [TF]

構造の変更（整理）と振る舞いの変更を同じコミット/PRに混ぜない。
いつ整理するかの経済学は `design-principles` を参照。

| テクニック | 内容 |
|-----------|------|
| ガード節 | ネストした if を早期 return に平坦化 |
| デッドコード | 使われないコードは消す（Git で戻せる） |
| シンメトリー | 同じことをするコードは同じ書き方に統一 |
| 新IF・旧実装 | 欲しいインターフェースを先に作り古い実装を包む |
| 読む順番 | 読み手が理解しやすい順に並べ替え |
| 凝集の順番 | 一緒に変更する要素を物理的に近づける |
| 宣言と初期化を近接 | 使う直前で宣言・初期化 |
| 説明変数 | 複雑な式の一部を意図が分かる名前の変数に抽出 |
| 説明定数 | マジックナンバーをシンボリック定数に。ただし意味の違う同値を共通化しない |
| 明示パラメーター | マップ一括渡しをやめ必要なデータを明示的引数で |
| ステートメント小分け | 意味単位で空行等に分ける |
| ヘルパー抽出 | まとまりのあるコードブロックを名前付きルーチンに |
| ひとかたまり | 過剰抽象をインライン化して大きな塊に戻してから再整理 |
| 説明コメント | コードから読み取れない「なぜ」だけを書く |
| ガラクタ削除 | コードと同じことを言うだけのコメントを消す |

## TDD とテストの規律 [CFH]

- **Red → Green → Refactor** の順序を守る。テストなしに実装を書き始めない。
- テストが書きにくいなら設計が悪いというフィードバック（テストの声を聞く）。設計に戻る。
- **Arrange-Act-Assert**: テストは「準備→実行→検証」の3フェーズで構造化する。
- **バグは必ず失敗するテストで再現してから修正する。** 推測で直さない。
- **悪魔の代弁者**: 意図的に間違った実装でテストを通そうと試み、通せたらテスト不十分。
- **検証は「誤実装が落ちること」を基準に選ぶ**: テストの価値は正しい実装が通ることではなく、ありうる誤実装が落ちること。境界（ゼロ回・順序・短絡）、全文一致（断片一致では別物が通る）、参照同一性、失敗注入をこの基準で選ぶ。「このテストを通したまま壊す実装が書けるか」を自問し、書けるなら判定力が足りない。
- **本番経路のスモークを1本含める**: テストランナーと本番の実行経路が異なる場合（ビルド変換・実行環境の差）、テスト全緑でも本番経路では動かないことがある。本番と同じ経路での実走スモークを1本含める。
- テストとプロダクションコードは**別々に**リファクタリングする（同時に触ると安全網が消える）。
- テスト戦略の形（ピラミッド／ダイヤモンド／逆ピラミッド）は実装パターンに合わせる。
  選択基準は `ddd-modeling` スキルの references を参照。

## スライスの切り方 [CFH]

- 水平層でなく、入力から永続化まで貫く**バーティカルスライス**で実装する。
- 最初にウォーキングスケルトン（アーキテクチャ全体を貫く最薄の end-to-end）を通す。
- アウトサイドイン: 境界（HTTP 等）から始めて内側（ドメイン）へ進める。

## どこに何を書くか

- コードには How のみを書く
- テストには What のみを書く
- コミットメッセージ, プルリクエストには Why のみを書く
- コードコメントには Why not のみを書く

## アンチパターン [CFH][TF]

- **長いメソッド・大きなコードブロック**: 複雑度7・変数7のいずれかを超過
- **コマンドとクエリを兼ねるメソッド**: 副作用の有無が不明
- **繰り返しのバリデーション**: 至る所で同じ妥当性チェック（→Parse, don't validate）
- **ビジネスロジックに混入した横断的関心事**: ロギング等の直書き
- **テストと本番コードの同時リファクタリング**: 安全網が消える
- **推測でのデバッグ**: 再現テストなしに原因を当て推量で修正
- **振る舞い変更と構造変更の混在**: 同一コミット/PRに混ぜる

## チェックリスト

- [ ] 循環的複雑度は7以下か？
- [ ] 変数（ローカル＋引数）は7個以下か？
- [ ] 各メソッドはコマンドかクエリの一方か？
- [ ] 不変条件はカプセル化で保護されているか？ 不正な状態を作れないか？
- [ ] 入力はパースで型に押し込めているか（Parse, don't validate）？
- [ ] 名前は利用者視点で付けられているか？
- [ ] 副作用は外周に押し出され、コアは参照透明か？
- [ ] 振る舞いの変更と構造の変更が同じコミット/PRに混在していないか？
- [ ] 各整理は可逆で中断可能なスライスになっているか？
- [ ] 過剰抽象で逆に読みにくくなっていないか？
- [ ] デッドコード・冗長コメントは残っていないか？
- [ ] バグ修正は再現テストを書いてから直したか？
- [ ] テストとプロダクションコードを別々にリファクタリングしたか？
- [ ] テスト戦略の形が実装パターンに合っているか？
