# コーディング規律 — 書く最中に守ること

コードを書くコストはエージェントにとって安い。だから過剰に作りやすい。人間の保守者が読むのに疲れると感じるコードは、動いていても悪い解である。

境界・分割・整理タイミングの判断理論は `design-principles` スキルを土台とする。構造（型・境界・データフロー・状態・エラー方針）が未決定なら、書き始める前に `design-code` で決める。

## 基本ルール

- 関心の分離を保つ。状態とロジックを分離する
- 冪等性と耐障害性を重視し、再実行・部分失敗・異常入力でも安全に失敗・回復するよう設計する
- コントラクト層（API/型）を厳密に定義し、実装層は交換容易性を保ち再生成可能にする
- 同じ指示を二度書いたら、lint / ast-grep / 型 / 実行時検査へ落とす。プロンプトに残すのは判断が要るものだけ。静的に検査できるルールは linter か ast-grep で記述する
- 人が直したこと、行き止まりのあと通った道が一般化できるなら、スキルか検査に落とす。「次から気をつけます」で終わらない
- 作業中にスキルが壊れている（手順が実行できない、誤誘導する）なら、回避せず、スキル修正を別差分にする
- 再実行しても安全にする。冪等キー・upsert・重複検出・再開可能なチェックポイントのどれかで表す
- 再起動やリトライでだけ壊れるなら、条件分岐ではなく状態（可変なグローバル・キャッシュ・初期化順）を先に疑う

## 学びを機構へ落とす

指摘・失敗・行き止まりは、機構（lint・型・テスト・スクリプト）に落ちて初めて再発しなくなる。**指示文は症状であり、原因ではない。**

| 手 | 効く範囲 | 落とし先 |
|---|---|---|
| 1 | その場の1箇所 | コード修正 |
| 2 | 同種の全箇所 | リンタ・ast-grep・型 |
| 3 | 実行しないと分からない | テスト・静的解析 |
| 4 | 判断が要る | スキル本文の規律 |

同じ指摘を2度受けたら手1で終えず、手2以上へ上げる。手4は機械が表せないときだけ選ぶ。「次から気をつけます」は手0である。

## リポジトリ規約の読み取り

コード変更の**着手前に一度だけ**読む。見つからなければ即座に諦める。

| 層 | 対象 | 扱い |
|----|------|------|
| 機械が強制する | linter 設定（`eslint.config.*`, `clippy.toml` 等） | **プロンプトに写さず lint/format を走らせて従う** |
| 文書化されている | 直下・`.claude/` の `CLAUDE.md` / `AGENTS.md`, `CONTRIBUTING.md`, `docs/` 配下の style 系 | 読んで従う |
| 明文化されていない | 変更対象の**近傍ファイル**（同ディレクトリ・対応するテスト） | 命名・レイヤ・テスト書式・エラー処理の実際の形を取る |

衝突したら領域で分ける。

- **表層はリポジトリ規約が無条件で勝つ** — 命名・整形・import 順・ファイル配置・言語・テストの書式
- **規律は本スキルが勝つ** — 複雑度7・変数7・CQS・Parse, don't validate・再現テスト・振る舞いと構造の分離。リポジトリが明示的に禁じている場合だけユーザーに上げる

## 認知負荷の閾値

すべての判断基準は「人間のワーキングメモリ ≒ 7±2 チャンク」に帰着する。

| メトリクス | 閾値 | 根拠 |
|------------|------|------|
| 循環的複雑度 | 7以下 | 分岐数。8に達したらリファクタリングのトリガー |
| 変数の数 | 7個以下 | ローカル変数＋引数の合計 |

## 構造の原則

### 関数型コアと命令型シェル

副作用・I/Oを最外周（シェル）に押し出し、中心（コア）を純粋関数＝参照透明に保つ。コアがテスト容易・推論容易になり、変数（状態）の数が減る。

### CQS（コマンドクエリ分離）

- **コマンド**: 副作用を持ち void を返す。
- **クエリ**: データを返し副作用を持たない。
- 両方を兼ねるメソッドを作らない。呼び出し側の推論コストが下がる。

### カプセル化とAPI設計

- **検証せずにパースする (Parse, don't validate)** — 入力を一度パースして「不正な状態を表現できない型」へ変換し、以降は再検証不要にする。
- **ポカヨケ** — 誤用を物理的に不可能（またはコンパイルエラー）にするAPI設計。
- **名前を外側から付ける** — メソッド・APIの名前は呼び出し側（利用者）の視点で付ける。
- **コミュニケーション階層** — 意図の伝達手段を価値の高い順に: ① 良いAPI（型） → ② 分かりやすいメソッド名 → ③ 良いコメント → ④ 自動テスト → ⑤ Gitコミットメッセージ → ⑥ ドキュメント。
- **デメテルの法則** — 内部のさらに内部（孫オブジェクト）へ手を伸ばさない。

### 型で不可能にする

- 不正な状態を表現できる型を作らない。フラグの組（`loading` と任意の `error`）は状態ごとのユニオンに置き換える
- 網羅性検査を効かせる。`switch` に `default` を書かず、種類が増えたらコンパイルを落とす
- 真実の源を1つにし、他はそこから導出する。2つの型が同じ事実を写し合っていたら片方を消す
- 賢い型より、読めば分かる型。型レベルの技巧は境界の誤用を止める場合だけ使う

TypeScript 固有のパターン（ブランド型・NonEmpty・時間範囲・オブジェクト引数）は `typescript-best-practices`。

### 横断的関心事

- ロギング・計測・キャッシュなどはビジネスロジックに混ぜず、デコレーターで包む。
- ストラングラーパターンで段階的に置き換える（ビッグバン書き換えを避ける）。内部 API を置き換えるときは、呼び側を移してから旧 API を消す。互換レイヤを残さない

### 作りすぎを止める

- **足す前に消せるものを探す** — 改善・リファクタを頼まれたら、まず削除の候補を洗う。依頼を満たす最小の差分にする。足した行が消した行より多くの問題を解いているか問う。
- **同じ判断を複数箇所で繰り返さない** — 判断を一箇所に寄せ、結果を単純な値で渡す。
- **シグナルの通しを疑う** — 新しい値を型・スキーマ・パイプラインに通せという要求が来たら、一度立ち止まってより直接的な経路を探す。
- **小さな漏れを早く塞ぐ** — 素通しのラッパー、内部表現の漏れ、重複した判断は、広がる前に消す。小さな漏れは恒久的な調整コストに育つ。

削除候補は思いつきで挙げず、次の反証可能な条件で選ぶ。本番の消費者がいない（テストと文書だけが使っている）／同じ事実を写す表現が2つある／全ての実装が持つが誰も使わない継ぎ目がある／標準ライブラリ・言語機能・既存の依存が既に提供している。薄い推測を多数並べるより、確証のある少数を出す。

## TDD とテストの規律

- **Red → Green → Refactor** の順序を守る。テストなしに実装を書き始めない。
- テストが書きにくいなら設計が悪いというフィードバック（テストの声を聞く）。設計に戻る。
- **Arrange-Act-Assert**: テストは「準備→実行→検証」の3フェーズで構造化する。
- **バグは必ず失敗するテストで再現してから修正する。** 推測で直さない。修正前にその失敗を実際に走らせて示す。「たぶん落ちるはず」は証拠ではない。
- **悪いテストより、テストが無い方がましである。** 誤った保証を固定したテストは、後で削るコストを生む
- **悪魔の代弁者**: 意図的に間違った実装でテストを通そうと試み、通せたらテスト不十分。
- **検証は「誤実装が落ちること」を基準に選ぶ**: テストの価値は正しい実装が通ることではなく、ありうる誤実装が落ちること。境界（ゼロ回・順序・短絡）、全文一致（断片一致では別物が通る）、参照同一性、失敗注入をこの基準で選ぶ。「このテストを通したまま壊す実装が書けるか」を自問し、書けるなら判定力が足りない。
- **入力が固定された判定器は暗記で満たせる。** テストの入力がソースに書き込まれていると、その入力だけを特別扱いする実装で通せてしまう（本物のロジックを一切書かずに）。判定力を上げる手は 2 つ、両方使う: **入力を実行時に生成する**（乱数の seed は固定してよい。固定なのは再現性のためで、値がソースに現れないことが要点）／**期待値を判定器側で計算する**（被験側のコードに期待値を求めさせない。それは受験者が自分の答案を採点する形になる）。「入力を 1 つ足したら出力が追随するか」を確かめると、暗記かどうかが分かる。
- **本番経路のスモークを1本含める**: テストランナーと本番の実行経路が異なる場合（ビルド変換・実行環境の差）、テスト全緑でも本番経路では動かないことがある。本番と同じ経路での実走スモークを1本含める。
- テストとプロダクションコードは**別々に**リファクタリングする（同時に触ると安全網が消える）。
- テスト戦略の形（ピラミッド／ダイヤモンド／逆ピラミッド）は実装パターンに合わせる。選択基準は `ddd-modeling` スキルの references を参照。

## スライスの切り方

- 水平層でなく、入力から永続化まで貫く **vertical slice** で実装する。
- 最初に walking skeleton（アーキテクチャ全体を貫く最薄の end-to-end）を通す。
- アウトサイドイン: 境界（HTTP 等）から始めて内側（ドメイン）へ進める。

## どこに何を書くか

- コードには How のみを書く
- テストには What のみを書く
- コミットログ, プルリクエストには Why のみを書く
- コードコメントには Why not のみを書く

## サボった兆候

規律を飛ばすと、コードに次の見た目で現れる。見つけたら対応する規律に戻る。

- 新機能が既存の if/else を1分岐増やしただけで終わっている
- 同期を取り続けねばならない2つ目のフラグが増えた
- 回避策に、それを正当化する段落コメントが付いている
- 同じ妥当性チェックが複数箇所に現れている
- ロギング・計測がビジネスロジックの中に直書きされている
- メソッド名から副作用の有無が読めない
- 1つのコミットに振る舞いの変更と構造の変更が両方入っている
- バグ修正の差分に、失敗するテストが先に入っていない
- テストとプロダクションコードを同じ手で同時に書き換えている
- 同じ指示をプロンプトに二度書いて、lint / 型 / スクリプトに落としていない
- 内部の旧 API を、呼び側が残ったまま互換レイヤにした
- 訂正を「気をつける」で終え、スキルも検査も増えていない
- 壊れたスキルを、その場の例外手順で回避している
- 再起動・リトライでだけ壊れる不具合を、条件分岐の追加で直している（状態を疑っていない）
- 同じ事実を写す型・定数・スキーマが2つあり、片方を更新し忘れる形になっている

## 判定テスト

- 「このテストを通したまま壊す実装が書けるか」— 書けるなら、テストが見ているのは正しい実装が通ることだけで、ありうる誤実装は落ちない
- 「この関数の分岐と変数を数えたか」— どちらかが8に達しているなら、読み手のワーキングメモリを超えている
- 「不正な状態を持つ値を構築できるか」— できるなら、パースで型に押し込めていない
- 「このメソッドは値を返すか状態を変えるか、どちらか一方か」— 両方なら呼び出し側が推論できない
- 「バグ修正で、先に失敗するテストを書いたか」— 書いていないなら、直ったと言える根拠がない
- 「一つの問いに答えるのに何層辿ったか」— 3を超えるなら平坦にする
- 「表層の書き方をリポジトリの既存コードに合わせたか」— lint 設定・近傍ファイルと食い違っていないか
- 「今回の訂正は、スキルか検査に落ちたか」— 一回限りなら、そう判断した理由があるか
- 「壊れたスキルを回避していないか」
- 「この指摘は2度目か」— 2度目なら、コード修正ではなく機構（手2以上）に落ちているか
- 「同じ事実を写す型が2つないか」— あれば片方を導出に変えたか
