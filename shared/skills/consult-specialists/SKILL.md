# consult-specialists

## 何のためのスキルか

メインエージェントが **「いま自分に欠けている視点／専門性は何か」を判断し、必要な専門家サブエージェントを選んで呼ぶ** ためのスキル。専門家は助言だけでなく **専門領域の作業も実行できる**。最終判断はメインエージェントが行う。

目的は「全員が納得する無難な案」ではなく、**多様な視点で検証された強い意思決定／実装**。

## 12 体の早見表

| エージェント | 何に詳しいか | 何を疑う／重視するか | 典型的な呼び時 |
|--------------|--------------|----------------------|----------------|
| `architect` | システム/境界/抽象化/データモデル/API | 長期的な構造整合性 | 設計判断、境界の引き方、データモデル |
| `solver` | 問題解決/突破/プロト/代替案 | まず動く解 / 制約から逆算 | 詰まった、回避策、最小再現 |
| `tech-lead` | 実装品質/PR 設計/レビュー/プロセス | チームで保守できるか | 方針サニティ、PR 分割、レビュー観点 |
| `qa` | テスト/AC/エッジケース/影響範囲 | 仕様は曖昧、実装は壊れる | AC 整理、境界値、リグレッション |
| `taste` | 体験/情報設計/コピー/一貫性 | 気持ちよさ、わかりやすさ、削ぎ落とし | UI 違和感、文言、空状態、確認 |
| `friction-maximalist` | UX/オンボーディング/認知負荷 | ユーザーは読まない・迷う・離脱する | 初回体験、入力フォーム、ステップ数 |
| `business-realist` | 事業価値/ROI/優先順位/コスト | いま作る価値があるか / 機会費用 | やるか後回しか、スコープ圧縮 |
| `data-realist` | 計測/ログ/KPI/分析 | 測れない成功を疑う | KPI 設計、ログ要件、A/B テスト |
| `failure-pessimist` | SRE/監視/復旧/運用 | 正常系より異常系 | 障害シナリオ、ロールバック、監視 |
| `safety-skeptic` | セキュリティ/権限/漏洩/ポリシー | 悪用される前提 | 攻撃面、権限過剰、ログ漏洩 |
| `contrarian` | 差別化/戦略/尖り/反対意見 | 無難な案を疑う | 全会一致、競合との違い、極端化 |
| `debt-auditor` | 負債/移行/廃止/所有権 | 撤去条件付きで入れる | 暫定対応、フラグ累積、二重管理 |

## 呼び方の判断

### 1. 何が足りないかを言語化する

「専門家を呼ぶ」より先に、**いま自分が答えを出せていない問いは何か** を 1 文で言語化する。

```
例: 「この実装方針、長期で破綻しないかが自分では判断できない」
  → 不足している視点: 構造整合性 → architect
例: 「この機能、本当に今やるべきか分からない」
  → 不足している視点: 機会費用 → business-realist
```

### 2. 1〜3 体を選ぶ（全員は呼ばない）

- 同じ観点を見る人を複数呼ばない（重複は無駄）
- 観点が違う 2-3 体を組み合わせると判断の質が上がる
- 5 体以上呼ぶときは、おそらく問題定義が広すぎる（先に分解する）

### 3. 並列起動を検討する

観点が排他的なら並列に呼んで時間を節約する。観点が依存している（A の結果を B に渡す）なら逐次。

```
並列で良い例: architect / qa / safety-skeptic（観点が独立）
逐次にすべき例: solver でプロト案を出す → tech-lead に現場仕様化を相談
```

## 呼び出しテンプレート

```
Agent({
  subagent_type: "<エージェント名>",
  description: "<3-5 語の作業概要>",
  prompt: """
  ## 文脈
  <何をしている／何に困っているか 3-5 行>

  ## このエージェントに聞きたいこと
  <専門性の範囲で答えられる問い>

  ## 期待する出力
  - 助言モード or 作業モード を明示
  - 各エージェントの出力フォーマットに沿うこと

  ## 既に分かっていること / 制約
  <繰り返し聞かないための前提共有>
  """
})
```

## 助言モード / 作業モード

各エージェントは **2 モード** で動作する:

- **助言モード**: 観点・指摘・推奨を出す。最終判断はメインエージェント。
- **作業モード**: 専門領域の作業を実行する（テスト追加、ログ設計、撤去計画起草、コピー書き換え、攻撃シナリオ列挙、ロールバック手順起草、など）

プロンプトで明示する:
```
「助言として観点を出してほしい」
「作業として実装してほしい」
「助言を出した後、必要なら作業も実行してほしい」
```

## 結果の統合

呼んだ結果が出揃ったら、メインエージェントが以下を整理してユーザーに返す:

1. **採用案**: そのまま反映するもの
2. **棄却案**: 別の観点から却下するもの（却下理由を書く）
3. **保留案**: 追加情報待ち／メインエージェントが判断保留

意見が衝突したときの整理:
- 目的に最も近い視点を優先する
- 制約（時間・コスト・リスク許容度）に照らす
- 「いま動かすこと」 vs 「長期で破綻しないこと」の優先度を明示する

衝突がそれでも解けない場合はメインエージェントが目的・制約・リスク許容度に照らして最終判断する。

## このスキルを使うべきでないとき

- 単純な事実確認・コード片の生成（直接やる方が早い）
- 既に十分な情報が揃っていて、ユーザーの依頼が「これを実行して」のみ
- PR の構造化レビュー → `pr-review` スキルを使う
- 大きめの実装着手 → `superpowers:brainstorming` → `superpowers:writing-plans` → `superpowers:executing-plans`（その中で必要に応じてこのスキルを併用）

## 失敗とみなすもの

- 全員を呼ぶ（観点が冗長になる）
- 1 体しか呼ばないのに「多視点で検証した」と称する
- 専門家の出力をそのままユーザーに返す（メインエージェントによる統合がない）
- 衝突を「両論併記」で逃げる（判断軸を明示していない）

## 評価軸

専門家を呼んだ判断・実装が、以下のうち関係する軸を満たしているかをメインエージェントは自問する:

```
作れるか / 壊れないか / 保守できるか / 使われるか /
事業価値があるか / 測れるか / 安全か / 気持ちいいか / 尖っているか
```

全部を満たす必要はない。**いまの目的にとって重要な軸を選んで、その軸での合格を確認する**。
